# Review: Build Step Metadata Summary vs. the 1500-Byte Stdout Cap

**The plan fails on input it has already seen in testing.**

## Main issue: value sizes are unbounded

- **Keys are bounded, values are not.** Six keys of at most 12 bytes each, plus JSON punctuation (braces, quotes, colons, commas), cost about 125 bytes at most. Values are "written in full" with no limit.
- **The test case already breaks the cap.** Three values of about 700 bytes each come to roughly 2100 bytes. That is well over 1500, before counting the other three values or any overhead.
- **ASCII escaping makes it worse.** Each non-ASCII character becomes `\uXXXX` (6 bytes), or 12 bytes for a surrogate pair. Even if "about 700 bytes" was measured before escaping, the encoded output can be several times larger.
- **The assertion does not prevent failure.** Checking the encoded length before writing stops oversized output from reaching stdout. But a failed assertion still fails the step, and per the harness contract that aborts the release with no retry. The assertion turns a cap violation into a clearer error message, not a passing build. On the observed input, the release aborts either way.

## Minor issues

- **The trailing newline counts.** Make sure the asserted length is exactly the bytes written, including any newline the print call appends. Otherwise a 1500-byte payload can produce 1501 bytes on stdout.
- **The debug log can't hold the overflow.** It is outside the cap, which is correct. But it is a temp file deleted on exit, so it cannot store full values for anyone to read after the build.

## Recommended changes

1. **Give each value a byte budget.** Measure it after escaping. With about 125 bytes of fixed overhead, roughly 220 bytes per value keeps the total under about 1450, leaving margin.
2. **Truncate oversized values with a marker.** For example, `"...(truncated, sha256=abcd1234, len=2104)"`, so the summary stays self-describing.
3. **Save full values somewhere that survives the step.** Write them to a persistent artifact file, outside the cap and not deleted on exit, and put its path or hash in the summary.
4. **Keep the assertion as a last-resort guard.** After truncation it should never fire. Add a test that feeds in the 3×700-byte case and non-ASCII-heavy values to confirm the output stays under 1500 bytes.
