# Review: orders.shipped_at Migration

## Does it work as written?

Yes. Taking the plan's stated facts as given, the sequence holds together:

1. **Add the nullable column.** This is safe and fast on most engines.
2. **Backfill from shipments.** Every order has a non-null `shipped_at` there, so every row gets a value.
3. **Add NOT NULL.** No nulls remain, so the constraint succeeds.

The steps run strictly in order, and the maintenance window removes concurrent-write and lock-contention concerns. Nothing in the plan breaks a rule it states.

## Recommended changes

1. **Add a verification gate before Step 3.** Run `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL;` and abort if it isn't 0. The whole plan depends on the claim that every order has a shipment. Checking it costs little and turns a late failure into a clear one.

2. **Define how multiple shipments per order are handled.** If an order can have more than one shipments row (partial or split shipments), an `UPDATE ... FROM shipments` may pick an arbitrary row. Specify the rule, such as `MIN(shipped_at)` or `MAX(shipped_at)`, and backfill from an aggregated subquery.

3. **Check how new orders will behave after the release.** This is the biggest practical risk. After Step 3, every insert into `orders` must supply `shipped_at`. New orders usually haven't shipped when they're created. If the application inserts orders before shipping, inserts will fail once the window closes. Confirm one of these:
   - The app writes `shipped_at` at insert time, or
   - The column should stay nullable, or
   - The NOT NULL rule really fits the domain.

4. **Make the backfill reliable to run.**
   - Batch the 2M-row update (for example, by primary key ranges) to limit transaction log or WAL growth and lock duration.
   - Measure the runtime on a production-sized copy to confirm it fits the window.

5. **Tighten the rollback.**
   - State whether the steps run in one transaction. Transactional DDL works in Postgres but not in MySQL.
   - Make the rollback idempotent (`DROP COLUMN IF EXISTS`).
   - Add a plan for rolling back after all steps succeed but the app misbehaves. Dropping the column at that point needs the app's cooperation.

6. **Confirm the app deploy order.** Code that reads `shipped_at` should ship after the migration, or tolerate the column being absent.

## Summary

The migration will run successfully as specified. Its main weaknesses are a missing pre-constraint check, unclear handling of duplicate shipments, and an untested assumption that new orders can satisfy NOT NULL. These are improvements, not blockers.
