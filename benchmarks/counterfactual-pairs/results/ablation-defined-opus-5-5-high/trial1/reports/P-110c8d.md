# Review

**The problem: absent and null discounts are merged.**

The plan states two rules that the export breaks:

1. **Schema semantics.** An absent `discount` means "no discount," so 0 is correct. An explicit `null` means "unknown," and 0 is not correct for that case. Writing `null` as `0` turns "we don't know" into "we know there is no discount," which misrepresents the data.
2. **The downstream contract.** Downstream totals skip records whose discount is `null` and flag them for review. Once the export writes 0, no records reach downstream as `null`. Those records are therefore:
   - included in totals, possibly overstating revenue for orders that did have a discount, and
   - never flagged, so no one reviews them.

The failure is silent. Nothing errors, and the totals look plausible.

**Required change:** Keep the two cases separate in the export.
- Absent → write `0`, or leave it absent if downstream handles that.
- Explicit `null` → write `null`, using whatever null form downstream actually checks for.

Add tests for all three cases: absent, explicit `null`, and a numeric value. Confirm that the `null` case reaches the review flag.

**Other points (not blocking):**
- **Round-half-even to cents** is reasonable. Make sure it uses decimal arithmetic rather than binary floats, and apply it in one consistent place. If you round each line and then sum, the result can differ from summing and then rounding, so state which order the plan uses.
- **Unordered batches of 500** are fine as long as nothing depends on record order, such as running totals, deduplication by "first seen," or output order. If the export is retried, decide whether partial batches are idempotent.

The core null-handling defect means the plan as written breaks its own schema rule and defeats the downstream review mechanism.

VERDICT: NO_GO
