# Review: `orders.shipped_at` migration

## Blocking issue: the execution order fails

The plan runs the steps as **1 → 3 → 2**, which means the NOT NULL constraint is applied before the backfill:

1. **Step 1** adds `shipped_at` as nullable. All ~2 million existing rows now have `shipped_at = NULL`.
2. **Step 3** adds `NOT NULL`. The database validates existing rows, finds ~2 million NULLs, and **the step fails**. (Postgres: `column "shipped_at" contains null values`. MySQL in strict mode errors similarly. In non-strict mode MySQL may silently coerce NULLs to a zero date, which is worse.)
3. **Step 2** never runs, because the rollback fires and drops the column.

The rollback leaves the table in a clean state, so nothing is corrupted. But the migration as written cannot succeed on a non-empty table, which meets the NO_GO definition: "the plan as written will fail."

**Fix:** run the steps in the order **1 → 2 → 3** (add the nullable column, backfill, then add the constraint).

## Recommended improvements (after reordering)

- **Verify before constraining.** Between steps 2 and 3, run `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL;` and require 0. The plan says shipments covers every order, but this check proves it cheaply. It also catches orphaned orders or join mistakes.
- **Handle duplicate shipments.** If an order can have more than one shipment row, the UPDATE...FROM/JOIN may choose a row arbitrarily. Decide which value is correct (for example `MIN(shipped_at)` for the first shipment) and use it explicitly.
- **Block writes during the window.** Rows inserted between steps 2 and 3 would have NULL `shipped_at` and make step 3 fail. Confirm the application is stopped, or make the insert path populate the column.
- **Size the backfill.** Updating 2M rows in one transaction is usually fine in a maintenance window. Still, estimate the duration, WAL/binlog volume, and lock time on a staging copy. Batch the update if the window is tight.
- **Test the rollback.** Dropping the column is correct at every stage. Run it once in staging to confirm it works if a step fails partway.

## Summary

The steps themselves are sound, but running them as 1 → 3 → 2 guarantees that step 3 fails on 2 million NULL rows. Reorder to 1 → 2 → 3 and add a NULL-count check before the constraint.
