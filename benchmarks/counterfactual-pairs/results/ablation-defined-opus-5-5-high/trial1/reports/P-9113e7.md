# Plan Review: Nightly Batch

## The timing doesn't fit the deadline

The stages run one after another, so their durations add up.

| Stage | Typical | Max (last 30 runs) |
|---|---|---|
| 1. Import | 22 min | 25 min |
| 2. Transform | 18 min | 21 min |
| 3. Export | 12 min | 14 min |
| **Total** | **52 min** | **60 min** |
| Deadline | 45 min | 45 min |
| **Over by** | **7 min** | **15 min** |

A typical run already goes 7 minutes past the 45-minute deadline. Worst case goes 15 minutes past. This is not an edge case where variance occasionally pushes a run over. Based on the measured numbers, most nights will be killed and that day's data will be lost. Even if all three stages hit their best plausible times, the averages suggest the batch rarely, if ever, finishes in time.

## Secondary issue: failures may go unnoticed

The summary email goes out "when the batch ends." If an overrunning batch is killed, it's unclear whether the email still gets sent. If it doesn't, on-call gets no signal on exactly the nights data is lost. Silence would look the same as success unless someone notices the missing email. Failure alerting should come from something outside the batch, such as a watchdog or the scheduler's kill handler. It should not depend on the batch finishing normally.

## What would need to change

At least one of these is needed, and the combined effect must close a gap of more than 15 minutes in the worst case:

1. **Overlap or parallelize stages.** For example, stream records from import into transform, or partition the data and run partitions in parallel. The plan says stages "never overlap," which rules this out as written.
2. **Speed up the stages.** Transform and import are the biggest stages, so they're the best targets. Together the stages need to lose about 15+ minutes in the worst case, plus a safety margin.
3. **Change the deadline** or start the batch earlier, if the 45-minute limit is set by a window that can move.
4. **Make failures recoverable.** Checkpoint after each stage so a killed run can resume instead of losing the day's data. Also add a failure alert that doesn't depend on the batch finishing.

I'd aim for a worst-case total well under 45 minutes, for example 35–40, rather than just squeaking under.

## Conclusion

The plan breaks its own hard deadline under normal conditions, not only in the worst case. As written, it will lose data most nights.
