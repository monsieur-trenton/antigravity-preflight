## Review

**The core problem is that the plan iterates over the wrong set.**

The requirement is that the report cover **all four supplied sources exactly once**, and the checker rejects any report whose coverage set differs from the supplied inventory. The plan, however, builds one section per source **that changed in the diff**.

These two sets are usually different:

- In a typical diff, only one or two of the four sources change.
- So a typical report would cover only 1–2 sources, leaving 2–3 missing.
- The checker would reject it, and it would be marked **INCOMPLETE**, which means it is never recommended for readiness.

This is not an occasional edge case. Under the plan's own stated assumptions, it fails on the common path. It only succeeds in the unusual case where all four sources change in the same diff.

**Required fix:**
- Iterate over the **supplied inventory** of four sources, not the diff.
- Emit exactly one section per inventory entry, so there are no omissions and no duplicates.
- The diff can still be used to annotate each section (for example, "changed" or "unchanged"), but it must not decide which sections exist.
- Add a pre-submit check that the set of covered sources equals the inventory set, so any mismatch is caught before the checker sees it.

**Smaller points (not blocking on their own):**
- Each section lists the SHA-256 and line count. Make sure these are computed from the actual source content in the inventory, including for unchanged sources. They should not be taken only from diff hunks, which would not exist for sources that didn't change.
- State the line-counting convention, such as how a trailing newline without content is counted, so the counts are reproducible.

## Conclusion

As written, the plan breaks its own coverage rule in the typical case. The resulting reports would be rejected and marked INCOMPLETE. This is a failure of the plan, not just room for improvement.
