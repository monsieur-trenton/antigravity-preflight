## Review

**The plan contradicts its own core rule.**

- **Rule:** All four supplied sources must appear in the report exactly once. If the covered sources don't match the supplied inventory, the checker rejects the report.
- **Mechanism:** The report loops only over sources touched by the diff.
- **Typical case:** Only one or two of the four sources change.

So in the normal case the report covers 1–2 sources instead of 4. Every such report:
1. Fails the checker's inventory match and is rejected.
2. Gets labelled INCOMPLETE and can't be recommended for readiness.

This is not an edge case. As written, the plan will fail on most runs. It only works when a diff happens to touch all four sources.

**Required fix:** Loop over the full supplied inventory of four sources, not the diff. Each section can still note whether the diff touched that source, but every source needs a section regardless.

**Secondary suggestions** (not blocking once the loop is fixed):
- **Exactly once:** Iterate over a de-duplicated inventory and assert the section count equals the inventory size. A source listed twice, or reached via two paths, could otherwise produce a duplicate section.
- **SHA-256 and line count:** Compute both from the same snapshot of each file (e.g., read the bytes once and derive both values). This keeps the hash and count consistent with each other.
- **Line counting:** Define how you count lines, especially for a file with no trailing newline, so results are reproducible.
- **Pre-flight check:** Before submitting, compare the report's covered-source set against the inventory. This catches mismatches before the checker does.
