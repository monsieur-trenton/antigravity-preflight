# Review: Adding `shipped_at` to `orders`

## Does the plan work as written?

Yes. The sequence is sound:

1. **Add nullable column.** This is a cheap metadata change on most engines.
2. **Backfill from `shipments`.** The plan says every order has a non-null `shipped_at` there, so after this step every row has a value.
3. **Add NOT NULL.** This succeeds because step 2 left no nulls.

The rollback restores the original schema. The steps run in strict order, and the maintenance window rules out concurrent writes. Nothing in the plan, as stated, fails or breaks its own rules.

## Recommended improvements

1. **Make the rollback idempotent.** If step 1 fails, the column doesn't exist, and a plain `DROP COLUMN` will error. Use `DROP COLUMN IF EXISTS`. Better still, run all three steps in one transaction where the engine supports transactional DDL (e.g. PostgreSQL). A failure then rolls back automatically and the rollback script becomes a fallback.

2. **Verify the "every order has a shipment" premise before step 2.** Step 3 depends on it. Run a pre-check such as:
   ```sql
   SELECT count(*) FROM orders o
   LEFT JOIN shipments s ON s.order_id = o.id
   WHERE s.order_id IS NULL OR s.shipped_at IS NULL;
   ```
   Abort early if the count is non-zero. Then run the same null check after step 2, before step 3.

3. **Define the rule for orders with several shipments.** If `shipments` is one-to-many, `UPDATE ... FROM` will pick an arbitrary row, which can differ between runs. State the rule explicitly, e.g. `MIN(shipped_at)` for first shipment or `MAX` for the final one.

4. **Consider batching the 2M-row update.** A single update works, but it holds row locks for its full duration and produces a large burst of WAL/undo. It also leaves many dead tuples, so plan a `VACUUM`/`ANALYZE` afterward. Batching by primary key range, say 50k rows per batch, keeps each unit short and the progress visible. If you batch, the single-transaction approach from point 1 no longer applies. Choose one approach on purpose.

5. **Confirm writes are actually blocked.** Make sure application writes, cron jobs, and replicas or CDC consumers are stopped for the window. Any order inserted between steps 2 and 3 without `shipped_at` would make step 3 fail.

6. **Rehearse on a production-sized copy.** This tells you how long the update and constraint validation take. On some engines, adding NOT NULL scans the full table. Make sure the timing fits inside the window.

## Summary

Given the stated assumptions, the plan is correct. The changes above make it more robust: an idempotent or transactional rollback, explicit checks of the data assumption, a defined rule for multiple shipments, and batching or timing for the large update.
