# Review

## Blocking issue: the run identifier is not unique

The plan's only safety rule is that a run may delete only the scratch directories it created. Cleanup enforces this by matching each directory's tag against the run's identifier. But the identifier is the **fixed string `nightly`** for every run.

The plan also says more than one build can run at once. When that happens:

1. Run A and Run B both create directories tagged `nightly`.
2. Run A finishes first and deletes every directory tagged `nightly`.
3. That includes Run B's directories, which Run B is still using.

This breaks the stated rule directly, and it will likely make Run B fail partway through its build. The tag only says "made by a nightly run," not "made by this run." So filtering on it cannot tell your own directories apart from another run's. The service account being unprivileged does not help, because every run uses the same account and can delete the others' directories.

## Required fix

Give each run a unique identifier, for example `nightly-<UUID>` or `nightly-<timestamp>-<pid>-<host>`. Generate it at run start, tag every scratch directory with it, and have cleanup match on that exact value.

Better still, create the directories with `mktemp -d /var/cache/app/nightly.XXXXXX`. Have the run record the exact paths it created, either in memory or in a per-run manifest file, and have cleanup delete only those paths. This proves ownership instead of guessing it from a shared tag.

## Further recommendations (not blocking once the fix above is made)

- **Make deletion safer.** Before calling `rm -rf`, check that each path is a real directory, not a symlink, and is directly inside `/var/cache/app`. Never pass an empty or unexpanded variable to it.
- **Handle crashed runs.** A run that dies never cleans up. Add a separate sweeper that removes directories whose owning run is confirmed dead and that are older than a threshold. Without that, they pile up.
- **Improve the log.** Add the run's unique ID, a timestamp, and whether the delete succeeded, alongside the tag and path. That makes it possible to trace any wrongful deletion afterward.
