# Review of the Nightly Batch Plan

## Timing check

| Stage | Typical | Observed max (30 runs) |
|---|---|---|
| 1. Import | ~22 min | 25 min |
| 2. Transform | ~18 min | 21 min |
| 3. Export | ~12 min | 14 min |
| **Total (sequential)** | **~52 min** | **60 min** |

- **Typical runs** finish about 23 minutes inside the 75-minute deadline.
- **Worst case** assumes every stage hits its maximum on the same night. That run still finishes at 60 minutes, with 15 minutes (20%) to spare.

The plan meets its stated hard deadline. It is not a NO_GO.

## Weaknesses worth fixing

1. **No alert when the batch is killed.** The summary email is sent "when the batch ends." A run killed at 75 minutes may never reach that step, so the worst failure (losing a day's data) could happen silently. Send an alert from outside the batch, such as a watchdog or scheduler hook, on kill or timeout. Alternatively, alert when no summary arrives by an expected time.

2. **Overhead isn't counted.** The 60-minute worst case covers only the three stages. Startup, handoffs between stages, and sending the email also take time. These are probably small, but they should be measured and added to the budget.

3. **The margin may shrink over time.** Thirty runs is roughly one month of history. If data volumes grow, stage times will rise. Track runtime trends and set an early warning, for example at 65 minutes, so you can act before reaching the hard limit.

4. **A single kill loses the whole day.** With nothing checkpointed between stages, an overrun throws away work that already finished. Saving each stage's output would allow a restart or a catch-up run instead of total loss.

5. **Infrastructure risks aren't covered.** Thirty clean runs don't capture rare events such as slow storage, a source system outage, or contention with other jobs. Decide in advance what happens if, for example, import is still running at minute 50. One option is to abort early and alert rather than run into the kill.

## Summary

As written, the plan works: even the observed worst case finishes 15 minutes early. Its main gap is how failures are handled and reported, especially the risk that a killed run sends no notification. That makes improvements advisable but not blocking.
