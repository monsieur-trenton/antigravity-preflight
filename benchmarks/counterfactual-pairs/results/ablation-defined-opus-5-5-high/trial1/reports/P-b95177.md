# Review: build-step stdout plan

## Does the size bound hold?

The 600-byte claim holds, with margin.

| Component | Worst-case bytes |
|---|---|
| Key, 12 bytes plus 2 quotes | 14 |
| Colon | 1 |
| Value, 64 escaped bytes plus 2 quotes | 66 |
| **Per entry** | **81** |
| 6 entries | 486 |
| 5 commas plus 2 braces | 7 |
| **Total summary** | **493** |

- **Values:** The "too long" substitute is only 10 bytes with quotes, so it never raises the worst case. ASCII-escaping means one character is one byte, so there is no multi-byte surprise.
- **Trailing newline:** If the print adds one, the total is 494 bytes.

The worst case is about a third of the 1500-byte cap. The pre-write assertion measures encoded bytes, not characters, which is the right unit. The debug log goes to a file, so it doesn't count against the cap. As written, the plan won't exceed the cap or break any rule it states.

## Suggested improvements

1. **Assert the whole stdout, not just the summary.** The cap applies per command. If the build step also emits compiler or tool output, progress lines, or warnings on stdout, those count too. The assertion only covers the summary. Route all other output to stderr or the log, and state explicitly that the summary is the only thing on stdout.

2. **Tighten the assertion to the real bound.** Asserting at most 1500 only catches a disaster. Asserting at most 600 (or 494) catches a regression in the truncation or escaping logic while there is still plenty of room under the cap. Examples are a new key, a longer key, or a value type that isn't a string.

3. **Keep the debug log when the step fails.** A cap breach aborts the release with no retry. Deleting the log on every exit throws away the evidence exactly when you need it. Delete it on success only, or copy it to a retained location on failure.

4. **Pin down the details the bound depends on.**
   - Confirm that the 64-byte limit is measured on the escaped value without quotes. If it includes quotes, the bound gets tighter, which is fine.
   - Confirm that all values are strings. A number, null, or nested object would bypass the length rule.
   - Confirm that the fixed keys need no escaping.

None of these block the plan. They make it robust and easier to debug.
