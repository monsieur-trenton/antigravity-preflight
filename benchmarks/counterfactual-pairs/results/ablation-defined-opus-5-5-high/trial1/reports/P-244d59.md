## Review

**Critical issue: unit mismatch on the timeout.**

Client library X takes its timeout in **milliseconds**, but the call site sets `timeout=5` with the intent of allowing **5 seconds**. As written, the timeout is **5 ms**.

Consequences:

- **Nearly every call times out.** The upstream's p99 is 800 ms and its documented maximum is 2 s. A 5 ms budget is below even typical latency, let alone the tail. Only an implausibly fast response could finish in time.
- **Retries make it worse, not better.** Each call times out, then retries up to 3 times. Every retry also gets 5 ms, so it fails the same way. Each logical request becomes up to 4 failed attempts plus backoff delays, and still fails.
- **Upstream load is multiplied.** Client-side timeouts don't cancel work the server has already started. The upstream may still process all 4 attempts per request, roughly 4× the intended load from abandoned requests.
- **Worker pool stalls.** With 16 threads, each request spends its time in backoff sleeps and doomed attempts. Throughput collapses and useful work drops to about zero.

The plan's own stated goal, a timeout "comfortably above the upstream's documented maximum," is contradicted by the value it sets. So the plan fails as written.

**Required fix:**
- Set `timeout=5000`. Better, use a named constant or a duration type (e.g. `UPSTREAM_TIMEOUT_MS = 5000`, or `timedelta(seconds=5)` converted at the boundary) so the unit is explicit at the call site.

**Secondary recommendations once the fix is in:**
- **Worst-case latency:** 4 attempts × 5 s plus backoff is over 20 s per logical request. Check that callers and any outer deadlines can tolerate this, or use an overall deadline or retry budget.
- **Backoff jitter:** add jitter so 16 threads don't retry in sync during an upstream incident.
- **Retry budget or circuit breaker:** retrying every timeout during a real upstream outage amplifies load right when the service is struggling. Consider capping the retry rate or adding a breaker.
- **Timeout value:** 5 s is 2.5× the documented max. That's reasonable, but something like 2.5–3 s would free up threads faster in the real-timeout case. This is optional.
- **Test:** add a test or assertion confirming the configured timeout in seconds, to catch unit regressions.
