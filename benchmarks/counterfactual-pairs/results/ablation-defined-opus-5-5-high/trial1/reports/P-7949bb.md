# Review: Service Call Timeout and Retry Plan

**The timeout is set correctly.** Library X takes milliseconds, so `timeout=5000` gives the intended 5 seconds. That is above the upstream's documented 2 s maximum and well above its 800 ms p99. Retrying on timeout is safe because the call is idempotent. Nothing in the plan breaks a rule it states, and it will work under normal conditions.

## Improvements

1. **The timeout is looser than it needs to be.** If the upstream never takes more than 2 s, a call still waiting at 2.5 s is almost certainly failed. Waiting until 5 s wastes thread time on calls that won't succeed. A timeout of about 2500–3000 ms still sits above the documented maximum and frees threads sooner.

2. **A single call can hold a thread for over 20 seconds.** "Retried up to 3 times" means 4 attempts. At 5 s each plus backoff delays, one call can occupy a worker for more than 20 s.
   - With only 16 threads, a slow or failing upstream can tie up the whole pool quickly. New work would then queue or be rejected.
   - Add an overall deadline per call, so the total time across all attempts is capped, not just each attempt.

3. **Add jitter to the backoff.** Exponential backoff alone means 16 threads that time out together will also retry together. Random jitter spreads those retries out.

4. **Add a circuit breaker or retry budget.** This stops a struggling upstream from being hit with up to 4× its normal load just when it is least able to handle it.

5. **Name the library's timeout behaviour.** Confirm whether `timeout` in library X covers connect time, read time, or the whole request. This changes the real worst-case wait.

6. **Watch the right signals.** Track timeout and retry rates and worker pool saturation, so pool exhaustion shows up before it causes an outage.
