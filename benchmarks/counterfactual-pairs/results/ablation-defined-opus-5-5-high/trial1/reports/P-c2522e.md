# Review: Orders Table `shipped_at` Migration

## Blocking issue: the execution order makes the plan fail

The plan requires the steps to run strictly as **1 → 3 → 2**:

1. **Step 1** adds `shipped_at` as nullable. All ~2 million existing rows now have `shipped_at = NULL`.
2. **Step 3** adds `NOT NULL` to `shipped_at`. The database checks existing rows when the constraint is added. About 2 million rows are NULL, so the step fails. (On PostgreSQL, for example, it fails with "column contains null values". Other engines either reject it or, like MySQL in non-strict mode, silently coerce the NULLs to a zero or default value, which corrupts the data.)
3. **Step 2**, the backfill, never runs. The rollback drops the column.

The plan as written can't succeed. The fix is to use the logical order **1 → 2 → 3**: add the nullable column, backfill it, then enforce `NOT NULL`.

## Other issues to fix while revising

- **Verify the "every order has a shipment" assumption before Step 3.** The plan says the shipments table has a non-null `shipped_at` for every order. That premise needs checking, not assuming. Orders that are unshipped, cancelled, or pending would have no shipment row. Run a pre-check such as `SELECT COUNT(*) FROM orders o LEFT JOIN shipments s ON s.order_id = o.id WHERE s.shipped_at IS NULL` and confirm it returns 0. If it doesn't, `NOT NULL` is the wrong constraint for this column.
- **Handle orders with multiple shipments.** If one order can have several shipment rows, the backfill needs a defined rule, such as `MIN(shipped_at)` or `MAX(shipped_at)`. Otherwise the UPDATE…FROM/JOIN result is nondeterministic, or it errors.
- **Block or account for writes during the window.** New orders inserted between the backfill and the constraint would have NULL `shipped_at`. Confirm that application writes are stopped. Also confirm that the application sets `shipped_at` on insert once the constraint exists, or new order creation will start failing after the release.
- **Batch the backfill.** A single 2M-row UPDATE inflates WAL/redo and holds locks for a long time. Batching (say 10k–50k rows per transaction) makes it more predictable and lets you monitor progress.
- **Validate before enforcing.** Add an explicit `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL` = 0 gate between Steps 2 and 3, rather than relying on Step 3 failing.
- **Rollback scope.** Dropping the column is a correct and safe rollback here, since the column is new and no existing data is lost. Make sure the rollback also runs cleanly if the failure happens partway through a batched backfill, and that any application code deployed alongside the migration is rolled back too.
- **Timing.** Rehearse on a production-sized copy so you know the backfill and constraint-validation times fit inside the maintenance window.

## Summary

The stated order (1 → 3 → 2) puts the `NOT NULL` constraint on a column that is entirely NULL, so the migration fails at Step 3. Reordering to 1 → 2 → 3 and adding the verification gates above would make the plan sound.
