## Review: Nightly Compaction Plan

### Can the job finish in the window?

Finishing 40 GB in 30 minutes needs a sustained rate of about **22 MB/s** (40,000 MB ÷ 1,800 s). One thread on reasonable hardware can often reach that, but nobody has measured it on the target host. Success is plausible but unproven.

### Does the plan fail or break a rule it states?

No. The plan says what happens on overrun: the step is cancelled and the cancellation is reported. An overrun therefore follows the plan rather than breaking it. Nothing as written is guaranteed to fail, so this is not a NO_GO.

### Gaps that should be fixed

1. **Measure throughput first.** Run a benchmark on the target host, using representative data, before relying on the window. Without it, nobody knows whether the plan normally completes or normally cancels.

2. **State what cancellation leaves behind.** The plan does not say whether a cancelled run:
   - leaves the original data intact,
   - discards partial output cleanly, or
   - leaves a half-compacted state that needs cleanup.

   Compaction should write to a temporary location and swap atomically, or be crash-safe by design.

3. **Plan for repeated cancellation.** If throughput is marginal, the job could cancel every night and compaction would never finish. Either make it resumable (checkpoint progress so the next run continues) or add an alert after N consecutive cancellations.

4. **Use the progress logs to stop early.** The per-minute logs could feed a projected finish time. If the projection clearly exceeds 30 minutes, the step can stop early and save the remaining window.

5. **Keep parallelism as a fallback.** If measured single-thread throughput is near or below 22 MB/s, consider multiple threads or partitioning the input, provided the compaction format allows it.

6. **Allow for input growth.** "Roughly 40 GB" will probably grow. Size the window, or the throughput target, with headroom, and track the trend.

### Summary

The plan is internally consistent and handles overrun explicitly. However, its feasibility is unverified, cancellation safety is unspecified, and nothing prevents the job from cancelling every night. It works as written but should be tightened along these lines.
