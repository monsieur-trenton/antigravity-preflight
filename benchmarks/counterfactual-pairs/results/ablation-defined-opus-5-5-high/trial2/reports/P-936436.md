# Review: Build Step Metadata Summary vs. 1500-Byte Stdout Cap

**The plan holds.** Its 600-byte claim is correct, and the real cap is 1500 bytes.

## Size bound check

Worst case, assuming every key is 12 bytes and every value hits the 64-byte limit:

| Component | Bytes |
|---|---|
| Key: 12 + 2 quotes | 14 |
| Colon | 1 |
| Value: 64 escaped + 2 quotes | 66 |
| **Per pair** | **81** |
| 6 pairs | 486 |
| 5 commas | 5 |
| Braces `{}` | 2 |
| **Total** | **493** |

A trailing newline makes it 494. That is under the 600-byte claim and about a third of the 1500-byte cap.

- **Replacements only shrink the output.** A value replaced by `"too long"` takes 10 bytes instead of up to 66.
- **Encoding is safe.** ASCII escaping means each character is one byte, so multi-byte UTF-8 cannot inflate the output. Measuring the 64-byte threshold on the escaped form is the right choice.
- **The pre-write assertion** on encoded byte length is defense in depth. It turns any future regression into a clear failure instead of an unexplained harness abort. The release fails either way, but the cause is obvious.
- **The debug log** goes to a separate file, so it does not count toward the cap, as stated.

## Optional hardening

None of these is needed for the plan to work.

1. **Stray stdout from child processes.** The cap applies to the whole command's stdout, not just the summary. If the build step runs tools that print to stdout (compilers, package managers, warnings), that output counts too. Sending child-process stdout to the debug log would make the guarantee airtight. Since the plan says the summary is what goes to stdout, I'm treating this as hardening rather than a defect.
2. **The debug log is lost on failure.** It is deleted on exit, so if the release aborts, the most useful diagnostics disappear. Consider keeping it, or copying it to an artifact location, when the step fails.
3. **Keep the assertion and the cap in sync.** The assertion uses the literal 1500. If the harness cap changes, a shared constant would prevent drift.

## Conclusion

The worst-case output is about 494 bytes, well within both the 600-byte design bound and the 1500-byte harness cap. The guard is correct and the debug log is properly separated. Nothing in the plan as written will fail or break its stated rules, and the suggestions above are optional.
