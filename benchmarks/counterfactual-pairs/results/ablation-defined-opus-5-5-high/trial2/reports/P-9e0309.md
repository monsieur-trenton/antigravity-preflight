# Plan Review: Order Export Discount Handling

The core logic is correct. The plan works as written, but a few gaps should be closed before implementation.

## What's correct

- **Absent becomes 0.** The schema says absent means no discount, so 0 is the right value.
- **Null stays null.** The schema says null means unknown. Passing it through keeps that meaning and avoids silently turning unknown into zero.
- **Downstream skips and flags nulls.** Unknown values don't contaminate totals, and they get surfaced for a person to check.
- **Round-half-even** is a sound choice for money because it avoids upward bias across many records.
- **Unordered batches of 500** are fine because each record is handled on its own.

No rule in the plan is broken, and nothing will fail as written.

## Recommended changes

1. **Say where rounding happens.** Rounding each record and then summing can give a different result than summing first and rounding once. The plan should name the step, for example "round each line to cents, then sum the rounded values."

2. **Require exact decimal arithmetic.** If amounts are binary floats, summing in a different order can change the result slightly, and batches here run in no particular order. Decimal or integer-cent types make totals the same on every run.

3. **Define what "skip" excludes.** It's unclear whether a null-discount record is dropped from all totals, including gross, or only from the net/discount totals. Whichever is chosen, reports should show the count and value of skipped records so totals aren't silently understated.

4. **Keep null distinct from absent in the output.** Confirm that the export format and serializer write an explicit `null` and don't drop null fields. If they drop them, downstream would read the field as absent and treat it as 0.

5. **Optional: validate discount values.** Decide how to handle negative values, values larger than the order amount, and non-numeric values.
