# Plan Review: Scratch Directory Cleanup

## The blocking problem: the run identifier is not unique

The plan's safety rests on one rule:

> A run may remove only the scratch directories that it made itself, and never directories made by another run.

Cleanup enforces this by matching each directory's tag against the run's identifier. But that identifier is **the fixed string `nightly`**, so every run has the same one.

The plan also says **more than one build run can be going at once.** Together, these facts break the rule:

1. Run A starts and creates `/var/cache/app/scratch-1`, tagged `nightly`.
2. Run B starts and creates `/var/cache/app/scratch-2`, tagged `nightly`.
3. Run A finishes. Cleanup selects every directory tagged `nightly`, which includes `scratch-2`.
4. Run A runs `rm -rf` on Run B's directory while Run B is still using it.

This is the normal concurrent case, not a rare edge case. Run B will likely fail partway through or produce corrupt output. The plan breaks the rule it sets for itself. The deletion log won't prevent this. It will only record it.

## Required fix

Give each run a unique identity and limit cleanup to that identity. Options, from most to least preferred:

- **Record what the run created.** Each run keeps a list of the exact paths it made, in memory or in a per-run file. Cleanup deletes only those paths. This doesn't depend on tags at all.
- **Use a unique run identifier.** For example, `nightly-<UUID>` or `nightly-<timestamp>-<pid>`. Tag directories with it and match it exactly at cleanup.
- **Give each run its own parent directory.** For example, create `/var/cache/app/run-<unique-id>/` with `mktemp -d` and put all scratch directories inside it. Cleanup removes only that one parent.

## Other improvements (not blocking on their own)

- **Use `mktemp -d` to create directories.** This prevents name collisions between concurrent runs and avoids predictable paths in a shared directory.
- **Don't follow symlinks.** Before deleting, check that each target is a real directory inside `/var/cache/app` and not a symlink. Resolve the path and confirm the prefix. `rm -rf` on a swapped or symlinked path could delete things outside the cache, limited only by what the service account can write.
- **Guard against empty or malformed paths.** Refuse to delete if the path is empty, `/`, or `/var/cache/app` itself.
- **Plan for crashed runs.** A run that dies never cleans up, and with unique IDs nothing else will either. Add a separate sweeper that removes directories only after their owning run is confirmed dead, using an age threshold plus a liveness check such as a lock file or PID.
- **Log the run ID and the outcome.** Include the run's unique ID and whether each deletion succeeded, not just the tag and path.
- **Keep the unprivileged service account.** It limits the damage if something goes wrong.

## Summary

The design is reasonable, but its ownership check is meaningless because every run has the same identifier. With concurrent runs, one run's cleanup will delete another run's active scratch directories. That directly breaks the stated rule, so the plan can't proceed as written.
