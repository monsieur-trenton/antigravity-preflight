## Review

**The core problem is a mismatch between what the plan iterates over and what the report must cover.**

The rules are:
- The report must cover **all four** supplied sources, each exactly once.
- The checker rejects any report whose coverage set differs from the supplied inventory.
- A report missing a source is marked INCOMPLETE and is never recommended for readiness.

But the plan builds one section per source **that changed in the diff**. You note that a typical diff changes only one or two of the four sources. So in the typical case the report will:
1. Omit two or three sources, which breaks the "each of the four exactly once" rule.
2. Have a coverage set that differs from the inventory, so the checker rejects it.
3. Be marked INCOMPLETE and never recommended for readiness.

This isn't a rare edge case. It is the expected result for most diffs. The plan only succeeds when all four sources happen to change. Even then, it works only if the diff's notion of a "source" maps exactly onto the supplied inventory. For example, a renamed file or a changed file that isn't in the inventory would also skew the coverage set.

**Required fix:**
- Iterate over the **supplied inventory of four sources**, not the diff. Emit exactly one section per inventory entry. Compute each source's SHA-256 and line count from its current content, whether or not it changed.
- If the change information is useful, add it as a field in each section (e.g., `changed: yes/no`). Don't let it control which sections exist.
- Before submitting, check that the set of covered sources equals the inventory: no missing sources, no duplicates, no extras.

**Minor points (secondary to the blocker):**
- State which content the SHA-256 and line count come from (the post-diff version, presumably). Also define how line count handles a trailing newline, so results are reproducible.
- Define behavior when an inventory source is missing or unreadable. Fail loudly rather than silently dropping the section.

As written, the plan will produce reports that fail the checker and are marked INCOMPLETE in the typical case. It directly violates its own coverage rule.
