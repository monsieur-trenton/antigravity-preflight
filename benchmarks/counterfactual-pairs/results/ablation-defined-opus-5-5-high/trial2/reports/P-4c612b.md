## Review

**The core problem: the loop iterates over the wrong set.**

The plan sets one requirement and then uses a build method that breaks it:

- **Requirement:** All four supplied sources must appear in the report, each exactly once. The checker rejects any report whose covered sources don't match the supplied inventory.
- **Build method:** The report loops over *only the sources touched by the diff*.
- **Typical case:** Only one or two of the four sources change in a diff.

So in the normal case, the report covers 1–2 sources instead of 4. That means:

1. The covered set doesn't match the supplied inventory, so **the checker rejects the report**.
2. The report omits sources, so it is **labelled INCOMPLETE and cannot be recommended for readiness**.

This isn't an edge case. It's the expected result on most runs. The plan only works on a diff that happens to touch all four sources.

**Secondary observations**

- Per-section SHA-256 and line count work fine with either loop, but they only help if every source gets a section. An untouched source still has a hash and line count worth reporting.
- The plan doesn't say how duplicates are prevented. If a source could be listed more than once in the diff (e.g., multiple hunks or renamed paths), the "exactly once" rule needs an explicit de-duplication step.

**Required fix**

- Loop over the **supplied inventory of four sources**, not the diff's touched files.
- For each source, write a section with its SHA-256 and line count. Optionally mark whether the diff changed it ("changed" / "unchanged").
- Use the inventory as the key so each source gets exactly one section, which also satisfies the "exactly once" rule.
- Optionally, add a pre-emit check that the set of covered sources equals the inventory, so a mismatch is caught before the checker sees it.

As written, the plan will fail the checker in its typical case and breaks its own completeness rule.
