# Review: orders.shipped_at Migration Plan

## Blocking issue: the execution order makes Step 3 fail

The plan requires the steps to run strictly as **1 → 3 → 2**. In that order:

1. **Step 1** adds `shipped_at` as nullable. All ~2 million existing rows now have `shipped_at = NULL`.
2. **Step 3** then adds `NOT NULL` to `shipped_at`. Every existing row violates the constraint, so the database rejects it (e.g., PostgreSQL: `column "shipped_at" contains null values`; MySQL in strict mode errors similarly).
3. **Step 2**, the backfill, never runs.

The rollback script would then drop the column. The database ends up back where it started, but the release has failed. The order is stated as a strict requirement, so the plan cannot succeed as written.

**Fix:** run the steps in the order **1 → 2 → 3**: add the nullable column, backfill it, then enforce `NOT NULL`.

## Other recommendations (after reordering)

- **Verify before constraining.** Between Step 2 and Step 3, run `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL`. The plan says every order has a shipments row with a non-null `shipped_at`. Confirm that with a check rather than relying on it. Orphaned orders, or multiple shipments per order, would break or skew the backfill.
- **Define the join for multiple shipments.** If an order can have more than one shipment, state which value wins, such as `MIN(shipped_at)` or `MAX(shipped_at)`. Otherwise the result is nondeterministic, or the update errors out.
- **Batch the backfill.** A single `UPDATE` across 2M rows creates one large transaction, with heavy WAL/redo, lock, and bloat cost. Batching by primary key range is safer and easier to resume, even inside a maintenance window.
- **Handle concurrent writes.** Make sure nothing inserts into `orders` between the backfill and the constraint, or rows inserted in that gap will be NULL. The maintenance window probably covers this, but state it explicitly, for example by stopping writers or the application.
- **Consider whether NOT NULL is correct for all orders.** Every current order has shipped, but future orders will be created before they ship. A `NOT NULL` `shipped_at` would block inserting new unshipped orders unless the application always sets it. Confirm this matches the domain model.
- **Rollback details.** Make the rollback idempotent (`DROP COLUMN IF EXISTS`) and confirm it is safe to run at any point, including after a partial batched backfill.
- **Rehearse.** Run the full sequence on a production-sized copy to measure duration against the maintenance window.
