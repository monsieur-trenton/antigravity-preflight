# Review: Migrating `shipped_at` onto `orders`

## Will the plan work as written?

Yes, if the stated premise holds. Every order has a non-null `shipped_at` in `shipments`. So after Step 2, no row in `orders` has a null `shipped_at`, and the NOT NULL constraint in Step 3 succeeds. The order of the steps is correct: add the column as nullable, backfill it, then constrain it. The rollback is also safe at any point, because dropping a newly added column loses no existing data.

## Recommended changes

1. **Specify which shipment wins when an order has several.** The plan says every order has a shipped date, not that each order has exactly one shipment. If an order has split or re-sent shipments, an `UPDATE … FROM` / join-update picks an arbitrary matching row in PostgreSQL and MySQL. Define the rule explicitly, for example `MIN(shipped_at)` grouped by `order_id`.

2. **Verify the premise before Step 3.** Run `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL` after the backfill, or an anti-join against `shipments` beforehand. Then you find a bad assumption from a clear check, not from a failed constraint partway through the window.

3. **Block writes between Step 2 and Step 3.** Any order inserted after the backfill will have a null `shipped_at` and will make Step 3 fail. Since this runs in a maintenance window, state that the application is stopped or the table is write-locked for the whole migration.

4. **Batch the backfill.** A single `UPDATE` across 2 million rows creates one large transaction. That means heavy WAL or binlog volume, possible replica lag, long-held row locks, and table bloat in PostgreSQL. Updating in key-range batches of roughly 10k to 50k rows is safer and lets you track progress. Also note that adding NOT NULL scans the full table under an exclusive lock. In PostgreSQL you can shorten that by first adding `CHECK (shipped_at IS NOT NULL) NOT VALID`, then running `VALIDATE`, then `SET NOT NULL`.

5. **Make each step idempotent or transactional.** If your database supports transactional DDL, as PostgreSQL does, you can wrap the whole migration in one transaction and let a failure roll back automatically. Otherwise, make sure the rollback script works from any partial state, for example with `DROP COLUMN IF EXISTS`.

6. **Check the application's behavior for orders that haven't shipped.** NOT NULL on `shipped_at` means an order can't exist until it has a shipped date. If the application ever creates orders before shipping them, inserts will fail once the migration finishes. Confirm that the constraint matches the business model and that all write paths fill in the column.

## Summary

The plan is sound and should succeed as written. The changes above make it robust against ambiguous joins, concurrent writes, and the cost of a large single-transaction update.
