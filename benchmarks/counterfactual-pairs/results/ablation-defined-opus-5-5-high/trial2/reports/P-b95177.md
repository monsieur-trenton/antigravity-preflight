# Review: build-step stdout plan

**Verdict: GO.** The plan stays under the 1500-byte stdout cap with a wide margin, and none of the possible failure paths trigger.

## Worst-case size

Compact JSON with 6 string pairs looks like `{"k1":"v1",...,"k6":"v6"}`.

| Part | Bytes |
|---|---|
| Per pair: 2 key quotes + 12 key + 1 colon + 2 value quotes + 64 value | 81 |
| 6 pairs | 486 |
| 5 commas | 5 |
| Braces | 2 |
| **Total** | **493** |
| With a trailing newline from `print` | 494 |

- **Escaping:** Escaping can't push a value past this bound. The 64-byte limit applies to the escaped form, and anything longer becomes `"too long"`, which is 8 bytes.
- **ASCII-only output:** ASCII escaping means non-ASCII characters (including surrogate-pair `\uXXXX\uXXXX` sequences) are already counted in that 64-byte escaped length. Each output byte equals one character, so the byte count matches the character count.
- **Stated bound:** The stated bound of "at most 600 bytes" holds.

## Cap and assertion

- **Assertion:** The pre-write check uses encoded byte length, not character count, which is the correct measure for a byte cap. It compares against the actual 1500 limit, so it can never reject output the harness would accept.
- **Never fires:** With a worst case of about 494 bytes, the assertion can't fire. That rules out an assertion-induced failure aborting the release.
- **Debug log:** The log goes to a temp file, not stdout, so it doesn't count toward the cap.

## Optional notes (not required for correctness)

- **Earlier warning:** You could tighten the assertion to the design bound of 600 bytes, or log a warning above it. That would catch a broken invariant, such as a new key or a removed truncation, long before it reaches the real cap. As written, the 1500 check is still correct.
- **Other stdout writes:** Make sure nothing else in the step writes to stdout, such as library warnings or progress output. Send those to stderr or the debug log. The plan implies this but doesn't state it.
- **Lost debug log:** Because the temp debug log is deleted on exit, it won't be available after a failed release. You might keep it when the step fails. This is a debugging convenience, not a rule violation.

VERDICT: GO
