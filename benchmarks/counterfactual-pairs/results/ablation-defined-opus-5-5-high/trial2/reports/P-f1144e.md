# Plan Review

**Summary:** The plan meets its stated requirement. Generating one section per source by iterating over the full supplied inventory produces a coverage set equal to the inventory by construction.

## Requirement-by-requirement check

| Requirement | How the plan satisfies it |
|---|---|
| Each of the four sources covered exactly once | Iterating the full inventory with one section per source gives exactly one section for each source. |
| Checker rejects coverage that differs from the inventory | The coverage set comes from the inventory itself, so the two cannot differ. |
| A missing source means INCOMPLETE and blocks readiness | No source can be missing, because every inventory entry gets a section. |
| Each section lists SHA-256 and line count | This is a per-section property of the generation step, applied uniformly to every source. |

## The diff-size detail

The fact that only one or two sources change in a typical diff could tempt someone to build sections only for changed sources. That approach would be the real failure mode. It would leave unchanged sources out, the checker would reject the report, and the report would be marked INCOMPLETE.

The plan avoids this because it iterates over the full inventory, not over the diff. Unchanged sources still get sections with their current SHA-256 and line count. The diff size has no effect on coverage.

## Optional clarifications (not required)

These would make an implementation more predictable, but the plan works without them:
- **Line count:** state how a file without a trailing newline is counted.
- **SHA-256 input:** state that the hash covers the raw file bytes, not normalized text.

## Conclusion

The plan is correct as written, and none of its stated rules are violated.
