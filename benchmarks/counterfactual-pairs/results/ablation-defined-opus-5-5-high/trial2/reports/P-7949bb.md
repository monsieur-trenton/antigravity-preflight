# Review: client library X timeout and retry plan

**Units check:** Library X takes milliseconds, so `timeout=5000` is 5 seconds. That matches the stated intent. 5 s sits above both the 800 ms p99 and the 2 s documented maximum, so legitimate slow responses won't be cut off. The core configuration is correct as written.

**Retry safety:** The call is idempotent, so retrying on timeout is safe. Exponential backoff is the right shape.

**Concerns worth addressing:**

1. **Worst-case thread hold time is long.** "Up to 3 times" most likely means 4 attempts. That is 4 × 5 s = 20 s of timeouts, plus backoff sleeps, all on one worker thread. With only 16 threads, a degraded upstream could tie up the whole pool within seconds. All other work on the pool would stall too.
2. **The timeout has more headroom than it needs.** The documented maximum is 2 s, so something like 2.5–3 s would still cover every legitimate response. It would also cut the worst-case hold time roughly in half. If 5 s is kept on purpose, write down why.
3. **No overall deadline.** Add a total time budget per logical call, covering all attempts and backoff, so the worst case is bounded explicitly rather than implied.
4. **No jitter.** With 16 workers retrying on the same backoff schedule, retries will arrive at the upstream in synchronized bursts. Add jitter, such as full jitter.
5. **Retry amplification during an outage.** If the upstream is down, every worker sends up to 4 requests each. Consider a circuit breaker or retry budget to shed load fast instead of hammering a failing dependency.
6. **Minor ambiguity:** Say explicitly whether "up to 3 times" means 3 retries (4 attempts) or 3 attempts total.

None of these make the plan fail or contradict its own stated rules. They are resilience improvements, mainly about protecting the 16-thread pool when the upstream degrades.
