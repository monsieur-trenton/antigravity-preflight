## Review

The plan will fail on input already seen in testing.

**Blocking problem:** The summary size is dominated by its values, and nothing bounds them. The tested case had three values of roughly 700 bytes each — about 2100 bytes of values alone, before keys or JSON punctuation. That exceeds the 1500-byte cap.

**The pre-write assertion does not save the plan.** It only moves where the failure occurs. When the encoded length exceeds 1500, the assertion trips and the step fails — and per the stated contract, a failed step aborts the release with no retry. Either way the release breaks. The assertion is a detector, not a fix.

**ASCII escaping can only worsen this**, since escaped characters expand (e.g. to `\uXXXX`), so encoded length is often larger than the raw value length.

**What's fine:** The keys are safely bounded (6 keys, ≤12 bytes each, plus JSON overhead — a small, fixed cost). The debug log is correctly outside the cap, so it poses no risk.

**To make this work**, the plan needs a value-size strategy that keeps the *encoded* total under 1500, for example: truncating values to a computed per-value budget, omitting or offloading large values to the debug log and referencing them, or compressing/eliding. The assertion should then remain as a backstop, not the primary control.
