# Review: Nightly Compaction Plan

The plan works as written. I'd still make a few small improvements.

## The timing holds up

- 40 GB at 55 MB/s is about 727 s (decimal units) or about 745 s (binary units). Either way that is roughly **12 minutes**, so the stated figure is correct.
- 12 minutes in a 30-minute window is about **2.5× headroom**. That is comfortable for a single-threaded job.
- Logging every minute gives about 12 progress lines on a normal run and at most 30 on a cancelled one. That is enough to tell a slow run from a stalled one.
- Cancellation is defined and reported, so a timeout won't fail silently.

## Suggested changes

1. **Define what happens after cancellation.** The plan says the cancellation is reported, but not what state it leaves. Say whether a partial compaction is rolled back, discarded or resumable. Also say whether the original input stays valid. This matters most if the next night's run starts from an unclean state.
2. **Track input growth against the window.** The margin depends on the input staying near 40 GB. If the data grows, at 55 MB/s the window is used up at about 99 GB. Add an alert well before that point, for example when the projected duration passes about 20 minutes. That warns you before cancellations start.
3. **Confirm the throughput under nightly conditions.** The 55 MB/s comes from a single measurement. Check that it was taken with the same I/O contention as the real nightly slot, such as backups or other batch jobs. If it wasn't, re-measure once or a few times.
4. **Optional: log a rate and an ETA.** Each per-minute line could include bytes processed and the current MB/s. Then a slowdown is visible early, not only when the step is cancelled.

None of these block the plan. The timing works and the failure mode is handled.

VERDICT: GO_WITH_CHANGES
