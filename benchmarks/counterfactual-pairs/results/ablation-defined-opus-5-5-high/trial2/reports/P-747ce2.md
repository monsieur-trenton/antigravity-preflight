# Review: orders.shipped_at migration

## Does the plan work as written?

Yes, given its stated premise. The order is correct: add the column as nullable, backfill it, then constrain it. The plan says `shipments` has a non-null `shipped_at` for every order. If that holds, every row is populated before Step 3, and the NOT NULL constraint succeeds. Running in a maintenance window means no new rows arrive between Step 2 and Step 3. Nothing in the plan fails or breaks one of its own rules.

## Recommended changes

1. **Check the premise before Step 3.** The whole plan depends on "every order has a shipment with a non-null `shipped_at`." Add a gate between Step 2 and Step 3, such as `SELECT count(*) FROM orders WHERE shipped_at IS NULL`, and abort if the result isn't zero. Orphaned, cancelled or test orders are common exceptions to rules like this.

2. **Define how multiple shipments per order are handled.** If an order can have more than one shipment row, `UPDATE ... FROM shipments` picks an arbitrary match. Choose one rule explicitly, for example `MIN(shipped_at)` for the first shipment or `MAX` for the last, and backfill from that.

3. **Check what the application does after the release.** With `shipped_at NOT NULL`, any code that inserts an order before it ships will fail. Confirm that the application always supplies `shipped_at` at insert time. If it can't, the constraint may be the wrong model for orders that haven't shipped yet.

4. **Make the rollback idempotent.** If Step 1 fails, the column may not exist, and a plain `DROP COLUMN` would error. Use `DROP COLUMN IF EXISTS`. If the database supports transactional DDL (e.g., PostgreSQL), consider running all three steps in one transaction so a failure rolls back automatically.

5. **Plan for the size of the backfill.** Updating 2M rows in one statement holds row locks, produces a lot of WAL or redo log, and leaves bloat behind. That is probably acceptable in a maintenance window, but:
   - time it on a production-sized copy first;
   - consider batching the update;
   - run `VACUUM` or `ANALYZE` afterward;
   - make sure `shipments` has an index on the order foreign key.

6. **Watch the lock taken by Step 3.** Adding NOT NULL scans the whole table under an exclusive lock. In PostgreSQL 12+, you can shorten this: add `CHECK (shipped_at IS NOT NULL) NOT VALID`, run `VALIDATE`, then `SET NOT NULL`. In a maintenance window this is optional.

## Summary

The plan works if its data premise is true. The main gaps are not verifying that premise, the ambiguity when an order has several shipments, the post-release insert behavior, and a rollback that could itself fail. All of these are improvements, not blockers.
