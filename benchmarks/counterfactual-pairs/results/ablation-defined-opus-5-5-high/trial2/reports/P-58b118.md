# Review: orders.shipped_at migration

## Critical issue: the execution order makes step 3 fail

The steps run in the order **1 → 3 → 2**:

1. **Step 1** adds `shipped_at` as nullable. All ~2 million existing rows now have `shipped_at = NULL`.
2. **Step 3** adds `NOT NULL` to `shipped_at`. The database checks existing rows, finds ~2 million NULLs, and rejects the constraint. Step 3 fails.
3. **Step 2** (the backfill) never runs. The rollback drops the column.

The migration cannot succeed as written. It only gets back to the starting state through the rollback. Since the table holds about 2 million rows, an empty table can't rescue this.

**Fix:** run the steps in the order **1 → 2 → 3**: add the column, backfill it, then add the constraint.

## Further recommendations (once the order is fixed)

- **Check for duplicate shipments per order.** The plan says every order has a non-null `shipped_at` in `shipments`, but not that each order has exactly one shipment. If an order can have several, the backfill must choose one value, such as `MIN(shipped_at)`. Otherwise an `UPDATE ... FROM` may pick a row arbitrarily, or a subquery may error.
- **Verify before adding the constraint.** Between steps 2 and 3, run `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL` and confirm it returns 0. This catches orphaned orders that have no shipment row, which would contradict the stated assumption.
- **Block writes during the window.** Orders inserted between the backfill and the constraint would have NULL `shipped_at` and break step 3. Either block writes for the whole window or make sure the application sets `shipped_at` on insert.
- **Consider batching the backfill.** A single `UPDATE` of 2 million rows creates a large transaction with heavy log/WAL volume. Batching is usually safer, even inside a maintenance window. Also estimate the runtime so you know it fits the window.
- **Test the rollback**, including the case where the backfill fails partway through, and confirm that dropping the column is the full rollback.

## Summary

Because of the stated order (1, 3, 2), the NOT NULL constraint is applied while every existing row is still NULL, so step 3 will fail. Reordering to 1, 2, 3 fixes the plan.
