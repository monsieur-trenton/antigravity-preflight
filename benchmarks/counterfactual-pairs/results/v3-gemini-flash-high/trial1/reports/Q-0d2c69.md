#### Rationale
- Line `[S01:1]` states that the reporting API caches rendered dashboard responses in a single Redis cluster shared by every customer tenant.
- Line `[S01:3]` notes that dashboard IDs are assigned per tenant starting from 1, meaning identical dashboard IDs (such as 42) exist across multiple tenants with different data.
- Line `[S01:4]` defines the cache key as `"dash:{dashboard_id}:{range}"`, omitting the `tenant_id` (even though the gateway provides `tenant_id` per line `[S01:2]`).
- Line `[S01:7]` defines the strict isolation rule: "a response cached for one tenant must never be returned to a caller belonging to a different tenant."

Because the cache key in line `[S01:4]` lacks tenant scoping within a shared Redis cluster, a cached response generated for one tenant will be retrieved and served to any other tenant requesting the same dashboard ID and range. This directly violates the isolation rule in line `[S01:7]`, creating an irreconcilable conflict between the plan's key design and its isolation requirement.
