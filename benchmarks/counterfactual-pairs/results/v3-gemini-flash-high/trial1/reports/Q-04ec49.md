### Advisory Review Rationale

**Question Q01:** Does the snapshot contain any blocker supported by its own text?  
**Answer:** Yes. Snapshot S01 contains a verified blocker arising from a direct contradiction between its cache key specification and its tenant isolation requirements.

#### Analysis of Findings:
1. **Shared Cache Infrastructure & ID Collisions:** Line [S01:1] specifies that rendered dashboard responses are cached in a single Redis cluster shared jointly by all customer tenants. Line [S01:3] confirms that dashboard ID numbering restarts at 1 for each tenant, meaning identical dashboard IDs (e.g., ID 42) represent different data across different tenants.
2. **Missing Tenant Namespace in Cache Key:** Line [S01:4] specifies the cache key schema as `"dash:{dashboard_id}:{range}"` and explicitly restricts the handler from touching any key other than the one derived from the request. Although line [S01:2] notes that the gateway stamps requests with `tenant_id`, line [S01:4] fails to incorporate `tenant_id` into the cache key.
3. **Violation of the Isolation Rule:** Because `tenant_id` is omitted from the cache key, requests from different tenants requesting the same dashboard ID will map to identical Redis keys in the shared cluster. This causes one tenant to read dashboard responses cached by another tenant, directly violating the mandatory isolation rule in line [S01:7] ("Isolation rule: no tenant's caller may ever receive a response that was cached for another tenant.").

Because this design directly causes cross-tenant data leakage and violates the isolation requirement, it constitutes a critical architectural blocker.
