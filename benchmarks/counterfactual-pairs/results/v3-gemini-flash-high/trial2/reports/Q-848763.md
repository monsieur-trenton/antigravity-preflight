# Plan Review: Snapshot S01

### Review and Advisory Analysis

**Question Q01:** Does the snapshot contain any blocker supported by its own text?

**Answer:** Yes. Snapshot S01 contains a verified blocker supported directly by its text.

### Rationale

The plan contains a fatal lock-ordering conflict between concurrent operations that guarantees a circular-wait deadlock:

1. **Lock Order Inversion:** Line `[S01:2]` specifies that checkout acquires `stock_mu` first and then acquires `reserve_mu` without releasing `stock_mu`. Conversely, line `[S01:3]` specifies that restock acquires `reserve_mu` first and then acquires `stock_mu` without releasing `reserve_mu`.
2. **Indefinite Blocking:** Line `[S01:1]` states that acquiring either mutex blocks indefinitely with no timeout mechanism.
3. **High Concurrency:** Line `[S01:4]` establishes that checkouts arrive continuously while restocks execute every 30 seconds, frequently running simultaneously on separate threads.
4. **Requirement Violation:** Line `[S01:7]` explicitly establishes that deadlock is never acceptable because a hung pod will continue to pass liveness checks while failing to process sales until an operator performs a manual restart.

Because the lock acquisition orders in lines `[S01:2]` and `[S01:3]` are inverted across concurrently executing threads with indefinite blocking, circular wait is inevitable. This directly violates the strict requirement in line `[S01:7]`, making line `[S01:3]` a critical blocker.
