# Review

## Blocking: the timeout is 5 ms, not 5 seconds

Client library X takes its timeout in **milliseconds**, so `timeout=5` means **5 ms**. The intent was 5 seconds. With the upstream at p99 = 800 ms, essentially every call will time out.

The retry policy makes this worse:

- **100% failure rate.** Each call makes 4 attempts (1 + 3 retries), and all of them time out. Callers only see failures, after a delay from backoff.
- **Load amplification on the upstream.** A client-side timeout usually doesn't cancel server-side work. The upstream still processes each abandoned request, so it receives about 4× the intended traffic and none of the results are used. If the service is already degraded, this can push it into a retry storm.
- **Misleading signals.** Dashboards will show timeouts. That looks like an upstream latency problem, not a config bug, and could send debugging in the wrong direction.

**Fix:** use `timeout=5000`. Better still, use a named constant or a unit-explicit form if the library supports it (e.g., `timeout_ms=5000` or a duration type), so the bug can't come back. Add a test or startup assertion that the configured timeout is above the upstream's documented maximum.

## Recommended (non-blocking)

1. **Tighten the timeout value.** 5 s is 2.5× the documented 2 s maximum. That's safe, but each hung attempt holds a worker thread for 5 s. Something like 2.5–3 s still covers the documented maximum while freeing threads sooner.
2. **Bound total latency.** Worst case is 4 × 5 s plus backoff, so more than 20 s per call. Set an overall deadline across all attempts so callers get a predictable upper bound.
3. **Thread-pool exhaustion.** With 16 threads and up to about 20 s per call during an upstream incident, the pool saturates quickly. Make sure queued work has a bound and a clear rejection policy rather than an unbounded queue.
4. **Add jitter to the backoff.** 16 threads retrying on the same exponential schedule will synchronize. Full or decorrelated jitter avoids this.
5. **Retry budget / circuit breaker.** Cap retries as a fraction of total traffic (e.g., ≤10%), or trip a breaker when the timeout rate spikes. This keeps the retry policy from amplifying an upstream outage.
6. **Retry only on retryable errors.** Timeouts and 5xx/503 are reasonable to retry. 4xx and validation errors should not be retried. Idempotency is confirmed, which is good.

## Summary

The overall design is sound: an idempotent call, bounded retries, exponential backoff, and a timeout chosen with the upstream's documented maximum in mind. But the unit mismatch makes it fail 100% of the time and quadruples upstream load. It's a one-line fix, and it must be made before shipping, ideally along with a unit-explicit constant and the jitter and deadline improvements above.
