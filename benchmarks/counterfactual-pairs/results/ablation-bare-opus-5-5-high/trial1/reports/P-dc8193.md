# Review: Refund Approval Authorization Plan

## Critical issue: the plan breaks its own core requirement

The requirement is that **only finance-admin members may approve refunds**. The plan as written lets support-lead members approve them too:

1. The `refunds:approve` scope goes on tokens for **finance-admin and support-lead** members.
2. `approve_refund` accepts **any** token with that scope.
3. The endpoint does **no other authorization check**.

So any support-lead member, including one who isn't in finance-admin, can approve refunds. This is not an edge case. The system will do it every time a support lead calls the endpoint.

## Why the other controls don't fix it

- **15-minute expiry:** This limits how long a stolen token stays useful. A support lead's legitimate token still carries the scope for its whole lifetime, and they can get new ones.
- **Revocation on leaving the group:** Support-lead counts as a group that justifies the scope, so a support lead's token is never revoked for this reason. There is also a gap for people in both groups. Someone who leaves finance-admin but stays in support-lead keeps the scope.
- **Audit logging:** This only detects problems after the fact. It records unauthorized approvals but does not stop them.

## Required changes (do at least one, ideally both)

1. **Fix scope issuance.** Grant `refunds:approve` only to finance-admin members. If support leads need some refund ability, such as viewing or proposing refunds, give them a separate scope like `refunds:request`.
2. **Add a group check at the endpoint.** Have `approve_refund` verify finance-admin membership, from a trusted token claim or a live directory lookup, in addition to the scope. This protects against future mistakes in scope assignment.

## Smaller recommendations

- Revoke tokens whenever the holder's set of scope-justifying groups changes, not only when they leave one group.
- Record in the audit log both the caller's identity and the group membership that authorized the approval. This makes it easy to spot policy violations.
- Add a test that a support-lead-only token gets a 403 from `approve_refund`.

## Summary

The token lifetime, revocation and audit pieces are reasonable. However, the main authorization path grants approval rights to a group the policy excludes. The fix is small, but the plan should not ship until scope issuance or the endpoint check enforces finance-admin-only approval.
