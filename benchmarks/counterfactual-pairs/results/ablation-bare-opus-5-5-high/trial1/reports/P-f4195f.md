# Review: Nightly Batch Plan

## Timing

| Stage | Typical | Observed max (30 runs) |
|---|---|---|
| 1. Import | 22 min | 25 min |
| 2. Transform | 18 min | 21 min |
| 3. Export | 12 min | 14 min |
| **Total** | **52 min** | **60 min** |

The stages run in sequence, so the totals simply add. The worst observed run is 60 minutes against a 75-minute limit. That leaves 15 minutes of headroom (20%). Even if every stage hit its worst case on the same night, the batch would still finish in time. On timing alone, the plan is sound.

## Concerns

**1. The 15-minute margin is smaller than it looks.**
- Thirty runs is a short history. It probably missed month-end or quarter-end volumes, holiday backlogs, and nights when upstream data arrives late.
- The stage timings may not include startup, scheduling delay, or handoff time between stages. Real wall-clock time could be a few minutes longer.
- Data volumes usually grow. If import time grows about 1–2% a month, the margin shrinks noticeably within a year.

**2. A single failure can't be recovered within the window.**
If a stage fails partway and has to restart, the batch overruns. For example, if import fails at minute 20, the rerun alone pushes the total to about 80 minutes. The plan has no retry budget.

**3. The failure mode is total data loss, with no checkpointing.**
A kill at minute 75 discards the whole day, even if import and transform already finished. Since the consequence is lost data, this matters more than the timing does.

**4. Alerting only covers success.**
The summary email goes out "when the batch ends." If the batch is killed at the deadline, it never reaches the end, so the email may never be sent. The worst outcome, an overrun with lost data, could therefore be the one that generates no alert at all.

## Recommended changes

1. **Add a watchdog independent of the batch.** It should page on-call if no completion signal arrives by about minute 75, and also if the batch is killed. Don't depend on the batch to report its own death.
2. **Add early-warning thresholds.** For example, alert if import is still running at minute 30, or if total elapsed time passes 65 minutes. This gives on-call time to step in before the kill.
3. **Persist each stage's output.** After a kill, the next attempt could then resume from the last completed stage instead of losing the whole day.
4. **Track duration trends.** Log per-stage times over time and alert if the 95th-percentile total approaches about 65 minutes. That catches growth before it becomes an outage.
5. **Write down a recovery runbook.** It should say what on-call does when a run is lost: backfill, rerun the next day, or something else.

## Summary

The timing works with reasonable headroom. However, the plan has no defence against its own stated failure mode. An overrun silently loses a day's data, and the one alert in the plan likely doesn't fire in that case. Adding an external watchdog and stage checkpointing would make this solid.
