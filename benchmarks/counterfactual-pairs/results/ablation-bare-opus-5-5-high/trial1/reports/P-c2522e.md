# Review: Orders Table Migration Plan

## Blocking issue: the execution order is wrong

The plan runs **step 1 → step 3 → step 2**, which adds the NOT NULL constraint before the backfill.

- After step 1, `shipped_at` is NULL for all ~2 million existing rows.
- Step 3 then tries to enforce NOT NULL. In PostgreSQL, `ALTER COLUMN ... SET NOT NULL` scans the table and fails if any row is NULL. MySQL behaves similarly.
- **Step 3 will fail every time**, the rollback will drop the column, and the release will accomplish nothing. No data is lost, but the maintenance window is wasted.

**Required change:** run the steps as **1 → 2 → 3**: add the nullable column, backfill it, then add the constraint.

## Other things to address

1. **Verify the backfill assumption before the window.** The plan says every order has a shipment with a non-null `shipped_at`. Confirm this with queries:
   - Orders with no matching shipment: `SELECT count(*) FROM orders o LEFT JOIN shipments s ON s.order_id = o.id WHERE s.order_id IS NULL;`
   - Shipments with NULL `shipped_at`.
   
   If either count is non-zero, step 3 will still fail.

2. **One-to-many shipments.** If an order can have multiple shipments (for example, split shipments), the backfill must choose one deterministically, such as `MIN(shipped_at)`. Otherwise the result is arbitrary, or the UPDATE errors out.

3. **Writes after the window.** Once NOT NULL is in place, every insert into `orders` must supply `shipped_at`. Confirm two things:
   - The application code that does this is deployed before or alongside the constraint.
   - It makes sense for the business. Orders are usually created *before* they ship, so a NOT NULL `shipped_at` may be semantically wrong for new orders even if it's true for historical ones. If unshipped orders can exist, the constraint should not be added.

4. **Backfill performance.** Updating 2M rows in a single statement is usually fine in a maintenance window. Still, expect table bloat or a large WAL/binlog, and consider batching or running `VACUUM`/`ANALYZE` afterward. Rehearse it on a production-sized copy to confirm it fits the window.

5. **Rollback.** Dropping the column is a reasonable rollback for a brand-new column. Test it, and note what happens if the failure comes after app code that depends on the column has been deployed.

## Summary

The design is sound once the order is fixed to 1 → 2 → 3. As written, it cannot succeed. Fix the ordering, run the data-validation queries, settle how multiple shipments are handled, and make sure new-order writes are compatible with NOT NULL.
