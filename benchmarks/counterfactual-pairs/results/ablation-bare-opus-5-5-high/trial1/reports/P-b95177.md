## Review

**The byte budget holds, with large margin.** Worst case for the compact JSON:

- Per pair: `"` + 12-byte key + `"` + `:` + `"` + 64-byte value + `"` = 81 bytes
- Six pairs: 486 bytes
- Five commas and two braces: 7 bytes
- Total: **493 bytes**, or 494 with a trailing newline

So the "at most 600 bytes" claim is correct. Even if the 64-byte limit excludes the escaping overhead, the result is still far below the 1500-byte cap. Because values are ASCII-escaped, character count equals byte count, so there is no multibyte surprise. `"too long"` is 8 bytes, well within the limit.

**Assertion.** Checking the *encoded byte length* before writing is the right choice. It is a real backstop, not a character-count proxy. If it ever trips, the step fails before it writes, which is cleaner than overflowing mid-write.

**Debug log.** Writing it to a temp file keeps it out of stdout, so it doesn't affect the cap. Deleting it on exit doesn't matter for correctness here.

**Minor hardening (optional, not blocking):**
1. **Other stdout writers.** The cap covers *everything* the command prints, not just the summary. Make sure no logger, library warning, or child process inherits stdout. Send those to stderr or the debug log. This is the only realistic way to exceed 1500 bytes.
2. **Trailing newline.** Run the assertion on exactly the bytes written, newline included. Given the margin this is cosmetic.
3. **Fixed keys.** Since the keys are fixed, a unit test asserting the 493-byte worst case would keep the bound from drifting if someone later adds a key or raises the 64-byte limit.

The design is sound, and the cap cannot be reached by the summary itself.
