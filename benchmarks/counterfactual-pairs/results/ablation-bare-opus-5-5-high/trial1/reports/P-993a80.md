# Review: Refund Approval Authorization Plan

The plan is sound in principle. If every premise holds, only finance-admin members can approve refunds. The weakness is that the endpoint delegates all authorization to the token. Correctness therefore depends on things the plan states but doesn't show how it enforces.

## What works

- **Authorization chain:** scope is issued only to finance-admin, and the endpoint requires that scope. So approvers are finance-admin members at issuance time.
- **Short token lifetime:** a 15-minute expiry limits exposure from leaked or stale tokens.
- **Revocation on leaving the group:** this addresses the gap between issuance and use.
- **Audit logging:** every approval records the caller's identity, so actions are attributable.

## Concerns

1. **Is revocation enforced at the endpoint?** This is the biggest gap. Revoking a token only helps if the endpoint checks revocation status. If tokens are self-contained (e.g., JWTs validated by signature and expiry alone), a revoked token still works until it expires. A member removed from finance-admin could keep approving refunds for up to 15 minutes, which breaks the "only members" rule. The plan should say how revocation reaches the endpoint, for example token introspection or a denylist check on each request.

2. **Are there other ways to get the scope?** The rule "only issued to finance-admin members" must hold on every issuance path, not just the main login flow. Paths to check:
   - token exchange or delegation
   - refresh tokens (is group membership rechecked on refresh?)
   - client-credentials or service accounts
   - admin or test tooling
   - other trusted issuers or audiences the endpoint accepts

   Any path that skips the group check bypasses the whole control.

3. **No defense in depth.** The endpoint makes no other authorization check, so one misconfiguration in the token issuer grants refund authority. A cheap server-side check of current finance-admin membership at approval time would:
   - close the revocation-propagation gap
   - guard against issuer mistakes

4. **Token validation details.** Confirm the endpoint checks issuer, audience, signature, and expiry. Otherwise a token minted for another service with the same scope name might be accepted.

5. **Audit log completeness.**
   - Record the token ID and the caller's group membership at decision time, not just the caller's identity.
   - Make the log tamper-resistant. Finance-admin members shouldn't be able to edit it.
   - Log denied attempts as well as approvals.

6. **Out of scope but worth noting:** the plan doesn't say who controls finance-admin membership. Whoever can add members can effectively approve refunds, so that process needs its own controls and audit trail.

## Recommended changes

- Enforce revocation at the endpoint through introspection or a revocation check, or add a live group-membership check.
- Inventory every token issuance path and confirm each one enforces the finance-admin check, including on refresh.
- Fully validate tokens (issuer, audience, signature, expiry).
- Extend the audit log as described in point 5.

VERDICT: GO_WITH_CHANGES
