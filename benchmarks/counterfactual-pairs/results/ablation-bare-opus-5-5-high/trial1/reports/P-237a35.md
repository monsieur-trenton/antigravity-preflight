# Plan Review

## Critical defect: the plan iterates over the wrong set

The requirement is that the report cover **all four supplied sources, exactly once**, and the checker rejects any report whose coverage set differs from the inventory. The plan builds sections only from **sources that changed in the diff**.

You say a typical diff changes only one or two of the four sources. So in the typical case:

- The report covers 1–2 sources instead of 4.
- The coverage set differs from the inventory, so the checker rejects it.
- The report is marked INCOMPLETE and is never recommended for readiness.

As written, the plan fails in its normal operating mode. It produces a passing report only in the rare case where all four sources change.

## Required changes

1. **Iterate over the supplied inventory, not the diff.** Emit one section per inventory source, in a stable order. Use the diff only to annotate each section, for example "changed in this diff" or "unchanged."
2. **Compute SHA-256 and line count from each source's full current content, not from diff hunks.** Unchanged sources have no hunks but still need both values.
3. **Enforce "exactly once."** If a source appears in several diff entries (several hunks, renames, or path aliases such as `./a` vs `a`), normalize paths and deduplicate. Otherwise it may get duplicate sections.
4. **Exclude non-inventory files.** If the diff touches files outside the four sources, they must not get sections. Extra entries also make the coverage set differ and cause rejection.
5. **Handle edge cases explicitly:**
   - A source deleted or unreadable in the current state: define what its section reports, or fail loudly before emitting.
   - A renamed source: map it back to its inventory identity.
6. **Add a pre-submit self-check.** Before emitting, assert that the set of section sources equals the inventory set and that each appears once. This catches regressions before the checker does.

## What's fine

- One section per source is the right structure.
- SHA-256 plus line count per section is reasonable, as long as both come from full file content (change 2).

## Summary

The structure is sound, but the iteration source is wrong, and that guarantees rejection in the common case. The fix is contained: drive the report from the inventory and use the diff only as metadata. With changes 1–4 and the self-check, the plan should satisfy the checker.
