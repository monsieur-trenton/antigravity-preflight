# Review: adding `orders.shipped_at` as NOT NULL

The three-step structure (add nullable, backfill, then constrain) is the right pattern. Several gaps need closing before it runs.

## Must address

**1. New writes after Step 3 (the biggest risk).**
- Once `shipped_at` is NOT NULL, every `INSERT` into `orders` must supply it. If orders are normally created *before* they ship, the application breaks at the next checkout. Either confirm that orders are only inserted once shipped, or reconsider whether NOT NULL is the right rule.
- The application code that writes `shipped_at` must be deployed before or together with Step 3. Rolling it out afterward is too late.
- Something must keep the column in sync with `shipments` from now on: application logic, a trigger, or a documented rule that `orders` is the source of truth.

**2. Verify the backfill assumption instead of trusting it.** "Shipments holds a non-null shipped_at for every order" is exactly the kind of claim that turns out 99.98% true. Between Step 2 and Step 3, run a gate check:
```sql
SELECT count(*) FROM orders WHERE shipped_at IS NULL;  -- must be 0
```
If it isn't 0, abort before Step 3 and investigate, rather than letting the constraint fail mid-window.

**3. Multiple shipments per order.** If an order can have more than one shipment row (split or partial shipments, reships), an `UPDATE ... FROM shipments` join picks an arbitrary row. Decide which value is correct, probably `MIN(shipped_at)` or `MAX(shipped_at)`, and aggregate explicitly.

**4. Writes during the window.** Confirm that application writes to `orders` are actually stopped for the whole migration. Otherwise rows inserted after Step 2 will be NULL and Step 3 will fail.

## Should address

**5. Batch the backfill.** One `UPDATE` over 2M rows means one long transaction: heavy WAL/redo, table bloat (in Postgres), long row locks, and a painful rollback if it fails partway. Batch it by primary key range (e.g., 10–50k rows per batch). This also makes the step resumable.

**6. Cost of the constraint step.**
- Postgres: `SET NOT NULL` scans the full table under an ACCESS EXCLUSIVE lock. On PG12+, you can first add `CHECK (shipped_at IS NOT NULL) NOT VALID`, then `VALIDATE` it, then `SET NOT NULL`, which skips the scan.
- MySQL: the `ALTER` may rebuild the table.

Time all of this on a production-sized copy to confirm it fits the window.

**7. Rollback details.**
- In Postgres, consider wrapping the steps in a single transaction, since DDL is transactional there.
- In MySQL, DDL auto-commits, so the drop-column rollback is the real fallback. Make sure it is idempotent (`DROP COLUMN IF EXISTS`) and has been tested.
- Dropping the column is safe only if no deployed code reads it yet. Sequence the deploys so that a rollback cannot break the running application.
- Also define when a failure counts as a "failure." For example, if Step 3 succeeds but a later smoke test fails, do you still drop the column?

**8. Type consistency.** Match the column type to `shipments.shipped_at`, including timezone handling (`timestamptz` vs `timestamp`), so the backfill doesn't silently shift values.

## Summary

The approach is sound. The plan needs three things before it is safe to run: confirmation that NOT NULL fits how new orders are written, a verification gate before Step 3, and an explicit rule for orders with multiple shipments. Batching the backfill and rehearsing on a copy are strongly recommended.
