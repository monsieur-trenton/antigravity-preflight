# Review: Nightly Compaction Plan

## Timing check
The arithmetic holds. 40 GB at 55 MB/s is about 727 s (about 745 s if the units are GiB/MiB), so roughly 12 minutes. Against a 30-minute window that leaves about 2.5× headroom. The figure was measured on a production-class host, so it's a real number and not an estimate.

## What's solid
- **Hard bound on runtime.** Cancellation when the window expires means the step can't overrun into whatever comes next.
- **Cancellation is reported**, so failures are visible.
- **Single thread** is a reasonable choice. It's predictable and easy to reason about, and the measured rate already fits comfortably.
- **Per-minute progress logs** give enough detail to diagnose a slow run (where it stalled, rate over time) without being noisy.

## Changes I'd want before shipping
1. **Make cancellation safe.** The plan says what happens when the window runs out but not what state the data is left in. Compaction should write to a temporary output and swap it in atomically on success. On cancellation, partial output should be discarded and the original input left intact and readable. This is the main gap.
2. **Define what happens after a cancellation.** Does the next night retry from scratch? Does input that was never compacted pile up, making the next run larger and more likely to be cancelled again? A run that is cancelled twice in a row should probably page someone instead of only logging.
3. **Plan for growth and contention.** The 2.5× margin is based on one measurement at today's input size. Two cheap additions would cover this:
   - Log the input size and effective MB/s each night, and alert if the projected runtime goes above about 60–70% of the window, so you hear about it before cancellations start.
   - Check that other nightly jobs (backups, scans) don't compete for the same disk I/O during the window. If they do, the 55 MB/s may not hold.

None of these change the design. They close the gaps around failure and growth.

VERDICT: GO_WITH_CHANGES
