# Review: orders.shipped_at migration

The three-step sequence (add nullable, backfill, then constrain) is the right pattern. The plan depends on assumptions it doesn't verify, and one of them could break order creation after release.

## Blocking concerns

**1. NOT NULL may break new order inserts.**
The plan covers existing rows but not future writes. If orders are created before they ship, which is typical, every new order insert will fail after Step 3 unless one of these is true:
- the application always supplies `shipped_at` at insert time, or
- there is a default value, or
- orders are only ever created after shipment.

Confirm the write path. Also make sure the application code that populates `shipped_at` is deployed before or with Step 3. If unshipped orders are a valid state, the column should stay nullable.

**2. "Every order has a shipped_at in shipments" needs proof.**
The claim may be true for shipment rows that exist, but that is not the same as every order having a shipment row. Run a pre-check before Step 3 and abort if it returns anything:
```sql
SELECT count(*) FROM orders o
LEFT JOIN shipments s ON s.order_id = o.id
WHERE s.order_id IS NULL OR s.shipped_at IS NULL;
```
Also check that the backfill left no NULLs (`SELECT count(*) FROM orders WHERE shipped_at IS NULL`).

**3. Multiple shipments per order.**
If an order can have several shipment rows (split shipments, reships), the backfill is ambiguous or will fail on a scalar subquery. Define the rule explicitly, for example `MIN(shipped_at)` for first shipment or `MAX` for last.

## Recommended changes

- **Batch the backfill.** 2M rows in one `UPDATE` means a long transaction, heavy WAL/redo, and replication lag. Updating in chunks (say 10k–50k rows by primary key) is safer and lets you report progress.
- **Freeze writes during the window.** If anything can insert or modify orders between Steps 2 and 3, new NULLs can appear and Step 3 will fail. Confirm that writers are actually stopped, not just expected to be quiet.
- **Constraint cost.** On Postgres, `SET NOT NULL` scans the whole table under an ACCESS EXCLUSIVE lock. This is acceptable in a maintenance window, but time it on a production-sized copy. Alternatively, add `CHECK (shipped_at IS NOT NULL) NOT VALID`, run `VALIDATE`, and then set NOT NULL. On PG12+ the existing check lets it skip the scan.
- **Rollback details.**
  - State whether each step is transactional. If Step 2 is batched, a mid-backfill failure leaves partial data. Dropping the column handles that, but say so explicitly.
  - Coordinate the rollback with application code. If code that reads or writes `shipped_at` is already deployed, dropping the column breaks it. Roll back the code first, or keep the code tolerant of a missing column.
- **Rehearse.** Do a full dry run against a recent production snapshot to get real timings and catch data surprises.

## Summary

The sequencing is sound. Before this ships, the insert-path question in #1 must be answered and the data assumptions in #2 and #3 must be checked with an abort gate before Step 3. With those fixes, plus batching and a write freeze, the plan is reasonable.
