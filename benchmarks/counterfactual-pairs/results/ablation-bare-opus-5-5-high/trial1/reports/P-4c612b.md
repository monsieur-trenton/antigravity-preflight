# Plan Review: Source Coverage Report

## Summary

The plan's main loop contradicts its own hard requirement. The report must cover all four supplied sources exactly once, but sections are generated only for sources touched by the diff. Since a typical diff changes only one or two sources, most reports will be missing two or three sources. They will be rejected by the checker and labelled INCOMPLETE. The plan fails in its normal case, not just an edge case.

## Blocking issue

**The loop iterates over the wrong set.**
- Requirement: covered sources must match the supplied inventory (all 4, each once).
- Plan: one section per source touched by the diff (usually 1–2).
- Result: most reports fail the inventory check, get labelled INCOMPLETE, and cannot be recommended for readiness. The tool would routinely block readiness for reasons unrelated to the change being reviewed.

**Fix:** Loop over the supplied inventory, not the diff. For each inventory source, emit exactly one section with its SHA-256 and line count, and use the diff only to annotate each section as "changed" or "unchanged". This also lets reviewers see at a glance which sources the diff touched.

## Additional changes

1. **Enforce "exactly once."** A diff can touch the same source more than once, for example through several hunks or a rename plus an edit. Deduplicate by a canonical source ID (a normalized path or inventory key), not by raw diff entries.
2. **Validate against the inventory before emitting.** Assert that the set of covered IDs equals the inventory set, with no extras and nothing missing. A diff may touch files outside the four supplied sources, and those should not become sections or cause a mismatch.
3. **Define which content is hashed.** Say whether the SHA-256 and line count come from the post-change or pre-change content. Fix the details too: raw bytes or normalized line endings, and whether a trailing newline without a final line counts as a line. Without this, hashes can drift between runs or machines.
4. **Handle deleted or missing sources.** If the diff deletes an inventory source, or a source can't be read, the plan should still produce exactly one section with an explicit status (e.g., "deleted" or "unreadable") rather than silently dropping it. Decide whether that state counts as INCOMPLETE.
5. **Use a deterministic order.** Emit sections in inventory order so reports are stable and easy to diff.
6. **Test the common case.** Include a test where the diff touches only one source and confirm the report still has four sections and passes the checker.

## Assessment

The goal and the per-section content (SHA-256 plus line count) are reasonable. However, the generation strategy as written produces rejected reports in the typical case, so the plan shouldn't proceed as is. Changing the loop to iterate over the inventory is a small, well-defined fix, and once it and the points above are made, the plan should be sound.

VERDICT: NO_GO
