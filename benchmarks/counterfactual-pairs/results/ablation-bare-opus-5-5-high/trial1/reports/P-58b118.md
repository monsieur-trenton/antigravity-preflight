# Review: `orders.shipped_at` migration

The plan cannot run as written, because the constraint is applied before the data exists. The fix is simple, but it is mandatory.

## Blocking issue: the steps are in the wrong order

The plan runs step 1, then step 3, then step 2.

- After **step 1**, all ~2M existing rows have `shipped_at = NULL`.
- **Step 3** then adds `NOT NULL`. The database validates existing rows, finds 2M nulls, and the step fails. (In PostgreSQL, `SET NOT NULL` scans the table and errors on the first null. MySQL in strict mode also errors. Some engines or modes may instead coerce nulls to a zero or default value, which would be worse.)
- **Step 2**, the backfill, never runs. The rollback then drops the column.

As written, the migration will always fail and roll back. You would use up the maintenance window and gain nothing.

**Required change:** run the steps as 1 → 2 → 3 (add the column, backfill, then constrain).

## Other things to check before running

1. **Confirm the "every order has a shipment" claim with a query.** Run a pre-flight check like this:
   ```sql
   SELECT count(*) FROM orders o
   LEFT JOIN shipments s ON s.order_id = o.id
   WHERE s.shipped_at IS NULL;
   ```
   It must return 0. Any orphaned order will make step 3 fail.

2. **Handle orders with more than one shipment.** If an order can have several shipment rows, the backfill is ambiguous: an `UPDATE ... FROM` join may pick an arbitrary row. Decide on a rule, such as `MIN(shipped_at)` or `MAX(shipped_at)`, and aggregate explicitly.

3. **Check whether NOT NULL makes sense for future orders.** A column called `shipped_at` normally means "not shipped yet" when it is null. After step 3, every new order insert must supply a ship timestamp. Confirm that:
   - the application never creates an order before it ships, and
   - the insert code paths have been updated to set `shipped_at`, and are deployed before or together with this migration.

   If either is false, step 3 will break order creation in production, even if the migration itself succeeds.

4. **Stop writes during the window.** Make sure nothing inserts orders between step 2 and step 3. Otherwise new rows will have null values and step 3 will fail. Run the steps in a single transaction if your engine supports transactional DDL, or block writes during the window.

5. **Plan for the size of the backfill.** Updating 2M rows is manageable in a window, but it will rewrite rows and produce a lot of WAL/redo log. Either batch the update (for example, 10k–50k rows per batch by primary key) or do a test run on a production-sized copy to measure how long it takes. Also make sure `shipments.order_id` is indexed.

6. **Rollback.** Dropping the column is a fine rollback, since no other data is affected. Two things to confirm:
   - The rollback works correctly from every point of failure, including a partially completed batched backfill.
   - No application code that reads `shipped_at` has been deployed before the migration succeeds.

7. **Add a post-check.** After step 2 and before step 3, confirm that `SELECT count(*) FROM orders WHERE shipped_at IS NULL` returns 0.

## Summary

The overall approach (add a nullable column, backfill, then constrain) is correct. The step order is wrong, which guarantees failure. Reorder to 1 → 2 → 3, add the pre-flight and post-backfill checks, and confirm that NOT NULL fits how new orders are created. With those changes, the plan is sound.
