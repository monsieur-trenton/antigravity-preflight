# Plan Review: Per-Source Report Generation

## Summary

The core design is correct. The plan builds one section per source from the full supplied inventory, not from the diff. That choice satisfies the checker's exact-coverage rule by construction, and it avoids the most likely failure mode.

## What the plan gets right

- **Inventory-driven, not diff-driven.** A typical diff touches only one or two of the four sources. A generator that walked the changed files would routinely drop two or three sources. Those reports would fail the checker's set comparison and be marked INCOMPLETE. Iterating the full inventory means unchanged sources still get a section.
- **Coverage matches the checker's rule.** The checker requires the coverage set to equal the inventory. A single pass over that same inventory yields exactly that set. Nothing is missing and nothing is extra.
- **Content is verifiable.** A SHA-256 and line count per section let a reader confirm which version of each source was covered. They also make unchanged sources easy to recognise across reports.

## Suggestions (hardening, not blockers)

1. **Fail loudly on unreadable sources.** If a source can't be read or hashed, the run should stop with an error. It should not skip that section or write a placeholder. A skipped section produces a report that is guaranteed INCOMPLETE but looks like a normal output.
2. **Guard the "exactly once" half.** Iterating the inventory prevents omissions, but duplicate inventory entries would produce duplicate sections. Add a cheap guard:
   - Deduplicate or reject duplicate entries.
   - Before emitting, assert that the set of section IDs equals the inventory set and that the section count equals the inventory size.
   - Optionally assert the size is 4, if that number is truly fixed.
3. **Pin down the metadata definitions** so two runs on identical inputs produce identical reports:
   - Compute the SHA-256 over the raw file bytes, with no newline normalisation and no decoding.
   - Define line count precisely, including how a missing trailing newline is counted (e.g. `wc -l` semantics versus counting non-empty final segments).
4. **Use a deterministic section order**, either inventory order or sorted by ID. This keeps reports diffable across runs.

None of these change the architecture. They close edge cases the plan's main design already makes unlikely.
