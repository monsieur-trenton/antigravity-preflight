# Plan Review: Order Export, `discount` Handling

## The core semantics are correct

The export's mapping matches the schema:

| Input state | Schema meaning | Export behavior | Correct? |
|---|---|---|---|
| Field absent | No discount | `0` | ✅ |
| Explicit `null` | Unknown | `null` passed through | ✅ |
| Present with a value | Known discount | Value | ✅ (implied) |

The export doesn't collapse "unknown" into "zero," which is the most common mistake here. Downstream totals skip null records and flag them for review, so an unknown discount never gets counted as a real number. Collapsing absent into `0` is fine because the schema says they mean the same thing.

## Changes I'd want before shipping

1. **The output format must keep null separate from 0 and from empty.** The plan only works if the export's serialization can tell null apart from other values. JSON or Parquet can. CSV often cannot: an empty cell is ambiguous, and some readers turn it into `0` or `""`. State the output format and how null is written. If null is lost on the way downstream, the review-flag step never fires.

2. **Use decimal arithmetic for money, not floats.** Round-half-even only behaves predictably on exact decimal values. With binary floats, a value like `2.675` is really stored as `2.67499999...` and rounds the "wrong" way. Specify a decimal type, or integer cents, from parsing onward.

3. **Say where rounding happens.** Rounding each line and then summing gives different results from summing and then rounding once. Pick one, document it, and make downstream totals use the same convention. Otherwise reconciliation will show differences of a cent or so.

4. **Make totals order-independent across unordered batches.** Since batches arrive in no particular order, any float sum can vary slightly from run to run. Decimal or integer-cent sums avoid this. Also confirm that nothing depends on order, such as running totals, "first record wins" deduplication, or pagination cursors.

5. **Mark totals that are incomplete.** If null-discount records are skipped, the totals cover only part of the data. Show a count or amount of excluded records next to each total, so nobody reads a partial figure as the full number.

6. **Validate present values.** Decide what happens with negative discounts, discounts larger than the order amount, non-numeric strings, or a discount given as a percentage in one place and an absolute amount in another. Reject these or route them to review, rather than passing them through quietly.

## Minor points
- Keep an explicit `0` as `0`. It means the same as absent, so no issue, but don't let a "default if falsy" pattern turn it into something else.
- Batch retries need to be idempotent so a re-run batch isn't counted twice.

## Summary
The handling of absent versus null is right and agrees with the schema. The remaining risks are in implementation details: serialization keeping null intact, decimal precision, where rounding happens, and how partial totals are reported. These are fixable and don't require redesigning the plan.
