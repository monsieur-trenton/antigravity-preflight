# Review: Service Call Timeout and Retry Plan

**The timeout units are correct.** Library X takes milliseconds, so `timeout=5000` is 5 seconds, as intended. That is 2.5× the documented 2 s maximum and about 6× the p99. The retry policy is sound in principle because the call is idempotent. The issues below are about worst-case behavior, not correctness.

## Concerns

1. **The worst-case time per call is long.** With 4 attempts (1 initial + 3 retries) at 5 s each, plus backoff, a single logical call can hold a worker for about 20–25+ seconds.
   - If the upstream degrades and starts hanging, all 16 workers can be tied up within seconds. Throughput then collapses to under 1 call/s, and queued work backs up.
   - Add an **overall deadline** across all attempts, for example 6–8 s total. Alternatively, lower the per-attempt timeout to about 2.5–3 s, which still clears the documented maximum.

2. **The plan doesn't confirm what the timeout covers.** Check whether library X's `timeout` is connect-only, read/idle, or total request time. A read timeout that resets on each byte received can run well past 5 s. Confirm the semantics, and set connect and read timeouts separately if the library allows it.

3. **The backoff has no jitter.** Pure exponential backoff across 16 threads causes synchronized retry waves after an upstream blip. Add full or decorrelated jitter.

4. **Retries amplify load when the upstream is struggling.** Up to 4× traffic arrives exactly when the upstream is slow. Consider:
   - a retry budget, for example retries capped at about 10–20% of requests;
   - a circuit breaker that fails fast after sustained timeouts.

5. **The plan only retries on timeout.** Decide whether connection errors and 5xx/503 responses should also be retried. Also decide whether to honor `Retry-After`.

6. **Timeouts and retries aren't observable.** Emit metrics for timeouts, retry counts, and end-to-end latency, so you can tell when the 5 s ceiling is actually being reached.

## Summary

The core configuration is right: the units match and the margin over the documented maximum is reasonable. Before shipping, add an overall deadline, jitter, and some form of retry budget or circuit breaker, so a slow upstream can't exhaust the 16-thread pool.
