## Review: Nightly Compaction Plan

The structure is reasonable: a bounded window, explicit cancellation, reported failures, and periodic logging. The weak point is that the plan's feasibility rests on a number nobody has measured.

### 1. The throughput requirement is unverified (main risk)
- 40 GB in 30 minutes requires about **22–23 MB/s sustained**, end to end. Compaction usually reads and rewrites data, so real I/O is likely about 2× that, plus CPU for merging, sorting or compression.
- A single thread may or may not reach that. It depends on the format, compression codec, disk type, and what else runs at night.
- **Change:** Benchmark on the target host, or a representative sample, before go-live. You want at least 1.5–2× headroom over 23 MB/s, because input sizes tend to grow and nightly hosts are often contended.

### 2. Repeated cancellation could become the normal state
- If throughput falls short, the step gets cancelled every night. Each run is reported, but compaction never actually happens and the backlog grows, making the next run even less likely to finish.
- **Change:** Define what happens after a cancellation:
  - Is partial progress kept, through checkpointing, resumable or incremental compaction, or compacting by segment or partition?
  - Or is all the work thrown away?
- If work is thrown away, a 31-minute job will fail forever. Resumable or incremental compaction is strongly preferred.
- Also add an escalation rule, such as alerting after N consecutive cancellations, so this doesn't become a silent recurring report.

### 3. Cancellation must be safe
- **Change:** Confirm that cancelling at any point leaves the original data intact and readable. That means no half-written output gets swapped in, temporary files are cleaned up, and locks are released.
- Use write-to-temp plus an atomic swap, or an equivalent approach.
- State this explicitly in the plan and test it, for example by killing the job at several points during a trial run.

### 4. Logging could be more useful
- Logging once a minute is a fine interval. Make each log line include:
  - bytes processed
  - current rate
  - projected completion time
- **Optional:** If the projection clearly exceeds the window, say after 5–10 minutes, stop early or alert early instead of spending the full 30 minutes. This only makes sense if partial work is kept.

### 5. Single thread
- This is acceptable if the benchmark shows enough headroom. If it doesn't, parallelising by partition is the obvious lever.
- Note it as a fallback option rather than a blocker.

### 6. Minor
- Specify how "roughly 40 GB" is tracked over time. Size growth trends should feed back into the headroom check.
- Confirm the 30-minute window doesn't overlap with backups or other heavy nightly jobs on the same host.

### Summary
The design is sound in shape, but it isn't ready to rely on. The window's feasibility is unknown, and the plan doesn't say what happens to partial work or data integrity when cancellation fires. Measure throughput, make cancellation safe and ideally resumable, and add escalation for repeated cancellations.
