# Review: `orders.shipped_at` migration

The order of steps is correct: add the column as nullable, backfill it, then constrain it. The rollback is safe because the column is new, so dropping it loses no data that existed before. The problems are in the assumptions and what happens after the migration, not in the step sequence.

## Blocking concerns

**1. NOT NULL may be wrong for this table.**
An order normally exists before it ships. With NOT NULL on `shipped_at`, every insert into `orders` must supply a ship time. If the application creates an order at checkout and ships it later, every new order will fail after Step 3.
- "Shipments has a row for every order" may be true of today's historical data and false for new orders.
- **Confirm the business rule.** If an order can exist unshipped, drop Step 3 and leave the column nullable.

**2. The "every order has a shipment" claim is unverified.**
If it is wrong, Step 3 fails after Step 2 has already done its expensive work. Run these checks before the window:
```sql
-- orders with no shipment row
SELECT count(*) FROM orders o
WHERE NOT EXISTS (SELECT 1 FROM shipments s WHERE s.order_id = o.id);

-- orders with more than one shipment row
SELECT order_id, count(*) FROM shipments GROUP BY order_id HAVING count(*) > 1;
```

**3. The plan doesn't say which shipment to use when an order has several.**
Partial shipments and reshipments are common. A plain `UPDATE ... FROM shipments` join picks an arbitrary row in Postgres; MySQL behaves similarly. Define the rule explicitly, for example `MIN(shipped_at)` for first shipment or `MAX` for last.

## Required changes

**4. Plan the write path and keep the copies in sync.**
`shipped_at` will now be stored in two places. Decide who keeps them consistent after the migration:
- the application writing both, or
- a trigger, or
- treating `shipments` as the source of truth and `orders.shipped_at` as a cache.

Deploy any application change that writes `shipped_at` before Step 3. Otherwise inserts start failing as soon as the constraint lands.

**5. Make sure no writes happen between Step 2 and Step 3.**
Any order inserted or shipped during that gap arrives with a NULL and breaks Step 3. Do one of the following:
- confirm that application writes are actually stopped during the maintenance window, or
- run Steps 2 and 3 in one transaction (Postgres; DDL is transactional there), or
- re-run the backfill for NULLs immediately before Step 3.

**6. Make rollback match how the database handles DDL.**
- **Postgres:** wrap all three steps in one transaction. A failure then rolls back automatically, and the drop script becomes a backup.
- **MySQL:** each DDL statement commits on its own. Make the rollback idempotent with `DROP COLUMN IF EXISTS`, and test it from each possible failure point.

## Performance (acceptable in a maintenance window, still worth doing)

- **Step 2 cost:** updating 2M rows in one statement creates a large amount of WAL/binlog and table bloat, and in Postgres it rewrites every row. Batching it (for example 50k rows at a time by primary key) shortens lock times and makes progress visible. Run `VACUUM ANALYZE` afterwards.
- **Step 3 cost:** NOT NULL requires a full table scan under an exclusive lock. On Postgres 12+ you can avoid most of that lock time:
  1. Add `CHECK (shipped_at IS NOT NULL) NOT VALID`.
  2. Run `VALIDATE CONSTRAINT`, which takes a weaker lock.
  3. Run `SET NOT NULL`, which uses the validated check and skips the scan.
  4. Drop the check.
- **Index:** make sure `shipments.order_id` is indexed, or the backfill join will be slow.
- **Rehearsal:** run the full migration on a production-sized copy to measure how long it takes against the window.

## Summary

The mechanics are sound. The plan should not run until three things are settled: the NOT NULL business rule is confirmed against the real order lifecycle, the pre-check queries come back clean, and the multi-shipment rule and write path are defined. If orders can exist before they ship, remove Step 3 and keep the column nullable.
