# Review: Nightly Batch Plan

## Timing

| Stage | Typical | Observed max |
|---|---|---|
| 1. Import | 22 min | 25 min |
| 2. Transform | 18 min | 21 min |
| 3. Export | 12 min | 14 min |
| **Total (sequential)** | **52 min** | **60 min** |
| Deadline | | 75 min |
| **Headroom** | **23 min (31%)** | **15 min (20%)** |

The timing works. Even if every stage hit its worst observed time in the same run, the batch would finish 15 minutes early. Adding the per-stage maxima is conservative, since the slowest runs of each stage probably didn't all happen on the same night.

## Concerns

1. **A killed run fails silently.** The summary email goes out only when the batch ends. If the job is killed at 75 minutes, it probably never sends, so on-call would only learn about the lost data from the missing email. Since an overrun means permanent data loss, this is the most important gap.
2. **No early warning.** Nothing alerts when the run is heading toward the deadline. For example, if stage 1 plus stage 2 has passed about 55 minutes, someone should know before the kill happens.
3. **No recovery path.** The plan accepts losing a day's data but doesn't say whether that loss is truly unavoidable. Keeping the source data or checkpointing after each stage would allow a rerun or a resume from the last completed stage.
4. **Small sample and growth.** Thirty runs is only about a month. If data volume grows, durations will creep up, and the 15-minute margin could disappear within months. Trending stage durations would show this coming.
5. **Unaccounted overhead.** It's unclear whether the measured times include scheduler startup, environment setup, gaps between stages, or the time to send the email. If the 75-minute clock covers these, they come out of the headroom.

## Recommended changes

- Send an alert from a separate watchdog, not the batch itself, if no success email has arrived by T+75. Also have the batch alert on any stage failure.
- Add a soft-deadline warning, for example at T+60 or when cumulative elapsed time exceeds the expected value.
- Record each stage's duration and alert when it exceeds its historical maximum.
- Document how to recover or rerun after a killed batch, or confirm that recovery is impossible.

The schedule is sound, but because an overrun silently and permanently loses data, the plan needs failure detection before it can be considered complete.
