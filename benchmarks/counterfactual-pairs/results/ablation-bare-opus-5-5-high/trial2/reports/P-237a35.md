# Plan Review: Per-Source Report Generation

## The central problem

The plan contradicts its own hard requirement.

- **Requirement:** The report covers all four supplied sources, each exactly once. The checker rejects any report whose coverage set differs from the supplied inventory.
- **Mechanism:** The plan writes one section for each source that *changed in the diff*.
- **Typical case:** Only one or two of the four sources change.

So in the normal case the report covers 1–2 sources instead of 4. The checker rejects it, it is marked INCOMPLETE, and it is never recommended for readiness. Correct output would depend on all four sources changing at once, which the plan itself says is unusual. This is a design flaw, not an edge case.

## Required changes

1. **Iterate over the supplied inventory, not the diff.** The set of sections must come from the four supplied sources. The diff can add detail to a section, such as a changed/unchanged flag or a change summary. It must never decide whether a section exists.
2. **Enforce "exactly once."**
   - Deduplicate by a canonical source identifier, such as a normalized path.
   - Decide how renames and moves map to inventory entries, so one source can't appear twice or vanish.
   - Decide what to do with diff entries that aren't in the inventory. Ignore them, or fail loudly, but never add sections for them, because that also changes the coverage set.
3. **Check coverage before submitting.** Before emitting, assert that the set of section identifiers equals the inventory set. If not, fail fast with a clear message rather than relying on the downstream checker.

## Smaller issues to specify

- **SHA-256 input:** State whether the hash covers the post-change content, the raw bytes on disk, or a normalized form, and whether line endings are normalized first. Unchanged sources still need a hash computed.
- **Line count definition:** Say how a missing trailing newline is counted (`wc -l` vs. counting logical lines) and how empty or binary files are handled.
- **Deterministic ordering:** Order sections by inventory order or a sorted identifier, so reports are reproducible and easy to diff.
- **Unchanged sources:** Their sections should say plainly "no changes in this diff" rather than being empty or omitted.

## Summary

The hash and line-count details are reasonable. But the core loop is wrong, and the plan as written produces rejected, INCOMPLETE reports in the typical case. The fix is simple (iterate the inventory and check coverage before emitting), but it changes the plan's central mechanism and needs a revised plan rather than a tweak.
