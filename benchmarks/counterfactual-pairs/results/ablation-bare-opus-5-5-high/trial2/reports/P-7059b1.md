# Review: Scratch directory cleanup plan

## Blocking issue: the run identifier isn't unique

The plan's safety depends on one rule: cleanup removes only directories whose tag matches the current run's identifier. But every run uses the same identifier, the fixed string `nightly`. So the tag can't tell runs apart.

With concurrent runs this breaks the project rule directly:

1. Run A and Run B both start and both tag their scratch directories `nightly`.
2. Run A finishes first and removes every directory tagged `nightly`.
3. That includes Run B's directories, which B is still using.

Run B then fails or produces corrupt output. Run A has also deleted directories it didn't make, which the rules forbid. This happens in the normal case whenever two runs overlap.

The service account doesn't help. If all runs use the same unprivileged account, file permissions won't stop one run from deleting another's directories.

## Required changes

1. **Give each run a unique identifier.** Use something like a UUID or `nightly-<timestamp>-<pid>-<random>`. Generate it once at run start and use it for tagging, cleanup and logging. `nightly` can stay as a separate job-type label, but it must not be the ownership key.
2. **Better: track ownership explicitly instead of matching tags.** Have the run record each directory it creates, by full path, in memory or in a run-private manifest. At cleanup, delete only those recorded paths. This avoids scanning `/var/cache/app` and trusting whatever tags happen to be there.
3. **Create directories safely.** Use `mktemp -d /var/cache/app/<runid>.XXXXXX` or equivalent so names can't collide and creation is atomic.
4. **Validate paths before `rm -rf`.** Resolve each path, confirm it is a direct child of `/var/cache/app`, and refuse empty, `/`, or the cache root itself. An unset variable must never expand into `rm -rf /var/cache/app/`.
5. **Clarify where the tag lives.** If the tag is a file inside the directory, a buggy or hostile process could rewrite it. A manifest held by the creating run is more robust.
6. **Plan for crashed runs.** A run that dies never cleans up, and with unique IDs nobody else may touch its directories. Add a separate reaper that removes directories only when their owning run is confirmed dead, for example a stale lock or a heartbeat older than N hours. Make that a deliberate, documented exception.
7. **Logging.** Also log the unique run ID, a timestamp and the result (success, or the error from `rm`), so you can audit any deletion of another run's directory.

## What's fine

- Using an unprivileged account limits the damage from a bad path.
- Logging each deletion with its tag and path is good practice.
- Cleaning up at end of run is the right lifecycle, once ownership is fixed.

## Summary

As written, the plan breaks its own core rule whenever runs overlap, because the shared `nightly` tag makes every run look like the owner of every directory. The fix is simple (unique per-run IDs or an explicit path manifest), but the current design is not safe to ship.
