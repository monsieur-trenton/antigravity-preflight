# Review: Refund Approval Authorization Plan

## Does the logic hold?

Yes, as a chain of reasoning:

1. The endpoint admits only tokens with `refunds:approve`.
2. That scope is issued only to finance-admin members.
3. A token is revoked when its holder leaves the group and expires within 15 minutes anyway.
4. So only current finance-admin members can approve refunds.

The weak point is that the endpoint does no check of its own, so the whole policy depends on every step being true in practice. Each of the gaps below would break that chain.

## Gaps to close

**1. Revocation must actually reach the endpoint (highest risk)**
"Revoked as soon as its holder leaves the group" only helps if the endpoint checks revocation status. If tokens are self-contained JWTs checked locally by signature and expiry, revocation has no effect there. A removed member keeps approval power for up to 15 minutes. You need one of:
- token introspection, or a revocation-list check, on `approve_refund`, or
- acceptance of a 15-minute window, written down as a known exception to the policy.

**2. Refresh tokens**
The plan covers access tokens only. If refresh tokens exist, the issuer must check group membership again on every refresh. It must not copy scopes from the original grant. Otherwise a removed member can keep minting fresh access tokens with the scope.

**3. Other ways to get the scope**
"Only for members of finance-admin" must hold for every issuance path, not just interactive login. Check:
- client-credentials grants and service accounts
- token exchange or delegation flows
- admin or debug token minting
- test or staging issuers that share signing keys with production
- any other issuer the endpoint trusts

**4. Audience and issuer validation**
The endpoint should accept only tokens issued by the expected issuer and meant for this service (`aud`). Otherwise a token minted for another resource server could be replayed here if it happens to carry the same scope string.

**5. Audit identity source**
The identity in the audit log should come from the validated token subject, never from a request parameter. If service accounts can hold the scope, the log should also record the acting human.

## Recommended hardening (defense in depth)

- Have the endpoint also check a group claim, or look up group membership directly. A scope-issuance bug then fails safe instead of granting access.
- Decide whether separation of duties is in scope: can a finance-admin approve a refund they requested or that benefits them? The stated policy doesn't forbid it, but auditors often expect this rule.
- Add tests that a removed member's existing token and refresh token are rejected at `approve_refund`.

## Summary

The design is sound and the reasoning chain is valid. However, the policy holds only if revocation is enforced at the endpoint, refresh is gated on current membership, and no other issuance path grants the scope. Confirm or fix those items, and preferably add a direct group check on the endpoint.
