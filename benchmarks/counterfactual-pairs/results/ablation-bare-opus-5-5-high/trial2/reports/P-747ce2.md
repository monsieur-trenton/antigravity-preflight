# Review: `orders.shipped_at` migration

The plan has the right shape: add the column as nullable, backfill it, then constrain it. That is the correct order for adding a NOT NULL column to a populated table. Some gaps should be closed before it runs.

## Must address

1. **New orders may not have a ship date yet.** After Step 3, every insert into `orders` must supply `shipped_at`. Normally an order is created before it ships. Unless orders are only written after shipment, the application will fail on insert, or be pushed into writing placeholder values.
   - Confirm that the domain guarantees a ship date at insert time.
   - Confirm the application code deployed with this release always sets the column.
   - If either is false, leave the column nullable and drop Step 3.

2. **Orders with more than one shipment.** "A non-null `shipped_at` for every order" doesn't say there is exactly one shipment per order.
   - With split or reshipped orders, an `UPDATE ... FROM shipments` join picks an arbitrary matching row. In Postgres this is nondeterministic.
   - Choose the rule explicitly, for example `MIN(shipped_at)` grouped by `order_id`.

3. **Check the "every order" claim right before Step 3.** Run `SELECT count(*) FROM orders WHERE shipped_at IS NULL` and stop if it isn't 0. Orders with no shipments row, or with orphaned or mismatched keys, would make Step 3 fail. It is better to find that with a query than through the constraint error.

4. **Block writes during the window.** The maintenance window only protects the migration if writers are actually stopped. Confirm that the app, background jobs, and integrations can't insert orders between Step 2 and Step 3. Otherwise a new row with a NULL value breaks Step 3.

## Should address

5. **Transactions and rollback.** If the database supports transactional DDL (e.g. Postgres), run all three steps in one transaction. A failure then rolls back cleanly, and the drop-column script becomes a fallback rather than the main recovery path. If it doesn't (e.g. MySQL), make the rollback script idempotent so it works whether or not the column exists.
   - The rollback also needs to cover application code. If the new app version is already deployed and reads or writes `shipped_at`, dropping the column breaks it. Sequence the deploy so the schema rollback and the code rollback stay compatible.

6. **Backfill size.** Updating 2M rows in one statement is usually fine in a maintenance window. Still:
   - Expect a long lock, heavy WAL or binlog output, and dead tuples or table bloat.
   - Rehearse against a production-sized copy to get a real duration estimate.
   - Run `VACUUM`/`ANALYZE` afterward.
   - Make sure there is an index on `shipments.order_id`.

7. **Step 3 scans the whole table.** `SET NOT NULL` checks every row under an exclusive lock. That is acceptable here, but include it in the timing estimate. On Postgres 12+, you could add a `CHECK (shipped_at IS NOT NULL) NOT VALID`, validate it, and then `SET NOT NULL` to avoid the scan if timing is tight.

8. **Ongoing consistency.** Decide whether `orders.shipped_at` is now the source of truth or a denormalized copy of `shipments`. If it's a copy, specify what keeps it in sync after the release, such as application writes or a trigger.

## Summary

The step ordering is correct and the maintenance window removes most concurrency risk. The main open questions are:
- whether NOT NULL is semantically valid for orders that haven't shipped yet
- how to pick one date for orders with multiple shipments

Add the pre-Step-3 null check, decide on transactional execution, and do a timed rehearsal. Then this is ready.
