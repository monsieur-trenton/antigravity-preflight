# Review: orders.shipped_at migration

## Blocking issue: the step order guarantees failure

The plan runs **step 1 → step 3 → step 2**, which adds the NOT NULL constraint before the backfill.

- After step 1, all ~2M existing rows have `shipped_at = NULL`.
- Step 3 then tries to add NOT NULL. The database validates existing rows, finds 2M NULLs, and rejects the constraint. This happens on Postgres, MySQL, SQL Server and others.
- The step fails, the rollback drops the column, and the release does nothing.

This failure is certain, not a risk. The rollback keeps it from corrupting data, but the maintenance window is wasted.

**Required fix:** run **step 1 → step 2 → step 3**: add the nullable column, backfill it, then add NOT NULL.

## Other issues to resolve before running

1. **NOT NULL may break future inserts.** If the application creates an order before it ships, new rows will have no `shipped_at` and the constraint will reject them after the release. Confirm that every insert path supplies a value, or that orders only exist once shipped. If neither is true, the column should probably stay nullable, or the app change needs to ship with this migration.

2. **Check the backfill assumption.** "Shipments has a non-null shipped_at for every order" should be verified, not assumed:
   - Count orders that have no matching shipment row (anti-join). Any such rows will fail step 3.
   - If an order can have **multiple shipments**, decide which value wins (for example `MIN(shipped_at)`). Otherwise an `UPDATE ... FROM` join may pick a row arbitrarily.

3. **Add a gate between steps 2 and 3.** Run `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL` and continue only if it returns 0. If it doesn't, stop and investigate rather than triggering the rollback.

4. **Backfill at scale.** A single UPDATE on 2M rows is usually fine in a maintenance window. Still, expect lock duration, WAL/redo volume and table bloat (on Postgres, every row gets rewritten). Consider batching, and do a timed dry run on a production-sized copy.

5. **Constraint validation lock.** Adding NOT NULL scans the whole table under an exclusive lock. That's acceptable in the window, but include it in the timing estimate. On Postgres 12+, adding and validating a `CHECK (shipped_at IS NOT NULL)` constraint first lets `SET NOT NULL` skip the scan.

6. **Rollback.** Test the rollback script too. Make sure that dropping the column is safe at every point of failure, including after the backfill, and that no application code already depends on the column.

## Summary

The approach (add nullable column, backfill, enforce constraint) is the right pattern, but the stated order makes the release fail deterministically. Reorder to 1 → 2 → 3, check the data before applying the constraint, and confirm that NOT NULL fits how orders are created. With those changes the plan is sound.
