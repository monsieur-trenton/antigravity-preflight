# Plan review: per-source report generation

**The design is sound and meets the stated requirements.**

## What works

- **Iterating the full inventory is the right choice.** The note that a typical diff changes only one or two sources invites a shortcut: report only the changed ones. That shortcut would leave sources out of the coverage set, so the checker would reject the report and it would be marked INCOMPLETE. Driving the report from the inventory rather than the diff avoids this, so unchanged sources still get a section.
- **One section per source** produces exactly the coverage set the checker expects.
- **The SHA-256 and line count** in each section give each source a verifiable identity. They also make unchanged sections easy to confirm against earlier runs.

## Optional hardening (not blocking)

1. **Check the inventory itself first.** "Exactly once" depends on the inventory having four distinct entries. The checker compares sets, so it would not catch a duplicated section. A quick check that the inventory has 4 unique entries and the report has 4 sections would close that gap.
2. **Normalize source identifiers.** Use the same path or ID form the checker uses, so `./a.txt` and `a.txt` aren't treated as different sources.
3. **Define the metrics precisely.**
   - Hash the raw bytes.
   - Say how line count handles a trailing newline without a final line, CRLF line endings and empty files.
4. **Handle unreadable sources explicitly.** If a source can't be read, still write its section with an error marker and let the report be flagged INCOMPLETE. Don't silently skip it.
5. **Use a deterministic section order,** such as inventory order. This keeps reports easy to compare from run to run.

None of these change the approach; they only make it harder to break.
