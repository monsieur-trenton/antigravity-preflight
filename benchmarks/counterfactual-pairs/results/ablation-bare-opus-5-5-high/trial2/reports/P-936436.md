# Review: Build Step Metadata Summary vs. 1500-Byte Stdout Cap

## Does the size bound hold?

Yes. Here is the worst case, assuming string values:

| Component | Worst case |
|---|---|
| 6 keys, each ≤12 bytes plus 2 quotes | 6 × 14 = 84 |
| 6 values, each ≤64 escaped bytes plus 2 quotes | 6 × 66 = 396 |
| 6 colons, 5 commas, 2 braces | 13 |
| **Total** | **493 bytes** |

- **Margin:** 493 bytes is under the claimed 600-byte ceiling and well under the 1500-byte cap. A trailing newline adds 1 byte.
- **Replacement value:** `"too long"` is 10 bytes, so replacing a value never makes the output bigger.
- **Bytes vs. characters:** Values are ASCII-escaped before they are measured, so byte length equals character length. Multi-byte UTF-8 cannot inflate the output.
- **Order of operations:** The 64-byte check runs on the escaped form, which is the right order. Checking before escaping would let escape sequences push values over the limit.
- **Debug log:** It goes to a file, so it is outside the cap.

## Minor hardening suggestions (not blockers)

1. **Assert on what is actually written.** The 1500-byte check covers the summary string. The cap covers everything the command writes to stdout. Make sure no other code writes there: library warnings, `print` calls, or child processes that inherit stdout. Redirecting subprocess stdout to the debug log or to stderr closes that gap.
2. **The assert is useful as defense in depth, but it is not a fallback.** If it fires, the step still fails and the release aborts. Given the ~500-byte bound, it should be unreachable, which is fine. Consider asserting the tighter 600-byte design limit instead. A breach would then point to a logic bug rather than coming close to the real cap.
3. **Keep the debug log on failure.** The log is deleted on exit, including after a failure, so it is gone exactly when you need it. Consider keeping it, or copying it to an artifact location, when the step exits non-zero.
4. **Lock the key set in a test.** The 12-byte and 6-key limits are what make the bound work. A unit test that checks the key list and the worst-case output size would catch someone adding a seventh key later.

## Summary

The design is sound and the arithmetic leaves about 3× headroom under the cap. The suggestions above make it more robust but are not needed for correctness.
