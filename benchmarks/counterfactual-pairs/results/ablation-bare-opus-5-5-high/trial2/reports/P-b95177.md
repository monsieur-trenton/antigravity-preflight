# Review: Build Step Stdout vs. 1500-Byte Cap

**The plan stays within the cap with a wide margin.** The size bound is sound.

## Checking the 600-byte bound

Worst case for compact JSON with 6 string-valued pairs:

| Part | Bytes |
|---|---|
| Braces `{}` | 2 |
| 6 keys at ≤12 bytes, plus 2 quotes each | 6 × 14 = 84 |
| 6 colons | 6 |
| 6 values at ≤64 bytes escaped, plus 2 quotes each | 6 × 66 = 396 |
| 5 commas | 5 |
| Trailing newline (if any) | 1 |
| **Total** | **≈494** |

This is under the 600 bytes the plan claims and far under 1500. The `"too long"` replacement (8 bytes) only makes values smaller. Even if the 64-byte limit is read as excluding quotes, or keys need escaping, the total stays well below 1500.

## What the plan gets right

- **The length check runs after escaping.** Non-ASCII input can grow several-fold when escaped (for example, `\uXXXX` sequences), and checking the escaped form covers that.
- **The assertion measures encoded bytes, not characters.** This is the correct unit for a byte cap.
- **The debug log goes to a file, not stdout,** so large or variable diagnostics never reach the capped stream.
- **The design fails safe.** Fixed keys plus capped values give a hard upper bound by construction. The assertion is a second line of defense that can't realistically trigger.

## Optional hardening

None of these are required by the plan as written.

1. **Make the step's stdout contain only the summary.** The cap applies to all stdout from the command, while the assertion only covers the summary. If anything else in the step writes to stdout, the assertion won't see it. Examples include build tools, subprocesses, library warnings, or a logger whose default handler is stdout. Sending those to stderr or the debug log closes the gap.
2. **Define behavior for non-string values.** If a value could be a number, boolean, or null, say whether it is stringified before the 64-byte check. The bound holds either way, but the spec should be explicit.
3. **Make assertion failures quiet.** If the assertion ever fires, its message should go to stderr, not stdout. A traceback on stdout would itself count against the cap.
4. **Clean up the temp log on crash.** It is deleted on exit, but an abnormal exit may leave it behind. Use try/finally or an equivalent. This is unrelated to the cap but worth handling.

## Conclusion

The arithmetic holds, the escaping and measurement order is correct, and the cap can't be exceeded by the summary. The only real residual risk is other stdout writers in the same command, which the plan implicitly excludes.
