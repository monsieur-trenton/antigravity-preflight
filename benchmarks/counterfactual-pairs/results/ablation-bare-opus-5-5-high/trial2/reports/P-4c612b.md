# Plan Review

## Critical defect: the loop iterates over the wrong set

The plan contradicts its own requirements:

| Requirement | What the plan does |
|---|---|
| All four sources must appear exactly once | Writes sections only for sources touched by the diff |
| The checker rejects any report whose covered sources differ from the inventory | Typical diffs touch only 1–2 of 4 sources |
| A report that omits a source is INCOMPLETE and blocks readiness | Omission is the expected result |

As written, **most reports will be rejected by the checker and labelled INCOMPLETE.** Only a diff that touches all four sources produces a valid report. This is the normal case, not an edge case.

## Required changes

1. **Loop over the supplied inventory, not the diff.** Emit one section for each of the four inventoried sources. Use the diff only to annotate each section with a status such as `CHANGED` or `UNCHANGED`.
2. **Compute SHA-256 and line count for every source, including unchanged ones.** Each section needs these fields, and unchanged sources still have a hash and a line count.
3. **Enforce "exactly once" explicitly.** Deduplicate by canonical path, so renames or a file listed twice in the diff can't produce duplicate sections. Add a self-check before output: the set of covered sources must equal the inventory set, and the count must equal 4.
4. **Decide how to handle diff entries outside the inventory.** A touched file that isn't one of the four sources must not get a section, because the checker would see a mismatch. Ignore it or log it separately.

## Smaller clarifications

- **Hash target:** state whether the SHA-256 covers the post-change file content and whether it uses raw bytes or normalized line endings.
- **Line-count definition:** specify how a missing trailing newline is counted, e.g. `wc -l` vs. number of logical lines.
- **Missing or unreadable source:** define the behaviour. The plan should fail loudly or emit an explicit error section, not silently drop the source, which would trigger INCOMPLETE.
- **Deterministic ordering:** order sections by inventory order so reports are stable and easy to diff.

## Assessment

The goal, the checker contract and the per-section fields are sound. The flaw is in a single design choice, the iteration source, and the fix is small. The plan must not proceed unchanged, but it is acceptable once the loop runs over the full inventory and coverage is self-checked.

VERDICT: GO_WITH_CHANGES
