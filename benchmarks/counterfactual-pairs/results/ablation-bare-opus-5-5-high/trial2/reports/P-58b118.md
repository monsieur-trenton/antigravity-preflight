# Review: `orders.shipped_at` migration

## Blocking issue: the steps run in the wrong order

The plan runs **1 → 3 → 2**, so the NOT NULL constraint goes on before the backfill.

- After step 1, all ~2M existing rows have `shipped_at = NULL`.
- Step 3 then tries to add NOT NULL. PostgreSQL, MySQL, SQL Server and Oracle all check existing rows when the constraint is added, so **step 3 will fail every time**.
- The rollback then drops the column. Step 2 never runs.

At best, the migration uses the maintenance window and changes nothing. If the tooling doesn't stop on errors, step 2 could run against a dropped column or a half-rolled-back state. The plan cannot succeed as written.

**Fix:** run 1 → 2 → 3. Add the column, backfill it, confirm there are no NULLs, then add the constraint.

## Other issues to fix before re-review

1. **NOT NULL may be the wrong rule for future orders.** The backfill works because every *existing* order has shipped. But a newly placed order hasn't shipped yet. With NOT NULL, either inserts of new orders will fail, or the application will have to write a placeholder value, which is false data. Confirm that orders are only ever inserted after they ship. Otherwise, leave the column nullable or use a different design.

2. **The backfill join needs to be precise.** "Shipments holds a shipped_at for every order" doesn't say whether it's exactly one shipment per order. If an order can have several shipments (split or partial shipments), the UPDATE-with-join may pick one at random or fail. Decide which value is correct, such as `MIN(shipped_at)` or the first shipment, and aggregate explicitly.

3. **Check for NULLs before step 3.** Run `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL` and stop if it returns anything other than 0. That catches orphaned orders and join mismatches before they become a failed constraint.

4. **Lock time and transaction size for 2M rows.**
   - Backfill in batches (for example 10k–50k rows per batch) instead of one huge UPDATE. This limits log/WAL growth, lock time and replication lag.
   - Make sure `shipments.order_id` is indexed, or the join will be slow.
   - On PostgreSQL, `SET NOT NULL` scans the whole table while holding an ACCESS EXCLUSIVE lock. On PG 12+ you can avoid most of that: add `CHECK (shipped_at IS NOT NULL) NOT VALID`, run `VALIDATE CONSTRAINT`, then `SET NOT NULL`, which uses the validated check and skips the scan.

5. **Make the rollback safe.**
   - Use `DROP COLUMN IF EXISTS` so it still works if step 1 is what failed.
   - Running steps 1–3 in a single transaction (where the database supports transactional DDL, such as PostgreSQL) gives a clean automatic rollback. The trade-off is one long transaction, which conflicts with batching. Pick one approach on purpose.
   - Check that nothing outside the migration (app code, views, ETL jobs) has started using `shipped_at` before the rollback drops it.

6. **Block writes during the window.** Confirm the maintenance window actually stops inserts and updates to `orders`. Otherwise rows added between the backfill and the constraint can break step 3.

7. **Rehearse it.** Run the corrected migration against a production-sized copy to measure how long it takes and to test the rollback, before the real window.

## Summary

The step order makes the migration fail every time, so it can't go ahead as written. Reordering to 1 → 2 → 3 is necessary but not sufficient. Also settle whether NOT NULL fits future unshipped orders and define the join for orders with several shipments, then re-review.
