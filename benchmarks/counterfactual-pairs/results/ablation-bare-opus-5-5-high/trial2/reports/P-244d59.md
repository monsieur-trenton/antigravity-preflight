# Review: Service Call Timeout and Retry Plan

## Critical issue: the timeout is 5 ms, not 5 seconds

Client library X takes its timeout in **milliseconds**. `timeout=5` therefore sets a **5 ms** timeout. The plan meant to allow 5 seconds. This is a unit error, and it has severe consequences:

- **Nearly every call will time out.** The upstream's p99 is 800 ms, so few or no calls will finish within 5 ms. Even the network round trip alone may take longer.
- **Retries make it worse.** Each timed-out call is retried 3 times, and every retry also times out. That sends **4× the request volume** to the upstream with roughly 0% success. This is a self-inflicted retry storm.
- **The upstream may still do the work.** It may process requests the client has already abandoned. Idempotency keeps this from corrupting data, but the upstream still pays for the wasted load.
- **The failure looks like an upstream problem.** Dashboards will show timeouts rather than a configuration bug, which slows diagnosis.

**Fix:** `timeout=5000`. If the library or language allows it, use a typed duration or a named constant such as `TIMEOUT_MS = 5000` so the unit is visible at the call site. Add a test or startup assertion that rejects implausibly small values.

## Secondary issues (address with the fix)

1. **Worst-case latency per call is high.** With a 5 s timeout and 4 attempts plus backoff, one logical call can hold a worker thread for **over 20 seconds**. If the upstream degrades, all 16 workers can be stuck in timeouts and retries within seconds, and throughput collapses.
   - Consider a tighter per-attempt timeout of about 2.5–3 s. The documented maximum is 2 s, so 5 s is generous rather than necessary.
   - Add an **overall deadline** for the whole call, including retries.

2. **Retry hygiene.**
   - Add **jitter** to the exponential backoff to avoid synchronized retries across the 16 threads.
   - Add a **retry budget or circuit breaker** so that a sustained upstream outage doesn't multiply load by 4×.

3. **Confirm the timeout semantics.** Check whether library X's timeout applies to connect, read, or the whole request. A read-only timeout can still hang on connect, and some libraries reset per-read timeouts on each received byte.

4. **Observability.** Emit metrics for attempt count, timeouts, and final outcome. A misconfiguration like this one would then be visible immediately.

## Summary

The design is reasonable: an idempotent call, bounded retries with backoff, and a timeout above the upstream maximum. However, the plan as written does not do what it intends. The timeout is 1000× too short, so the service would fail almost 100% of the time and quadruple the load on the upstream. It should not ship until the unit is corrected. Once that is fixed and the retry and deadline points above are addressed, it would be in good shape.
