## Review

**Main issue: `main()` is now broken.**

The plan changes `load_config(path)` so a missing file raises `ConfigError` instead of returning `None`, but leaves `main()` unchanged. `main()` still relies on the old contract:

```python
cfg = load_config(path)
if cfg is None:
    print("no config")
    sys.exit(2)
```

After the change:
- When the config is missing, `ConfigError` escapes `main()` uncaught.
- The user sees a traceback instead of `no config`.
- The process exits with status **1** (Python's default for an uncaught exception) instead of **2**.
- The `if cfg is None` branch becomes dead code.

Any script, CI job or wrapper that checks for exit code 2 or for the `no config` message will silently change behaviour. This is a regression in the program's public interface.

**Fix:** update `main()` along with the other callers:

```python
try:
    cfg = load_config(path)
except ConfigError:
    print("no config")
    sys.exit(2)
```

Then remove the `is None` check, unless `load_config` can still return `None` on some other path. If it can, document that path.

**Secondary points**

1. **Test gap.** Tests cover `schedule()` and `report()` but not `main()`, which is why this regression would go unnoticed. Add a test that runs `main()` with a missing config path and asserts the `no config` output and exit status 2.
2. **Scope of `ConfigError`.** Check whether `ConfigError` is raised *only* for a missing file. If it is also raised (now or later) for malformed or unreadable configs, then `schedule()` and `report()` will silently fall back to defaults when a config is broken. That hides real errors from users. Consider catching a narrower subclass (e.g. `ConfigNotFoundError`), or at least logging a warning when falling back.
3. **Other callers.** Confirm by search (grep, IDE "find usages") that these three are really the only callers of `load_config`, including scripts, plugins and tests. Any caller that checks for `None` will have the same problem as `main()`.
4. **The file-size note** (plain text, under 10 KB) doesn't affect this change and needs no action.

**Overall:** the direction is sound. Raising an exception for a missing file is clearer than returning `None`, and the fallback in `schedule()` and `report()` is reasonable. But the plan as written breaks the CLI's documented behaviour. It's safe to proceed once `main()` is updated and covered by a test.

VERDICT: GO_WITH_CHANGES
