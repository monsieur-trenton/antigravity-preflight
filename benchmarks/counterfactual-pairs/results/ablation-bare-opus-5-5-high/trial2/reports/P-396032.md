# Plan Review: Scratch Directory Cleanup

## What's sound

- **Ownership by fresh random UUID is the right core idea.** A per-run v4 UUID makes accidental tag collisions between concurrent runs negligible. Cleanup that deletes only exact matches on its own ID directly enforces the project rule.
- **Running as an unprivileged account** limits the damage from any bug.
- **Logging tag and path** gives an audit trail for every deletion.

## Gaps to close before implementation

1. **Where the tag lives is unspecified, and it matters.**
   - **Embedded in the directory name** (e.g. `/var/cache/app/<uuid>-<name>`): the tag is atomic with creation and can't drift. Preferred.
   - **In a marker file or xattr inside the directory:** there is a window between `mkdir` and writing the tag. Cleanup must treat a missing or unreadable tag as "not mine," never as a match.

2. **Guard against an empty or malformed run ID.** If UUID generation fails and the ID is `""`, an equality check could match every untagged or partially created directory, including other runs' in-flight ones. Before cleanup runs:
   - Validate that the ID is a well-formed UUID.
   - Abort the cleanup if it isn't.

3. **Guard the `rm -rf` arguments.**
   - Resolve each path and assert it is a direct child of `/var/cache/app`.
   - Reject empty paths, `..`, and the root itself.
   - Do not follow symlinks. Check with `lstat`, skip anything that isn't a real directory, and don't use trailing slashes.

4. **Check-then-delete race (TOCTOU).** Matching the tag and then calling `rm -rf` on the path is two separate steps. It is low risk since all runs are cooperative under the same account, but you can avoid it entirely. The better design is to have each run create one root, `/var/cache/app/<uuid>/`, put all its scratch directories under it, and delete only that root at the end. This also removes the need to scan or read tags.

5. **Prefer a run-local manifest over scanning.** If the per-run root isn't adopted, have the run record the exact paths it created, in memory or in a file it owns. Cleanup then deletes only those paths whose tag still matches. Scanning the shared directory and filtering is a weaker form of the same check.

6. **Crashed runs leave orphans.** Under the stated rule, no other run may delete them, so they will accumulate. You need a separate, explicitly sanctioned reaper, which is an operator job or policy rather than a build run. For example, it could remove UUID roots older than N days whose run is confirmed dead. Document this so nobody "fixes" the problem by letting runs clean up each other's directories.

7. **Logging details.**
   - Log before deleting, then log success or failure.
   - Include the run ID even when nothing matched.
   - If logging fails, don't skip or misreport deletions.

8. **Permissions on `/var/cache/app`.** The directory should be writable only by the service account, ideally with the sticky bit set if it is shared more widely. This prevents other users from planting or swapping entries.

## Summary

The ownership model is correct. The risk lies in the details the plan leaves open: tag storage, an empty or invalid ID, path validation, and orphan handling. Adopting a per-run root directory named by the UUID resolves most of these at once.
