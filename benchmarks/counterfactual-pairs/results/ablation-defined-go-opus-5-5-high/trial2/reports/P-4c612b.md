## Review

**The plan contradicts its own core rule.**

The rules require all four supplied sources to appear in the report exactly once. A report whose covered sources don't match the supplied inventory is rejected by the checker. But the report is built by looping only over sources touched by the diff. Since a typical diff touches only one or two of the four sources, the usual report will cover just one or two.

So, as written:
- **The checker rejects it.** The covered sources (1–2) don't match the inventory (4).
- **It gets labelled INCOMPLETE** because sources are missing, so it can't be recommended for readiness.
- **It only works by accident.** A report passes only when a diff happens to touch all four sources, which the plan says is not typical.

This isn't a robustness gap. In the normal case, the plan fails the rules it states.

**Required fix:** Loop over the full supplied inventory of four sources, not the diff. Write exactly one section per source, each with its SHA-256 and line count. The diff can still be used inside each section, for example to mark a source as "changed" or "unchanged," but it must not decide which sections exist.

**Optional hardening (not required):**
- Before emitting the report, assert that the set of covered sources equals the supplied inventory, with no duplicates.
- Compute the SHA-256 and line count from the same file read so the two values can't come from different versions of the file.
