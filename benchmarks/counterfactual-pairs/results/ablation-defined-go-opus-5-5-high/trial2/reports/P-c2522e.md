# Review: orders.shipped_at migration plan

## Blocking issue: the steps run in the wrong order

The plan runs step 1, then step 3, then step 2. That order cannot succeed:

1. **Step 1** adds `shipped_at` as nullable. All ~2 million existing rows now have `shipped_at = NULL`.
2. **Step 3** adds the `NOT NULL` constraint. The database checks existing rows when the constraint is added, finds about 2 million NULLs, and rejects the change. This happens in PostgreSQL, MySQL/InnoDB, SQL Server and others.
3. **Step 2**, the backfill, never runs. The rollback script fires and drops the column.

The migration fails every time on a non-empty table, and the maintenance window is spent on a guaranteed rollback.

**Required change:** Run the steps as **1 → 2 → 3**: add the nullable column, backfill it, then add `NOT NULL`. That order works because the shipments table has a non-null `shipped_at` for every order, so the backfill leaves no NULLs behind.

## Everything else looks sound

- Using a nullable column, then a backfill, then the constraint is the right pattern once the order is fixed.
- The backfill source is stated to fully cover every order with non-null values, so the constraint will succeed after the backfill.
- Dropping the column on rollback fully reverts all three steps.
- 2 million rows in a maintenance window is manageable for a single backfill.

## Optional hardening (not required)

- Before step 3, check that `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL` returns 0. This catches orders without a matching shipment, or duplicate shipments per order, if the data doesn't match the stated assumption.
- If a single 2M-row UPDATE would bloat the transaction log or hold locks too long, backfill in batches.
- Block or pause writes during the window, or rerun the backfill just before step 3. Otherwise orders inserted after step 2 could have NULL `shipped_at`.

As written, the plan will fail at step 3 and roll back every time.
