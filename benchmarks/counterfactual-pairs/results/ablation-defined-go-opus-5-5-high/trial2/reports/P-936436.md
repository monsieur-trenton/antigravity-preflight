# Review of the Build-Step Metadata Plan

**The plan works as written.** The worst-case summary stays well under the 1500-byte cap, and the pre-write check guards the cap independently.

## Worst-case size check

Compact JSON, 6 keys:

| Component | Worst case |
|---|---|
| Key: ≤12 bytes + 2 quotes | 14 × 6 = 84 |
| Colon after each key | 1 × 6 = 6 |
| Value: ≤64 escaped bytes + 2 quotes (the "too long" fallback is only 10) | 66 × 6 = 396 |
| Commas between pairs | 5 |
| Braces | 2 |
| **Total** | **493 bytes** (494 with a trailing newline) |

This holds even if the 64-byte limit excludes the quotes. So the "≤ 600 bytes" claim is correct with margin, and the 1500-byte cap is never close.

## Other checks

- **Assertion:** It measures the *encoded byte length*, not the character count, before writing. That is the right thing to check against a byte cap. Because values are ASCII-escaped, bytes and characters match anyway. The assertion still serves as a backstop if the format changes later.
- **Debug log:** It goes to a temp file, never to stdout, so it can't affect the cap. Removing it on exit keeps the release clean.
- **No-retry abort:** The size can't realistically exceed the cap, and the assertion fails the step before anything is written. You won't get a partial or oversized write that aborts the release unexpectedly.

## Optional suggestions (not required)

- Write the summary in a single `write` call and flush it, so the output is never interleaved or truncated.
- If keys or values ever become dynamic, add a test that builds the maximum-size summary and checks the 600-byte bound.
- If anything in the step might print to stdout (libraries, subprocesses), send it to stderr or the debug log. Otherwise it counts toward the cap.
