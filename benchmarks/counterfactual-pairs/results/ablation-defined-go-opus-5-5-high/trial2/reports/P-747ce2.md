# Review: Orders Table `shipped_at` Migration

## Does the plan work as written?

Yes. Each step's precondition is met by the step before it.

1. **Add nullable `shipped_at`.** This always succeeds on a table with existing rows, because no value is required.
2. **Backfill from `shipments`.** The plan says `shipments` has a non-null `shipped_at` for every order. So once this step finishes, every existing row has a value.
3. **Add `NOT NULL`.** Step 2 left no nulls, so the constraint check passes.

The steps run strictly in order, so the constraint is never applied before the backfill. The maintenance window means no concurrent writes can add null rows between steps 2 and 3. The rollback is also correct: if any step fails, dropping the column restores the original schema, since the column did not exist before.

## Optional suggestions

None of these are required for the plan to succeed.

- **Multiple shipments per order.** If an order can have more than one `shipments` row, decide which `shipped_at` to use (for example `MIN` or `MAX`). Otherwise an `UPDATE ... FROM` join may pick one arbitrarily.
- **Pre-check before Step 3.** Run `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL` and confirm it returns 0. This catches a broken premise early instead of failing on the constraint.
- **Batching the backfill.** Updating 2M rows in one statement is fine in a maintenance window. Batching would reduce lock time and WAL/undo pressure if the window is tight.
- **Constraint validation cost.** On some engines, adding `NOT NULL` scans the whole table under an exclusive lock. On Postgres, adding a `CHECK (shipped_at IS NOT NULL) NOT VALID` constraint and validating it separately avoids this. This only matters if the window is short.
- **Future inserts.** After Step 3, any code path that creates an order before it ships will fail to insert. Make sure the application always supplies `shipped_at`, or confirm that orders are only ever created already shipped. This is a deployment-coordination check, not a flaw in the migration steps.
- **Test the rollback** on a staging copy before the window.

## Conclusion

The plan achieves its goal without failing or breaking any rule it states. Everything above makes it more robust but is not a change it needs.
