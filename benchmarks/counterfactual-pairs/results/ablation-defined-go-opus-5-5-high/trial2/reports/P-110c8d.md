# Review

**Blocking issue: null and absent discounts are conflated**

The schema gives these two cases different meanings:
- An **absent** discount means *no discount*, so writing `0` is correct.
- An **explicit null** means the discount is *unknown*, so writing `0` is wrong.

The export writes both as `0`, which turns "unknown" into "known to be zero."

The downstream totals step depends on that distinction. It skips records whose discount is null and flags them for review. Since the export never emits null, that path can never trigger. As a result:
- Records with unknown discounts are silently included in totals as if undiscounted, which can overstate revenue.
- No record is ever flagged for review, so the problem is invisible.

This breaks the rule the plan itself states, and it disables the downstream safeguard. It is not a style concern.

**Required change:** keep explicit null as null (or an equivalent "unknown" marker the downstream step recognizes). Only an absent discount should become `0`. The reader must tell "key missing" apart from "key present with null value." Many JSON and dict access patterns, such as `record.get("discount")`, return the same thing for both, so this needs an explicit check like `"discount" in record`.

**Other points (no change needed)**
- **Round-half-even to cents:** fine as a stated policy. Make sure it runs on decimal amounts, not binary floats, or half-cent ties may not round as intended. That is an implementation note, not a flaw in the plan.
- **Batches of 500 in no particular order:** fine, as long as each record is handled independently and totals are summed without depending on order. Nothing in the plan suggests otherwise.
