# Review: Nightly Compaction Plan

The plan is internally consistent. It doesn't promise that compaction finishes within 30 minutes. It promises that compaction either finishes or gets cancelled and reported. Both outcomes are handled, and none of the plan's stated rules is at risk of being broken.

**Feasibility.** To finish, the job needs about 22 MB/s sustained (40 GB in 1,800 s). That is modest for a single thread on typical server hardware, so completion is plausible. Because throughput hasn't been measured, this can't be confirmed. If the host turns out slower, the plan's cancel-and-report path covers it, so this is a risk rather than a defect.

**Checks against the plan's own rules:**
- **30-minute window:** enforced by cancellation. ✔
- **Overrun handling:** cancellation is reported. ✔
- **Single thread:** stated and nothing conflicts with it. ✔
- **Progress logging every minute:** about 30 log lines per run, with nothing in conflict. ✔

**Optional suggestions** (these add robustness and are not required):
1. **Measure throughput** on the target host with a representative sample, or record bytes processed in the per-minute progress log. You'd then know your margin within the first night or two.
2. **Clarify what cancellation leaves behind.** Is the output from a cancelled run discarded or resumable, and is the input left intact? If every run is cancelled and nothing is kept, compaction would never complete. Adding checkpoint/resume, or an alert after N consecutive cancellations, would catch that.
3. **Consider multithreading** if measurements show the margin is thin.
