# Plan Review: Scratch Directory Cleanup Under /var/cache/app

## Does the plan meet its stated rule?

The rule is that a run may delete only the scratch directories it created itself. The plan satisfies it.

- **Ownership comes from a per-run identity.** Each run generates a fresh random UUID and tags every directory it creates with it. Cleanup selects only directories whose tag equals that UUID.
- **Concurrent runs can't select each other's directories.** Several runs can be active at once, but each holds a different UUID. A random v4 UUID has 122 bits of randomness, so a collision is not a practical concern. No run can match another run's tag.
- **Selection is by exact equality.** It doesn't use path prefixes, timestamps, or name patterns, which could overlap between runs.
- **Permissions work.** The service account that created the directories is the one that deletes them, so it has the access it needs without elevated privileges.
- **`rm -rf` stays within the selected directory.** It doesn't follow symlinks inside the tree, so a link inside a scratch directory can't cause deletion outside it.
- **The logging is useful.** Recording the tag and path for each deletion gives an audit trail showing that only the run's own UUID was ever removed.

## Optional hardening (not required for correctness)

1. **Orphaned directories.** If a run crashes or is killed before cleanup, its directories stay forever, because no later run will ever have that UUID. A separate reaper could remove directories whose run is known to have finished, for example with a heartbeat or lock file per run plus an age threshold. Leaking space doesn't violate the deletion rule.
2. **Tag immediately on creation.** Write the tag (a marker file or xattr) right after `mkdir`, before filling the directory. Otherwise a crash between the two leaves an untagged directory that nothing will claim. This also only leaks space.
3. **Choose a durable tag mechanism.** A marker file inside the directory is simplest and most portable. Xattrs can be lost on some filesystems or copy paths.
4. **Remove only top-level entries.** Restrict cleanup to direct children of `/var/cache/app` and skip any selected path that is itself a symlink. This guards against a future change nesting directories or adding links.
5. **Generate the UUID from a strong source.** Use `uuidgen -r` or `/proc/sys/kernel/random/uuid` rather than something time-based.

None of these is needed for the plan to work or to follow its rule. They only make it more robust.
