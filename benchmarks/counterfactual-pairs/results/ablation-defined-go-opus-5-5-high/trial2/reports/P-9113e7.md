## Review

**The plan does not fit its own 45-minute deadline.**

Sequential stage timings, as stated in the plan:

| Stage | Typical | Max (last 30 runs) |
|---|---|---|
| 1. Import | 22 min | 25 min |
| 2. Transform | 18 min | 21 min |
| 3. Export | 12 min | 14 min |
| **Total** | **52 min** | **60 min** |

The stages never overlap, so total runtime is the sum. A *typical* run takes 52 minutes, 7 minutes over the hard limit. A worst-case run takes up to 60 minutes. The plan says an overrunning batch is killed and that day's data is lost, so as written the batch will be killed nearly every night. Even the fastest plausible run would need every stage to beat its typical time by a combined 7+ minutes.

**Secondary issue:** The summary email is sent "when the batch ends." If the batch is killed at 45 minutes, it may never reach a normal end, so on-call might never hear about the data loss. Check that a killed run still triggers an alert.

**What would need to change:**
- Cut total runtime well under 45 minutes, with margin over the 60-minute worst case. Options include overlapping or pipelining stages (for example, starting transform on chunks as import produces them), parallelizing within stages, or optimizing the slowest stage (import).
- Or renegotiate the deadline, or split the batch across windows.
- Make sure a failure or kill is reported to on-call, not only a clean finish.
