# Plan Review: Scratch Directory Cleanup Under /var/cache/app

**The plan meets its stated rule.** Each run gets a fresh random UUID and deletes only directories tagged with that UUID. Another run's directories carry a different UUID, so they are never selected, even when several runs are active at once. UUID collisions are negligible in practice.

**Checks on the mechanics:**
- **Concurrency:** Selection is by exact tag match. It does not use timestamps, name prefixes, or "anything older than X", so overlapping runs cannot claim each other's directories.
- **rm -rf behaviour:** `rm -rf` on a directory does not follow symlinks inside it. A symlink in a scratch tree that points elsewhere is removed, not traversed. The target of each deletion is a directory the run created itself.
- **Privilege:** Running as an unprivileged service account limits the damage if something goes wrong.
- **Auditability:** Logging the tag and path for each deletion makes it easy to verify after the fact that only the run's own directories were removed.

**Optional hardening:**
1. **Crashed runs:** If a run dies before cleanup, its directories stay behind permanently. You could add a separate, explicitly authorized janitor process with its own rules, but that is outside this plan's scope and rules.
2. **Tag storage:** Store the tag somewhere tamper-resistant and record it at creation time. For example, the run could keep its own list of created paths and check that list against the tag before deleting. This protects against a corrupted or copied tag file causing a mis-selection.
3. **Path sanity check:** Before each `rm -rf`, confirm the resolved path is a real directory directly under /var/cache/app and not a symlink. This guards against bugs that produce an empty or wrong path.
4. **Use `--`:** Call `rm -rf -- "$path"` and quote the path, so odd directory names cannot be read as options.

None of these are needed for the plan to work or to follow its rule.
