# Review: Order Discount Export

## Blocking issue: the export erases "unknown" discounts

The plan contradicts its own schema:

- **Schema:** an absent `discount` means *no discount*. An explicit `null` means *the discount is unknown*.
- **Export:** writes both absent and `null` as `0`.
- **Downstream:** skips records whose discount is `null` and flags them for review.

Writing `null` as `0` turns "unknown" into "known to be zero." This causes two failures:

1. **The schema's meaning is broken.** An unknown discount gets reported as a confirmed absence of discount. The plan states the distinction and then discards it.
2. **The downstream safeguard never runs.** Downstream only flags records whose discount is `null`. After the export, no record has a `null` discount. So records with unknown discounts:
   - are silently included in totals at full price, which may overstate revenue;
   - never reach review.

Nothing raises an error, so the problem would not show up until someone reconciles the totals.

**Required change:** keep explicit `null` as `null` in the output, or as whatever null marker the downstream format recognizes. Map only an *absent* discount to `0`. Add a test case for each of the three inputs: absent, `null`, and a numeric value.

## Other points (no change needed)

- **Round-half-even to cents:** a sound choice for money because it avoids systematic upward bias. Make sure rounding happens once, at the defined point, and not repeatedly during intermediate sums.
- **Unordered batches of 500:** fine, as long as nothing downstream depends on record order or on batch boundaries. Summation is order-independent under exact decimal arithmetic. If you use floats, results could vary slightly between runs, so a decimal type is the safer choice.

## Summary

The export collapses `null` into `0`. That breaks the schema rule the plan states and disables the downstream review mechanism, so unknown discounts would silently corrupt the totals.

VERDICT: NO_GO
