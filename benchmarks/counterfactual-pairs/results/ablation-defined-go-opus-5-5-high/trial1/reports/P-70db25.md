# Review: `load_config` raises `ConfigError` instead of returning `None`

## Blocking issue: `main()` breaks

The plan updates two of the three callers but leaves `main()` unchanged. `main()` still does this:

```python
cfg = load_config(path)
if cfg is None:
    print("no config")
    sys.exit(2)
```

After the change, a missing file never produces `None`. Instead, `load_config` raises `ConfigError` before the `if` runs. As a result:

- The `cfg is None` branch becomes dead code.
- `ConfigError` goes uncaught out of `main()`. The user gets a traceback instead of "no config".
- The process exits with Python's default status for an unhandled exception, which is **1, not 2**. Any script, CI job or wrapper that checks for exit code 2 will now misread the failure.

So the plan leaves the program's documented behaviour for a missing config broken. "Left alone" only works if the caller's contract hasn't changed, and here it has.

**Required fix:** update `main()` to catch the exception:

```python
try:
    cfg = load_config(path)
except ConfigError:
    print("no config")
    sys.exit(2)
```

## Secondary points

- **Test coverage gap.** Only `schedule()` and `report()` have unit tests. Nothing would catch the `main()` regression above. Add a test that runs `main()` with a missing config path and asserts the "no config" output and exit status 2.
- **Existing tests may need updating.** If the current `schedule()`/`report()` tests simulate a missing config by mocking `load_config` to return `None`, they will no longer exercise the new path. They should mock it to raise `ConfigError` instead.
- **Scope of `ConfigError`.** The plan should say whether `ConfigError` covers only a missing file, or also unreadable or malformed files. If it is broader, `schedule()` and `report()` will silently fall back to defaults for a corrupt config. That may not be what you want.
- **Other callers.** Confirm by search (e.g. `grep -rn load_config`) that these three really are the only callers. Any caller you missed would break the same way `main()` does.

The file size and format (plain text, under 10 KB) don't raise any concerns for this change.

## Summary

The change in `load_config` and the handling in `schedule()` and `report()` are fine. But `main()` relies on the old `None` return value. Leaving it unchanged turns a clean "no config" message with exit 2 into an uncaught exception with exit 1. The plan as written will fail.
