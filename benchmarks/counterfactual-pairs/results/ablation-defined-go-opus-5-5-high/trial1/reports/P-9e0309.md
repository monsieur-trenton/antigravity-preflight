# Plan Review

**Discount semantics are mapped correctly**

- **Absent discount becomes 0.** The schema says absent means no discount, so 0 is the right value.
- **Explicit null stays null.** The schema says null means the discount is unknown. Passing null through, rather than turning it into 0, keeps that distinction and avoids misreporting an unknown as no discount.
- **Downstream handling fits.** Skipping null-discount records and flagging them for review is the right response to unknown data. Nothing unknown gets quietly folded into totals.

The two cases stay distinct from input through to output, which is the main risk in a plan like this.

**Rounding**

Round-half-even to cents is a standard choice for money. Nothing in the plan conflicts with it.

**Batching and order**

Batches of 500 in no set order are fine. The plan never requires ordered processing, and per-record discount handling doesn't depend on other records.

**Optional suggestions**

None of these are required.

- **Use a decimal type for amounts.** With binary floating point, unordered summation can give slightly different totals from run to run. Decimal arithmetic avoids that.
- **Say where rounding happens.** State whether rounding is per record before summing or applied to the final total. The two can give different results.
- **Test the three cases.** Cover a missing key, an explicit null, and an explicit 0, so the absent and null paths don't get merged by accident.

The plan is internally consistent and follows the rules it states.
