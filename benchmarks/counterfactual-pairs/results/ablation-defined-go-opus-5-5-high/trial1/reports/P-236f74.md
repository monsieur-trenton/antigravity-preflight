# Review: Nightly Compaction Plan

The plan is internally consistent and doesn't break any rule it states. I'd approve it as written.

## Feasibility

- **Required throughput:** 40 GB in 30 minutes needs about **22 MB/s sustained** (40,000 MB ÷ 1,800 s).
- **Single thread:** 22 MB/s is a modest rate for single-threaded compaction on typical server hardware. The plan is not infeasible on its face.
- **Unmeasured throughput:** this is a real unknown, but the plan already handles it. If the host is too slow, the window runs out and the step is cancelled and reported, as the plan specifies. A slow host produces the designed outcome, not a broken run.

## Rule consistency

| Stated rule | Does the plan satisfy it? |
|---|---|
| 30-minute work window | Yes, enforced by cancellation. |
| Cancel and report on timeout | Yes, it is the defined overrun behaviour. |
| Single thread | Yes, nothing conflicts with it. |
| Log progress every minute | Yes, about 30 log lines per run, nothing conflicting. |

None of the rules contradict each other, and nothing guarantees failure.

## Optional suggestions (not required)

These would make the plan more robust, but it works without them:

1. **Measure throughput once on the target host.** A short benchmark would show whether nightly runs will usually finish or usually cancel.
2. **Include progress in the cancellation report.** For example, bytes processed or percent done, taken from the per-minute log. Repeated near-misses would then be easy to spot.
3. **State what cancellation leaves behind.** Say whether a cancelled run leaves the data unchanged, or leaves resumable partial output. This is probably covered by the compaction tool, but writing it down helps operators.
4. **Alert on repeated cancellations.** If the step cancels several nights in a row, compaction is effectively not happening, and someone should hear about it.

VERDICT: GO
