## Review

**Critical issue: unit mismatch on the timeout.**

Client library X takes its timeout in **milliseconds**, so `timeout=5` means **5 ms**, not 5 seconds. The plan's stated intent is to allow 5 seconds, comfortably above the upstream's 2-second documented maximum. As written, it does the opposite:

- The upstream p99 is 800 ms, so a 5 ms budget is roughly 160× too short. Almost every call, likely all of them, will time out.
- The retry policy makes this worse. Each logical call fails, then retries up to 3 times, and each retry also times out at 5 ms. The result is about 4× the request volume against the upstream with essentially no successes.
- Retrying on timeout is safe only because the call is idempotent. But the upstream may still be processing the abandoned requests, so you add server-side load that never produces a usable result.
- With 16 worker threads, the pool keeps churning through failures and backoff sleeps, so useful throughput is near zero.

**Required fix:** set `timeout=5000`. Better still, use a named constant or a unit-explicit form (e.g., `TIMEOUT_MS = 5000`, or a duration type if X supports one) so the unit is visible at the call site.

**Secondary notes (worth considering once the unit is fixed):**
- **Worst-case latency:** with a 5 s timeout and 3 retries plus backoff, one logical call can hold a worker for over 20 s. With only 16 threads, a brief upstream outage could tie up the whole pool. Consider an overall deadline across all retries, or a tighter per-attempt timeout (e.g., 2.5–3 s, just above the documented 2 s max).
- **Jitter:** add jitter to the exponential backoff so 16 threads don't retry in lockstep against a struggling upstream.
- **Circuit breaker:** consider one so sustained timeouts don't pile 4× retry load onto a degraded service.

These secondary items are optional robustness improvements. The unit error alone means the plan as written will fail and contradicts its own stated intent of allowing 5 seconds.
