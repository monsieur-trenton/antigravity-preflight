# Review: orders.shipped_at migration

## Blocking issue: the steps run in the wrong order

The plan says the steps run in the order **1 → 3 → 2**:

1. **Step 1** adds `shipped_at` as nullable. All ~2 million existing rows get `NULL` in the new column.
2. **Step 3** then adds `NOT NULL` to `shipped_at`. The database checks existing rows when it adds the constraint. Every row is still `NULL`, so this step **fails**. On PostgreSQL, for example, you get `column "shipped_at" contains null values`.
3. **Step 2**, the backfill from `shipments`, never runs.

The rollback then drops the column. So the migration leaves the schema unchanged and wastes the maintenance window.

**Fix:** run the steps as **1 → 2 → 3**: add the nullable column, backfill it, then add `NOT NULL`. In that order the constraint holds, because the plan says `shipments` has a non-null `shipped_at` for every order.

## Other things to consider (not blocking)

- **Check the backfill before adding the constraint.** Run something like `SELECT count(*) FROM orders WHERE shipped_at IS NULL` after step 2. This catches the case where the claim that every order has a shipment turns out to be false. A plain `UPDATE ... FROM shipments` silently skips orders with no shipment row.
- **Multiple shipments per order.** If `shipments` can have more than one row per order, the `UPDATE ... FROM` join picks an arbitrary one. Decide which value you want (e.g., `MIN(shipped_at)`) and write the query to choose it.
- **Locks and duration.** Updating 2 million rows in one statement holds row locks, creates table bloat, and produces a lot of WAL. Batching the update or running `VACUUM` afterward may help. On PostgreSQL, you can avoid a long exclusive lock in step 3 by adding `CHECK (shipped_at IS NOT NULL) NOT VALID`, then `VALIDATE`, then `SET NOT NULL`.
- **Rollback.** Dropping the column is a fine rollback for this change. Make sure the script works no matter which step failed, for example by using `DROP COLUMN IF EXISTS`.

## Summary

As written, step 3 adds a `NOT NULL` constraint before step 2 has filled the column. The constraint will fail on all ~2 million existing rows, so the migration will fail.

VERDICT: NO_GO
