# Review: `orders.shipped_at` migration

The plan works as written. Each step's precondition is met by the step before it:

1. **Add nullable column.** This is safe on populated tables. Existing rows get NULL, which is allowed.
2. **Backfill from shipments.** You state that shipments holds a non-null `shipped_at` for every order. So after this step, no row in orders has a NULL `shipped_at`.
3. **Add NOT NULL.** This succeeds because step 2 left no NULLs. The steps run strictly in order, so step 3 never sees a partly filled column.

**Rollback.** Dropping the column fully undoes steps 1–3 at any point of failure. The column is new, so no existing data is lost.

**Scale.** About 2 million rows in a maintenance window is a modest backfill. Running it as one `UPDATE … FROM shipments` is reasonable when writes are paused.

## Optional suggestions

None of these is needed for the plan to work.

- **Multiple shipments per order.** If an order can have more than one shipments row, the `UPDATE … FROM` join picks an arbitrary row's value. If that's possible, choose one deterministically, for example `MIN(shipped_at)` or `MAX(shipped_at)`.
- **Pre-check before step 3.** Running `SELECT count(*) FROM orders WHERE shipped_at IS NULL` gives a clear diagnostic if the data assumption is ever wrong. Without it, you only learn from a constraint failure.
- **Index on `shipments.order_id`.** If one doesn't exist, the join may be slow at 2M rows.
- **Writes after the window.** Once NOT NULL is in place, every new order must be inserted with a `shipped_at`. Make sure the application does this when the window closes, especially for orders that haven't shipped yet.
- **Batching.** If the window is tight or lock time matters, a batched backfill reduces lock duration and WAL/undo pressure.
