# Review: orders.shipped_at migration

## Does the plan work as written?

Yes. The three steps are ordered correctly for adding a required column to a populated table:

1. **Add a nullable column.** This succeeds on a populated table because no default is needed.
2. **Backfill from shipments.** The plan states that every order has a non-null `shipped_at` there, so every row in `orders` gets a value.
3. **Add NOT NULL.** After a complete backfill there are no nulls left, so the constraint validates.

The plan also covers the other risks:
- **Concurrent writes:** The maintenance window rules out new rows arriving between steps 2 and 3.
- **Failure:** The rollback script returns the table to its original state if any step fails.
- **Table size:** At 2 million rows, a single-pass backfill fits comfortably in a maintenance window.

Nothing in the plan breaks a rule it states or will fail under its own premises.

## Optional suggestions

None of these are required.

- **Verify the premise before step 3.** Run `SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL`. This turns a mid-migration constraint failure into a clean stop.
- **Handle multiple shipments per order.** If an order can have more than one shipment, the backfill should pick one explicitly, for example with `MIN(shipped_at)`. Otherwise a correlated subquery may error or pick a value arbitrarily.
- **Check what writes to orders after the window.** Once the constraint is in place, any code path that inserts an order before it ships will fail. Confirm that the application always supplies `shipped_at`, or that the business meaning really is "every order has shipped."
- **Batch the backfill, optionally.** Updating in chunks would shorten lock duration and reduce WAL/undo pressure. At this size it is not necessary.
