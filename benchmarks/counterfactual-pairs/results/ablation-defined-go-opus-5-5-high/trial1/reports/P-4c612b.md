# Plan Review

## Critical flaw: the loop covers the wrong set of sources

The plan states that **all four supplied sources must appear in the report exactly once**. The checker rejects any report whose covered sources differ from the supplied inventory.

The generation step, however, **loops only over sources touched by the diff**. The plan itself says a typical diff changes only one or two of the four sources. So in the common case:

- The report covers 1–2 sources instead of 4.
- The covered set doesn't match the supplied inventory, so **the checker rejects it**.
- The report is labelled **INCOMPLETE** and **cannot be recommended for readiness**.

The plan fails in its normal, expected case, not just in an edge case. It only passes when a diff happens to touch all four sources.

## Required fix

Iterate over the **supplied source inventory**, not the diff:

1. Build the section list from the full inventory of four sources, de-duplicated so each appears exactly once.
2. For each source, write its section with its SHA-256 and line count, computed from the current file contents whether or not the diff touched it.
3. Optionally, use the diff only to annotate sections (e.g. "changed in this diff" / "unchanged").
4. Before submitting, check that the set of covered sources exactly equals the supplied inventory, with no omissions or duplicates.

## Minor notes (not blocking on their own)

- State how the SHA-256 and line count are computed: raw bytes vs. normalized line endings, and whether a trailing newline counts as a line. This avoids mismatches if the checker validates these values.
- Order sections deterministically, e.g. in inventory order, so reports are reproducible.

## Summary

As written, the plan builds a report from diff-touched sources only. In the typical case that omits sources, so the report is rejected and marked INCOMPLETE, which breaks the plan's own rule. It needs to iterate over the full inventory before it can work.
