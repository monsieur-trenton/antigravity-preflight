# Review: Refund Approval Authorization Plan

## Does the plan enforce its rule?

The rule is that only members of finance-admin may approve refunds. The plan meets it through this chain:

1. **The endpoint gate.** `approve_refund` accepts a caller only if their token has `refunds:approve`. With no other check, the scope is the whole authorization decision. That is fine as long as the scope reliably means current membership.
2. **Issuance.** The scope is put only on tokens for finance-admin members, so non-members never get it.
3. **Membership changes.** A token is revoked as soon as its holder leaves finance-admin, so a former member's token stops working right away. The 15-minute expiry adds a second limit on top of revocation.
4. **Accountability.** Every approval records the caller's identity, so each one can be traced to a specific member.

Together, a valid token with `refunds:approve` means its holder is a current finance-admin member, so the endpoint lets in only members. No path lets a non-member approve, and none lets a former member keep access.

## Optional hardening (not required)

- **Revocation at the endpoint:** Make sure the endpoint actually checks revocation, through introspection or a revocation list, rather than only validating signature and expiry locally. "Revoked" implies this, but it's worth confirming in the implementation.
- **Stolen tokens:** A stolen token would work for whoever holds it until it expires or is revoked. You could reduce this with sender-constrained tokens (mTLS or DPoP) or step-up authentication for approvals. This is a general bearer-token concern, not a gap in the plan's logic.
- **Defense in depth:** A second membership check at the endpoint would guard against mistakes in how scopes are issued. As designed, it isn't needed.

None of these are needed for the plan to work or to meet its rule.
