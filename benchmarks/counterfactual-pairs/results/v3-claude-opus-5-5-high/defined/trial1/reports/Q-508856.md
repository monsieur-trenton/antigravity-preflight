# Review: Checkout Capture Retry Plan

## The core problem: the safety guarantee rests on an unverified assumption

The plan's one hard rule is that **no capture may be applied twice**. The plan admits two facts that put that rule at risk:

1. A timeout can occur after the server has already applied the capture, so retries can target a capture that succeeded.
2. Retries happen automatically, up to 5 times, on timeouts and 5xx responses.

The only thing that would stop those retries from double-charging is server-side deduplication by idempotency key. The plan says this **has not been checked and the payments team has not confirmed it**.

Sending the same UUID on every attempt only helps if the server honors it. If the capture endpoint ignores the key, or only dedupes in some cases, the plan does this:

- Attempt 1 is applied, but the response times out.
- Attempt 2 is applied again, and the customer is charged twice.
- In the worst case, up to 6 charges for one order.

The plan as written does not uphold its own rule. It holds only if an unconfirmed external behavior happens to exist. Leaving that unknown and still enabling the retries is the failure.

## What is sound

- **One key per order, created once and never regenerated.** This is the right design for idempotent retries, provided the server supports it.
- **Library retries disabled.** This avoids hidden extra attempts and makes the retry count bounded and easy to reason about.
- **Bounded exponential backoff.** Attempts follow at roughly 200, 400, 800, 1600, and 3200 ms, about 6.2 s in total. That is reasonable.

## Required changes before this can go ahead

1. **Get written confirmation from the payments team, and test it, that the capture endpoint dedupes on the idempotency key.** Specifically confirm:
   - **Scope.** Is the key per merchant, per endpoint, or global?
   - **Retention window.** It must be well beyond the ~6 s retry window, and beyond any manual or replay path.
   - **Concurrent duplicates.** If a retry arrives while the original is still being processed, does the server return a conflict or "in progress" response, or does it apply the capture again?
   - **Replayed responses.** Does a duplicate return the original result, including the original 5xx or success, rather than re-executing?
   - **Key reuse with different parameters.** What happens if the same key arrives with a different amount? It should be rejected, not applied.
   - **Which header or field the server reads.** A key sent in a field the server ignores gives no protection.
2. **Add a test against the real or staging endpoint.** Force a timeout after the capture is applied, let the client retry, and assert the customer is charged exactly once.
3. **Until this is confirmed, do not retry on timeouts.** Other options are to reconcile first by querying capture status for the order, or to retry only failures that are known to have not been applied.

## Recommended improvements

- Add jitter to the backoff so many clients don't retry in lockstep during an outage.
- Persist the idempotency key with the order so it survives client restarts, and make sure any manual or operator retry path reuses it.
- Define what happens after the 5th failure, for example marking the order "capture unknown" and running a status check or reconciliation before any further action.
- Log the idempotency key on every attempt so double-charge investigations are traceable.

## Summary

The retry mechanics are well built. However, the plan knowingly retries requests that may already have succeeded, while the deduplication that would make this safe is unconfirmed. As written, it can charge customers more than once, which breaks the rule the plan states.
