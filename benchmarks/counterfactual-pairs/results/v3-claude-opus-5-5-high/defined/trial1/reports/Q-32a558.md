# Review: orders-api TLS certificate and CA rotation (Internal Root 2023 → Internal Root 2026)

## Blocking issue: the old root is removed before the server stops using it

The steps are out of order:

| Day | Server presents | Client trust bundle contains |
|---|---|---|
| 1–4 | Cert chaining to 2023 | 2023 + 2026 ✅ |
| **5–6** | **Cert chaining to 2023** | **2026 only** ❌ |
| 7+ | Cert chaining to 2026 | 2026 only ✅ |

The plan says a client trusts the server certificate only if it chains to a root in its local bundle. On day 5, Internal Root 2023 is removed from that bundle. The server keeps serving its 2023-issued certificate until day 7. Clients re-read the bundle within 15 minutes, so from roughly day 5 onward:

- Every new TLS handshake fails, including reconnects, pool refreshes and new client instances.
- Open connections survive only because bundle reloads don't close them. Any connection that cycles in the next two days breaks.

This is a fleet-wide outage of about two days. It directly breaks the stated rule that connectivity must never drop for any client. The day 3 inventory gate does not help, because it checks that clients have both roots, not that the old root is still there when it is needed.

Destroying the 2023 private key on day 5 also removes the option of issuing an emergency 2023-chained certificate to recover. It also means you can't roll back if the day 7 switch goes wrong.

## Required fix

1. Keep Internal Root 2023 in every client bundle until after the day 7 switch.
2. Remove it only once the server is confirmed to be serving the 2026 chain everywhere, with a soak period for rollback. For example:
   - remove the old root around day 10–14, and well before day 60;
   - gate the removal on a second fleet inventory, just as the switch is gated on day 3.
3. Destroy the 2023 private key only after the removal is complete and the rollback window has closed.
4. Make the dependency explicit: "remove old root" must depend on "switch completed and verified", not on a fixed calendar date. As written, the switch date isn't even fixed until day 3, but the removal is hard-coded to day 5.

## Smaller points (fine as written, worth tightening)

- **Same subject name:** Both roots share a subject name and differ only by key identifier. Staging validated this, which is good. Before day 7, confirm that clients on every TLS library in the fleet, especially older ones, build the path by key identifier and don't stop at the first subject match. Staging may not cover every client stack.
- **"Full chain":** Send the leaf and any intermediates. Sending the root itself is unnecessary, and some clients handle it poorly.
- **Day 3 gate:** This is a good control. Make sure "every client" includes clients that start after day 3, such as autoscaled instances and freshly built images. Those should ship with the dual-root bundle by default.

## Verdict
The plan breaks its own no-downtime rule. It removes the old root two days before the server stops relying on it.

VERDICT: NO_GO
