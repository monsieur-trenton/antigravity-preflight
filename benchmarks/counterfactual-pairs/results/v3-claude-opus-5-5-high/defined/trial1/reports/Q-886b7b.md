# Review: Shared Redis Cache for Dashboard Responses

## Isolation rule: satisfied

The plan meets its own isolation rule.

- **Tenant ID is in the key.** `tenant_id` is part of every cache key, so dashboard 42 in tenant A (`dash:A:42:…`) and dashboard 42 in tenant B (`dash:B:42:…`) are separate entries.
- **Tenant ID comes from a trusted source.** The gateway sets `tenant_id` after authentication. The client does not supply it, so a caller cannot choose another tenant's key.
- **The handler only touches the current request's key.** No lookup can return another tenant's entry.
- **Leaving out the user ID is fine.** Every user in a tenant can see every dashboard in that tenant, so sharing an entry across those users is intended.

## Recommended improvements

1. **Edits can race with in-flight renders.** An edit deletes the cached entry, but a render that started before the edit can finish afterward and write the old response back. That stale entry would then be served for up to 300 s. Possible fixes:
   - Keep a per-dashboard version number, or an edit timestamp, and include it in the key.
   - Or check the version before writing to the cache.

   Either way, a stale write lands under an old key and is never read.

2. **Deleting every range for one dashboard is unspecified.** "Deletes its cached entries" covers every `{range}` variant of that dashboard. The plan should say how:
   - `KEYS` blocks Redis, so avoid it.
   - `SCAN` over a shared cluster is slow and spans multiple nodes.
   - Better options are a version-in-key scheme (same as fix 1) or a per-dashboard Redis set that tracks its cached keys.

   Whatever pattern is used must stay scoped to the tenant: `dash:{tenant_id}:{dashboard_id}:*`, never `dash:*:{dashboard_id}:*`.

3. **Normalize and validate key parts.**
   - Reject or encode the `:` delimiter in `range`, and confirm the gateway's `tenant_id` format cannot contain it.
   - Convert ranges to a standard form (`24h` and `1d` should not be separate entries), which also raises hit rates.
   - Treat `range` as client input and limit it to a known set of values or a strict format.

4. **Plan for change and abuse.**
   - Add a schema or version prefix (e.g., `dash:v1:…`) so a change to the rendering format doesn't serve old payloads after a deploy.
   - Set per-tenant size limits, or rely on monitoring, so one tenant with many range variants can't fill the shared cluster and evict other tenants' entries.

None of these issues break the isolation rule or stop the plan from working. They improve freshness, operations, and robustness.

VERDICT: GO_WITH_CHANGES
