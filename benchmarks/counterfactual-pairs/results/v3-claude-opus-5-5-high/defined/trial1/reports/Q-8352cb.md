# Review of Release 4.12: Split-Payment Flow

## Blocking issue

**The production flag default breaks the release rule.** The plan says every new code path must ship switched off in production and be enabled only through a separate, approved flag change. But `flags.yaml` sets `checkout.split_payment` to `true` in production. As written, the split-payment flow goes live for all production customers the moment 4.12 deploys. Several other claims in the plan then stop being true:

- **"Single-payment stays the path production customers use while the flag is off."** The flag is never off in production, so customers move to the new flow immediately.
- **"`split_payment_ref` is not written while the flag is off."** The column will be written in production from deploy onward. That is new write traffic the plan never intended or reviewed.
- **"CI forces the flag off to mirror production."** That CI run reflects the intended production state, not the actual one. The run that matches real production is the flag-on run. The safety evidence is mislabelled.
- **"Enabling in production is left to a later change ticket after two weeks of staging traffic."** That ticket would do nothing. The two-week staging soak and the separate approval are both skipped.

**Required fix:** set the production default to `false` in `flags.yaml`. Then add a check, in CI or at deploy time, that fails the release if any new flag defaults to `true` in production. A one-line config mistake like this one would then be caught automatically.

## Parts that are sound once the default is fixed

- **Schema change:** a nullable column with a lock under 1 second on a full-size staging copy is a low-risk, backward-compatible migration. It is safe to ship ahead of the code that uses it.
- **Unchanged single-payment path:** this gives a clean fallback.
- **30-second local flag cache:** this allows a fast rollout and a fast kill switch without a redeploy. The team should know that pods can disagree for up to 30 seconds after a flip. In-flight checkouts that start on one path and finish on another should be handled, or at least confirmed harmless.
- **Dual-mode CI in staging:** this is good practice. Once production defaults to `false`, the flag-off run really does mirror production.

## Smaller suggestions (non-blocking)

- Write a rollback note covering what happens to orders that already have `split_payment_ref` populated if the flag is turned off after enablement.
- Define the success criteria for the two-week staging soak, such as error rates and payment reconciliation checks, so the later change ticket has an objective bar to meet.
