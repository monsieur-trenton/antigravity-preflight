# Review: Address Backfill Rate-Limiting Plan

## The blocking problem: worker caps add up to more than the contract allows

- 12 workers × 5 requests/second = **60 requests/second** possible combined.
- The contracted ceiling is **50 requests/second**.

The workers don't coordinate, so nothing stops all 12 from using their full allowance in the same second. Healthy workers will each try to run at their cap, so this will likely happen early and often. Going over in any one-second window suspends the key for 24 hours, which also takes down live checkout address lookups.

The rest of the plan is sound but cannot close this gap:
- The fixed worker count keeps the maximum at a predictable 60.
- Charging retries against each worker's own limiter keeps each worker at 5/s, but 5/s per worker is already too much.
- Having no other users of the key removes outside traffic but doesn't change the math.

## Required changes

1. **Lower the per-worker cap so the total stays below 50, with margin.**
   - 4 req/s per worker gives 48 req/s total. That is under the limit, but only by 2.
   - 3 req/s per worker gives 36 req/s total. This is safer because of timing effects (see point 2).
   - Or use a **shared limiter** (for example, a token bucket in Redis) set to about 40–45 req/s.

2. **Leave room for timing differences.** Each worker counts its own one-second windows on its own clock. The vendor counts requests as they arrive. Network delays, connection pooling and retries can bunch requests together, so a window that looked compliant on the client can look over the limit to the vendor. Aim for about 80–90% of the contract (40–45 req/s), not 98%.

3. **Back off on HTTP 429 and 500 errors.** Use exponential backoff with jitter on failures. Stop or slow down all workers if 429s appear, since they may warn that suspension is close. Find out whether the vendor sends 429s before suspending.

## Other points

- **Possible contradiction about the key.** The plan says no other service uses the key during the backfill, yet a suspension would halt checkout lookups. That suggests checkout normally shares this key. Confirm whether checkout traffic is truly paused during the backfill. If checkout keeps running on the same key, its traffic must also come out of the 50 req/s budget. A separate key for the backfill would be better: a suspension would then not affect checkout at all.
- **Expected run time:** 3.2M rows at 48 req/s takes about 18.5 hours. At 40 req/s it takes about 22 hours. Plan for retries on top of that, and make the job resumable, for example by tracking which rows are done.

## Summary

As written, the plan can send up to 60 req/s against a 50 req/s hard limit. That breaks its own stated requirement and risks a day-long checkout outage. Lower the per-worker rate or use a shared limiter, with safety margin, before running.
