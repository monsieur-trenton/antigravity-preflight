# Review: inventory service locking plan

**The plan cannot deadlock.**

## Lock ordering

| Path | Acquires | Holds while acquiring another? |
|---|---|---|
| Checkout handler | stock_mu → reserve_mu | Yes, holds stock_mu while taking reserve_mu |
| Restock worker | stock_mu → reserve_mu | Yes, holds stock_mu while taking reserve_mu |
| Nightly audit | stock_mu only | No |

A deadlock needs a cycle in the wait-for graph. That requires one thread to hold A and wait for B while another holds B and wait for A. Here:

- **Checkout and restock overlap often, but safely.** Both take stock_mu first. Whichever thread loses the race for stock_mu blocks before it holds anything. The winner can always go on to get reserve_mu, finish, and release both.
- **reserve_mu is only ever taken by a thread that already holds stock_mu.** So nobody can hold reserve_mu while waiting for stock_mu. That is the only edge that could close a cycle, and it never exists.
- **The audit holds one lock and waits for nothing while holding it.** It can't be part of a cycle. It only delays other threads, for at most 2 seconds.
- **No other code path touches either mutex.** The analysis above covers every acquisition site.

The missing acquisition timeouts don't matter for this requirement. Timeouts are a fallback for when ordering can't be guaranteed, and here the ordering is guaranteed.

## Notes that don't affect the verdict

- **Audit contention:** once a night, checkouts and restocks may wait up to 2 seconds behind the audit. This is a latency blip, not a stall. It only matters if checkout has a tighter latency budget.
- **The ordering is a convention:** "stock_mu before reserve_mu" holds today only because every call site follows it. A brief comment at the mutex declarations would help keep it that way as code changes. The current design does not need it to be correct.

The plan meets its stated requirement as written.
