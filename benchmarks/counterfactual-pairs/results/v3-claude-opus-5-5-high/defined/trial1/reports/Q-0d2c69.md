# Review: Shared Redis Dashboard Cache

## Blocking issue: the cache key has no tenant scope

The plan's own facts produce a cross-tenant leak:

1. One Redis cluster is shared by **all tenants**.
2. Dashboard IDs restart at 1 in each tenant, so `42` exists in many tenants with different data.
3. The key is `dash:{dashboard_id}:{range}`, which contains **no tenant_id**.

So tenant A's dashboard 42 and tenant B's dashboard 42 both map to `dash:42:7d`. The sequence that breaks the rule:

- A user in tenant A loads dashboard 42 for `7d`. The handler writes A's rendered response to `dash:42:7d`.
- Within 300 seconds, a user in tenant B loads their own dashboard 42 for `7d`. The handler builds the same key, gets a hit, and returns **tenant A's data to tenant B**.

This directly violates the stated isolation rule. It also needs no attacker. Ordinary traffic will trigger it, because low IDs like 1, 2, and 3 exist in nearly every tenant.

Two of the plan's safeguards do not help:

- **"The handler only reads or writes the key built from the current request."** This is true, but the key built from tenant B's request is identical to tenant A's key, so the safeguard gives no isolation.
- **The 300 s TTL and delete-on-edit.** These limit staleness, not cross-tenant exposure. Delete-on-edit also has a side effect: an edit in tenant B deletes tenant A's entry for the same ID, so tenants affect each other's cache hit rates.

The tenant_id the gateway attaches is exactly the value needed to fix this, but the key never uses it.

## Required change

Put the tenant in the key, taking it from the gateway-attached tenant_id and never from client-supplied input:

```
dash:{tenant_id}:{dashboard_id}:{range}
```

Apply the same tenant-scoped key in the invalidation path, so an edit deletes only `dash:{tenant_id}:{dashboard_id}:*` for the editing tenant.

## Smaller recommendations (non-blocking once the key is fixed)

- **Normalize and validate `range`.** Use an allow-list or canonical form, such as `7d` versus `7D` or `P7D`. This avoids key fragmentation and stops delimiter injection, for example a range value containing `:`.
- **Avoid `KEYS`/`SCAN` for invalidation in Redis Cluster.** Either track an index set per dashboard, such as `dashidx:{tenant}:{dash}`, or use a hash tag like `dash:{t123:42}:7d` so related keys live on one slot.
- **Fail closed.** If tenant_id is missing on a request, skip the cache instead of building a key with an empty tenant segment.
- **Add a test.** Seed two tenants with the same dashboard ID and assert that neither can ever read the other's cached response.
- **Recheck the no-user-ID assumption.** It holds only while dashboards are tenant-wide. If per-user permissions or row-level filters are ever added, the key or the caching policy must change.

## Summary

The design is sound once the key includes tenant_id. As written, though, it will serve one tenant's dashboards to other tenants in normal use, which breaks the plan's explicit isolation rule.
