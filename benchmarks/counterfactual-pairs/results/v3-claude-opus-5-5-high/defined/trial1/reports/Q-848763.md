**Review**

**The plan has a lock-ordering deadlock.**

- **Checkout** acquires `stock_mu`, then `reserve_mu`.
- **Restock** acquires `reserve_mu`, then `stock_mu`.

These are opposite orders, and the plan says both paths often run at the same time on separate threads. The failure sequence:

1. The checkout thread takes `stock_mu`.
2. The restock thread takes `reserve_mu`.
3. Checkout blocks waiting for `reserve_mu`, which restock holds.
4. Restock blocks waiting for `stock_mu`, which checkout holds.

Neither lock has a timeout, so neither thread ever recovers. Every later checkout and restock then piles up behind them. The pod still passes its liveness probe but sells nothing, which is exactly what the stated requirement forbids. With constant checkout traffic and a restock every 30 seconds, this is a matter of when, not if.

**The audit job is not a problem.** It holds only `stock_mu`, for at most 2 seconds, and requests no other lock. It cannot join a wait cycle. It only adds brief contention.

**Required changes**

1. **Use one global lock order** (the minimum fix). For example, always take `stock_mu` before `reserve_mu`. Change restock to acquire `stock_mu` first and then `reserve_mu`, matching checkout. Since no other code takes these mutexes, this removes the cycle completely. Document the order next to both mutex declarations.

2. **Optionally, use a single mutex.** Both write paths always need both locks, so a single `inventory_mu` may be simpler with little loss of concurrency. The audit would then take that lock. It holds it for at most 2 seconds a night, so that's probably acceptable, but confirm it.

3. **Optionally, add defense in depth:**
   - Use timed lock acquisition (`try_lock_for`) on the second lock, with back-off and retry or an error.
   - Add a readiness or liveness check that detects a stalled checkout path, so a future regression gets restarted automatically instead of waiting for an operator.

   These are safety nets only. They don't replace fix 1.

4. **Optionally, narrow restock's critical section.** Pruning expired reservations only touches reservation state, so consider doing it under `reserve_mu` alone, outside the dual-lock section.

As written, the plan will deadlock and violates its own stated requirement.
