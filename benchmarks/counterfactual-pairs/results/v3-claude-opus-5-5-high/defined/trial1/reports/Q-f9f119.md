# Review: unique constraint on `customers (tenant_id, email)`, release 4.12

## Blocking issue: the plan never checks for existing duplicates

Whether this migration succeeds depends on one fact nobody has checked: whether rows created before 4.9 contain duplicate `(tenant_id, email)` pairs.

- The 4.9 write path stops new duplicates. It does nothing about rows written earlier.
- If even one duplicate pair exists, `CREATE UNIQUE INDEX CONCURRENTLY` fails after scanning all 38M rows. It leaves behind an **INVALID** index named `customers_tenant_email_uq`.
- The constraint then can't be attached. Under the runbook, that aborts the release and 4.12 doesn't ship.

I can't say the migration will fail, because the data might be clean. I also can't say it works as written. Its success rests entirely on an untested assumption, and the cost of being wrong is the whole release. The check is cheap and the plan skips it, so I don't consider it ready to run.

**Required change:** before the release window, run a duplicate query against production or a fresh replica:

```sql
SELECT tenant_id, email, count(*)
FROM customers
GROUP BY tenant_id, email
HAVING count(*) > 1;
```

If it returns rows, you need a dedupe or merge plan, owned by product or support, before 4.12 can ship. Those accounts belong to real customers, so this can't be decided at migration time.

## Other issues (non-blocking)

1. **Retry path locking.** The plain `DROP INDEX IF EXISTS` does nothing on the first run. On a retry after a failed concurrent build, it would drop the INVALID index while holding an `ACCESS EXCLUSIVE` lock on `customers`. Use `DROP INDEX CONCURRENTLY IF EXISTS` instead.
2. **Transaction wrapping.** `CREATE INDEX CONCURRENTLY` can't run inside a transaction block. Confirm the migration tool runs this step outside a transaction, or it will error immediately.
3. **Attach step locking.** `ALTER TABLE ... ADD CONSTRAINT ... UNIQUE USING INDEX` takes a short `ACCESS EXCLUSIVE` lock. Set a `lock_timeout` so it doesn't queue behind long-running queries and block traffic.
4. **Email normalization.** Check that the 4.9 "already held" comparison uses the same equality as the index. If 4.9 compares case-insensitively but the index is case-sensitive, the sign-up code that relies on the constraint will behave differently from 4.9 for `Foo@x.com` vs `foo@x.com`. Decide whether you need `lower(email)` or `citext`.
5. **Rows written during the build.** Any write path that bypasses the 4.9 code, such as imports, admin tools or backfills, could add a duplicate while the concurrent build runs and fail it late. Confirm none are active during the window.

## Summary

The mechanics are mostly sound once items 1–3 are tightened. But the plan's success depends on an unverified data assumption, and a wrong guess aborts the release. Run the duplicate check and resolve any hits before going ahead.
