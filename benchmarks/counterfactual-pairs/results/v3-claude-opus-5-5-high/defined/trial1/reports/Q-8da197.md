# Review: orders-api TLS certificate and CA rotation

## Blocking issue: Root 2023 is removed before the server stops using it

The steps are listed out of order. Sorted by day:

| Day | Action | Server presents | Client bundle |
|---|---|---|---|
| 1 | Bundle becomes {2023, 2026} | 2023-issued | 2023 + 2026 |
| 3 | Inventory confirms both roots fleet-wide | 2023-issued | 2023 + 2026 |
| **5** | **Root 2023 removed from bundle; its key destroyed** | **2023-issued** | **2026 only** |
| 7 | Server switches to 2026-issued cert | 2026-issued | 2026 only |

On day 5 the server is still presenting its 2023-issued certificate. The plan says it keeps doing so "until the switch on day 7." Clients reload the bundle every 15 minutes, so within 15 minutes of the day-5 change, every client trusts only Root 2026.

- **What breaks:** For about two days, every new TLS handshake to orders-api fails chain validation. Existing connections survive only because the reload doesn't drop them. Any reconnect, pod restart, or connection-pool churn fails.
- **Rule broken:** This violates "no client may lose connectivity at any point."
- **Rollback is gone too:** The 2023 private key is destroyed the same day, so you can't issue a replacement 2023 certificate. You also can't go back to a 2023-only setup.

**Fix:** Remove Root 2023 from the bundle only after the day-7 switch has been confirmed. For example:

- **Day 7:** Switch the server to the 2026-issued certificate.
- **Day 7 to ~14:** Watch for handshake failures and confirm no endpoint or replica still serves the old certificate.
- **~Day 14 or later:** Remove Root 2023 from the bundle, still before its day-60 expiry. Re-check the fleet inventory, as on day 3.
- **After that:** Destroy the 2023 key only once removal is confirmed fleet-wide and the rollback window has closed.

## Other improvements

1. **Same subject name on both roots.** Chain building then depends entirely on Authority/Subject Key Identifier matching. Staging passed, which is encouraging. Still, confirm that every client TLS stack in production behaves the same way, especially older or non-standard ones. Some pick a candidate issuer by subject name and don't retry. Distinct subject names (for example, "Internal Root 2026") would avoid this risk on future rotations.
2. **"Full chain".** Send the leaf plus any intermediates. Including the root itself is harmless but unnecessary. If there are no intermediates, the "full chain" is just the leaf, so it's worth stating which one you mean.
3. **Day-7 gate.** Add an explicit go/no-go check before the switch: the day-3 inventory result plus a re-check on day 7. Clients added or rebuilt after day 3 might carry an old bundle.
4. **Every serving endpoint.** Make sure all orders-api replicas, load balancers, and any TLS-terminating proxies switch together, or at least that each one is tracked.
5. **Rollback plan for day 7.** Keep the 2023-issued certificate deployable until Root 2023 is removed. That way the switch can be reverted if a client class turns out to reject the 2026 chain.
