# Review: Nightly Compaction Job Plan

## The blocking issue: the 3-hour deadline is unverified

The plan's central rule is that every nightly run must finish inside the 01:00–04:00 window, because a killed run loses all its output. But the plan also says the job's throughput on a production-class host has never been measured. Nothing in the plan shows the job can meet its own hard requirement.

For scale, 1.3 TB in 3 hours needs about **120 MB/s sustained** for the whole run (1.3×10¹² B ÷ 10,800 s), with no margin. Compaction reads, merges, writes and checksums the data, so real disk traffic is at least twice the input size. That rate may be easy on this host or out of reach. The plan gives no way to tell.

I can't say the plan will definitely fail. But GO or GO_WITH_CHANGES would mean the plan works as written, and that can't be claimed while its one hard constraint rests on a missing number.

**Required change:** Benchmark the job on a production-class host using a real 1.3 TB day, with the actual nice and I/O class settings. Set a minimum margin, for example finishing in 2 hours or less, which leaves about 33% headroom.

## Secondary issues

- **Failed nights pile up.** The plan doesn't say what happens after a killed run. If the next night has to compact two days of data, a single overrun can keep failing every night after it.
- **No checkpointing.** Since a killed run discards everything, any overrun wastes the whole window. Committing work per segment, or making runs resumable, would greatly reduce this risk.
- **The idle I/O class is fragile.** Running at idle priority is fine only while the host really is quiet. An ad-hoc job, a late backup, or a rebuild could starve the job without anyone noticing. Monitor for this, or use best-effort low priority instead of idle.
- **Little slack after the backup.** The backup finishing by 00:45 leaves only 15 minutes. Make the job check that the backup has actually finished, rather than relying on the clock.
- **Volume growth.** The 90-day range of 1.0–1.3 TB is a snapshot. Add an alert when the daily volume or the runtime nears the window limit.

## What looks sound

- Deleting the old segments only after the new set is fully written and its checksums match the source is a safe ordering. You may still want to use a guarded path for `rm -rf`, and to log what gets deleted.
- Running nothing else on the host during the window, and the backup finishing before the job starts, are sensible choices, provided they are actually enforced.

VERDICT: NO_GO
