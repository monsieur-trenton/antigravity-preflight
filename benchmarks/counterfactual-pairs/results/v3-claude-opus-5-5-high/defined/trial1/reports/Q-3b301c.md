# Review of the Nightly Compaction Plan

The plan holds together. The timing has a large margin, the job doesn't compete for I/O, and the old data is deleted only after the new set is verified. It needs some hardening, but nothing in it fails as written.

## What holds up

- **Timing margin is large.** The worst observed volume is 1.3 TB. At the measured 1.0 TB/h that takes about 1.3 h, against a 3 h hard window. That is roughly 2.3× headroom, or about 1.7 h of slack.
- **The rehearsal is representative.** It ran at full size on a production-class host with the same disks and job settings. That is the right basis for the estimate.
- **No contention in the window.** The backup finishes by 00:45, and nothing else is scheduled between 01:00 and 04:00. The idle I/O class therefore shouldn't be starved.
- **Deletion is ordered safely.** The old segments are removed only after the new set is fully written and its checksums match the source. A killed run loses only its partial output, never the source data.

## Recommended changes

1. **Confirm disk headroom.** Old and new segment sets exist side by side until verification passes, so peak usage needs about 1.3 TB or more free beyond steady state. The plan doesn't mention this. Add a pre-flight free-space check that aborts cleanly if space is short.
2. **Guard against backup overrun.** The idle I/O class is fragile if the 00:45 finish ever slips. A late backup would starve the job and could push it past 04:00. Make the job wait for, or check, backup completion. Alternatively, alert when the backup runs late.
3. **Alert on kills and on runtime drift.** A killed run discards its output, and the next night then has two days of segments to compact. Alert on any kill or failure. Also track runtime against the window, for example warning above 2 h, so growth or disk degradation shows up before it becomes a miss.
4. **Plan for catch-up after a missed night.** Two days of backlog is about 2.6 TB, roughly 2.6 h. That still fits, but with little margin. Process one day per run, or document the backlog behavior explicitly.
5. **Harden the `rm -rf`.** Use absolute, validated paths. Refuse to run on empty or unset variables (`set -u`, `${VAR:?}`). Delete only the specific segment files that were verified, not a broad directory glob.
6. **Re-validate the throughput figure periodically.** One rehearsal is a single data point. Re-run it after hardware, kernel, or job-setting changes, and keep reviewing the volume trend beyond the 90-day window.
