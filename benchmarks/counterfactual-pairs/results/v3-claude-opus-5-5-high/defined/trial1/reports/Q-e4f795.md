# Plan Review: Month-End Invoice Batch Posting

## Does the plan work as written?

Yes, for the snapshot it describes.

**Size limit.** The arithmetic holds with a lot of headroom.

| Component | Bytes |
|---|---|
| 500 records × 4,100 bytes (measured maximum) | 2,050,000 |
| Envelope and separators | < 1,000 |
| **Worst case per request** | **< 2,051,000** |
| Partner limit | 5,000,000 |

That is about 41% of the limit. Two facts make the bound trustworthy:
- The snapshot is closed and fixed, so it can't change after the scan.
- The scan covered every record and measured serialized bytes, not characters. Multibyte text is therefore already counted.

The notes field has no length cap, but that doesn't matter here. The bound comes from measuring the actual data, not from a schema.

**Timeout.** 120 seconds against a stated 60-second worst case gives a 2× margin.

**No-resend rule.** No batch should be refused for size, so this rule never forces data loss on the size path.

## Recommended changes

1. **Run the size scan on every month's snapshot.** The 4,100-byte maximum is a fact about this snapshot. Because notes have no cap, next month's data could break the bound. Rescanning each cycle keeps the safety argument true over time.

2. **Check each batch's size just before sending it.** Serialize the full request body and compare its byte length to a margin below 5,000,000, such as 4,500,000. If it's over, split the batch before anything is sent. The check is cheap. The cost of skipping it is high: a refused batch can't be resent, and one missing invoice keeps the month open.

3. **Decide how to handle unclear outcomes.** If a request times out or the connection drops, the client can't tell whether the partner accepted the batch. Blindly resending risks a duplicate filing, and not resending risks a missing invoice. Before resending, the job should check with the partner, for example through a status or lookup endpoint, or by using an idempotency key if the partner supports one.

4. **Reconcile before the deadline.** After all batches are posted, compare the partner's record count with the snapshot. A missing invoice is then found while it can still be fixed, rather than at month-end close.

## Summary

The plan is sound for this snapshot: requests stay below half the size limit and the timeout is generous. Its weak spots are that the size guarantee depends on a one-time measurement of uncapped data, and that it doesn't say what to do when a send has an unknown outcome. Since a single failure keeps the month open, add the per-run scan, the pre-send size check, and an ambiguous-outcome procedure.

VERDICT: GO_WITH_CHANGES
