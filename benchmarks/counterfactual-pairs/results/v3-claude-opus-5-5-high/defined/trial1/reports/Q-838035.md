# Review: Nightly Compaction Job Plan

## Timing

- **Worst case:** 1.3 TB at the measured 1.0 TB/h is about 1.3 hours. That fits the 3-hour window with roughly 1.7 hours to spare, about 2.3× headroom.
- **Benchmark quality:** It used the full-size workload, identical disks and identical job settings. That includes the nice 19 / idle I/O priorities, so the 1.0 TB/h figure already reflects the real priority settings.
- **Growth room:** Input would have to reach about 3 TB before the window became a problem. That is well beyond the 90-day range of 1.0–1.3 TB.

## Contention

- **Priority risk:** Nice 19 and the idle I/O class only hurt when other work competes for CPU or disk.
- **Schedule:** Nothing else is booked from 01:00 to 04:00.
- **Backup agent:** It finishes by 00:45, before the job starts.
- **Result:** The low priorities are a reasonable choice, and the measured rate should hold.

## Deletion safety

- `rm -rf` of the previous segments runs only after the new set is fully written and its checksums match the source.
- This is the correct order. A terminated or failed run never deletes the old data, so discarded output loses nothing.

## Optional hardening (not required)

- **Backup overrun:** If "done by 00:45" is typical rather than guaranteed, a check or alert for an overrunning backup would protect the idle-class assumption.
- **Monitoring:** Alerting on runtime and on terminated runs would catch input growth or new competing work early.
- **Path guard:** A guard on the `rm -rf` target, such as refusing an empty or unexpected path, is cheap insurance.

None of these fixes a flaw in the plan as stated. The timing, priorities and deletion order all hold up.
