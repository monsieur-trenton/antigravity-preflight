# Review: Release 4.12 unique constraint on customers (tenant_id, email)

## Summary

The plan holds together. The duplicate check covers rows created before 4.9, and the 4.9 write path prevents any newer row from duplicating an older one or another newer one. So the index build should succeed. The build is non-blocking, and the sign-up dependency only takes effect once the constraint exists. Nothing breaks the abort rule. Still, several gaps could turn a "should succeed" into a failed or aborted release, and they are cheap to close.

## What's sound

- **Duplicate coverage logic is complete in principle.** Pre-4.9 rows were checked directly. Post-4.9 rows can't duplicate anything, because the write path locks the tenant and rejects an email that tenant already has. That covers old-vs-old, old-vs-new and new-vs-new pairs.
- **`CREATE UNIQUE INDEX CONCURRENTLY` followed by `ADD CONSTRAINT ... UNIQUE USING INDEX`** is the right pattern for a 38M-row table. Only the final attach takes a brief exclusive lock.
- **The leading `DROP INDEX IF EXISTS` is harmless on the first run.** It is also useful on a retry, because a failed concurrent build leaves an INVALID index with the same name.

## Recommended changes

1. **Re-run the duplicate check over the whole table, not just pre-4.9 rows.** The "since 4.9" guarantee assumes three things:
   - no 4.8 instances kept writing during the 4.9 rollout window,
   - the `created_at` boundary matches when the new code actually went live,
   - no out-of-band writes happened (admin scripts, bulk imports, manual data fixes, email *updates*).
   
   A full-table `GROUP BY tenant_id, email HAVING COUNT(*) > 1` costs little compared with an aborted release, and it removes all three assumptions. Run it again right before the migration.

2. **Make sure the migration does not run inside a transaction.** `CREATE INDEX CONCURRENTLY` cannot run in a transaction block. Many migration frameworks wrap each migration in one by default. If yours does, the migration errors out immediately and, under the runbook, 4.12 doesn't ship. Mark the migration non-transactional, or split it into separate steps.

3. **Use `DROP INDEX CONCURRENTLY IF EXISTS`** (also outside a transaction). A plain `DROP INDEX` takes an ACCESS EXCLUSIVE lock on `customers`. On a retry, that lock can queue behind long-running queries and stall all customer traffic behind it.

4. **Plan for a failed build explicitly.** If the build fails (a duplicate, a deadlock, or a cancelled session), you are left with an INVALID index. That index still adds write overhead and still enforces uniqueness on new writes. Add a post-build check that `pg_index.indisvalid` is true before attaching the constraint. Document the cleanup and retry steps, and state at what point the release counts as aborted.

5. **Set lock and statement timeouts for the attach step.** For example, a short `lock_timeout` on `ALTER TABLE ... ADD CONSTRAINT ... USING INDEX`, with a retry, so the step can't block traffic while it waits for its lock.

6. **Confirm what email equality means.** The index enforces exact byte equality under the column's collation. If the 4.9 code compares emails case-insensitively or after trimming, it is stricter than the index, which is fine. But if sign-up should treat `A@x.com` and `a@x.com` as the same account, this constraint won't do that. Decide whether the index should be on `lower(email)`, which would also need its own duplicate check. Also note that NULL emails won't conflict with each other.

7. **Order the deploy correctly.** The 4.12 sign-up code depends on the constraint to reject duplicates. Either the migration must finish before the new code serves traffic, or the existing 4.9 check must stay in place as a backstop.

VERDICT: GO_WITH_CHANGES
