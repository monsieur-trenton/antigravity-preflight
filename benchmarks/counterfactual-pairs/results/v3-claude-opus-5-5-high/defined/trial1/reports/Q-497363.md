# Review: 4.12 unique constraint on `customers (tenant_id, email)`

## Will the plan work as written?

**The duplicate check holds up.**
- The scan covered every row created before 4.9 and found no duplicate pairs.
- Since 4.9, every email write goes through one path. That path locks the tenant row and rejects any email the tenant already holds, including emails on pre-4.9 rows.
- So no post-4.9 write can collide with an older row or with another new row.
- NULLs are not a risk. `GROUP BY` puts NULLs in one group, while a unique index allows repeated NULLs, so the check is stricter than the constraint.

**The index sequence is sound.**
- `DROP INDEX IF EXISTS`, then `CREATE UNIQUE INDEX CONCURRENTLY`, then `ADD CONSTRAINT ... USING INDEX` is the standard low-lock way to do this.
- The leading DROP makes the migration safe to re-run if a concurrent build fails and leaves an INVALID index behind.

**Ordering is correct.** The 4.12 sign-up code depends on the constraint, and a failed migration stops the build from shipping. That code therefore never runs without the constraint.

I don't see anything that makes the plan fail or break its own rules. The improvements below are still worth making, because a failed migration aborts the whole release.

## Recommended changes

1. **Run the migration outside a transaction.** `CREATE INDEX CONCURRENTLY` errors inside a transaction block. Many migration frameworks wrap migrations in a transaction by default. Mark this migration as non-transactional explicitly, or it will abort the release.

2. **Use `DROP INDEX CONCURRENTLY IF EXISTS`.**
   - In production the DROP is a no-op on the first run.
   - On a retry after a failed build, a plain `DROP INDEX` takes an ACCESS EXCLUSIVE lock on a 38M-row table.
   - The concurrent form avoids that lock. It also requires running outside a transaction.

3. **Rerun the duplicate check over the full table right before the migration.**
   - The reasoning depends on "a single code path" really being the only writer. Admin tools, bulk imports, data-fix scripts, or tenant merges would break that assumption.
   - A full `GROUP BY ... HAVING COUNT(*) > 1` on 38M rows, run on a replica or off-peak, is cheap insurance. Without it, a surprise turns into a build failure late in the build.

4. **Verify the index before attaching it.** Confirm `pg_index.indisvalid` is true for the new index before `ADD CONSTRAINT ... USING INDEX`. A clear failure at that step is easier to diagnose than a confusing one.

5. **Set a `lock_timeout` on the `ALTER TABLE ... ADD CONSTRAINT` step, and plan a retry.**
   - The step needs a brief ACCESS EXCLUSIVE lock.
   - Behind a long-running transaction, it would queue and block all traffic to `customers`.
   - A short timeout with a retry keeps it from causing an outage.

6. **Plan for the build's duration.**
   - A concurrent build on 38M rows can take a long time.
   - It waits for every existing transaction to finish, so a long-running transaction can stall it.
   - Schedule the build with that in mind and monitor it with `pg_stat_progress_create_index`.

VERDICT: GO_WITH_CHANGES
