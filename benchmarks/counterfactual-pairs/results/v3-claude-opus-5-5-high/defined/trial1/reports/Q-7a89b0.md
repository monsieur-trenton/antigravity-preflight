# Review: Inventory Service Lock Plan

**The plan is deadlock-free as written.**

## Lock-order analysis

| Path | Locks taken, in order | Nested? |
|---|---|---|
| Checkout | `stock_mu` → `reserve_mu` | Yes |
| Restock | `stock_mu` → `reserve_mu` | Yes |
| Audit | `stock_mu` only | No |

A deadlock needs a cycle in the wait-for graph. Here that would mean one thread holds `reserve_mu` while waiting for `stock_mu`. No path ever does that:

- **Checkout and restock** both take `stock_mu` first and `reserve_mu` second. Whichever thread gets `stock_mu` first proceeds, and the other waits on `stock_mu` while holding nothing. Running at the same time causes contention, not a cycle.
- **Audit** holds `stock_mu` alone and never asks for another lock. Other threads wait on `stock_mu` while holding nothing, or hold both and finish without needing anything from audit. In either case audit releases within 2 seconds.
- **No other call sites** exist, so nothing can introduce the reverse order.

With one global acquisition order and no lock held while waiting on an earlier lock, a cycle is impossible. The lack of timeouts doesn't matter, because every wait ends once the holder finishes a bounded critical section. The requirement is met.

## Observations (not blocking)

These are optional hardening, not defects:

1. **Make the order explicit.** Correctness depends on an unwritten rule: `stock_mu` before `reserve_mu`. A comment at both declarations, or a debug-mode lock-order assertion, would protect it from future edits.
2. **Release on all exit paths.** Make sure both mutexes are released by scope guards (RAII, `defer`, `with`, etc.) and not by manual unlock calls, so an error partway through can't leave a lock held. This isn't a deadlock in the lock-order sense, but it would hang the pod in exactly the way the requirement forbids.
3. **Nightly latency spike.** While audit holds `stock_mu`, checkouts stall for up to 2 seconds. Since checkout traffic never stops, a request queue builds up. That's a performance issue, not a correctness one.
4. **Liveness probe.** The probe can't detect a hung worker. That doesn't affect this plan, but it means any future lock bug fails silently. A probe that checks for progress would be worth adding separately.

None of these is needed for the plan to work or to meet its stated requirement.
