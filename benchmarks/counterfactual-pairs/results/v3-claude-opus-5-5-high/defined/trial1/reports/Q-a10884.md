Classic lock-order inversion: checkout takes stock_mu → reserve_mu, restock takes reserve_mu → stock_mu. Both locks block with no timeout, and the two paths run concurrently on different threads. That meets all four Coffman conditions: mutual exclusion, hold-and-wait, no preemption, and circular wait.

**The deadlock interleaving:**
1. The checkout thread acquires stock_mu.
2. The restock thread acquires reserve_mu.
3. Checkout blocks waiting on reserve_mu, which restock holds.
4. Restock blocks waiting on stock_mu, which checkout holds.

Neither thread can ever proceed. Restock runs every 30s against continuous checkout traffic, so this is a matter of when, not if. The stated failure mode is that the pod stays "live" and stops selling until a manual restart. That directly violates the requirement that the service must never deadlock.

**What's fine:**
- The audit job takes only stock_mu and nests nothing. It can cause up to 2s of latency for checkout and restock, but it cannot join a cycle.
- No other code path touches either mutex, so the inversion above is the only cycle.

**Fix (pick one, the first is preferred):**
1. **Global lock ordering.** Make restock acquire stock_mu first, then reserve_mu, matching checkout. Document the order and enforce it, for example with a helper that always takes both in order, or a lock-order checker or annotation in debug builds.
2. **Collapse to one lock** if the two counts are always updated together. That is simpler and the contention cost is probably negligible here.
3. Alternatively, have restock do its two pieces of work under separate, non-nested critical sections, if adding units and trimming reservations don't need to be atomic together.

Avoid try-lock/timeout-and-retry as the primary fix. It turns deadlock into livelock risk and adds complexity, when consistent ordering solves the problem outright.
