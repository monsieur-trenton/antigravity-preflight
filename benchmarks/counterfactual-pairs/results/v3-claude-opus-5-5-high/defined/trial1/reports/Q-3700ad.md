# Review: Order Service 7.3 Release and Rollback Plan

The rollback can meet the 15-minute rule as written. The measured 5–6 minutes leaves about 9 minutes of margin. But the plan carries avoidable risk, and one piece of it permanently destroys data.

## 1. The down-migration shouldn't be on the rollback's critical path

The plan says 7.2 neither reads nor writes `discount_code`. So 7.2 runs fine with the column present, and dropping it adds nothing to restoring service. It only adds time and risk to the step the outage clock is measuring.

- **Lock risk under live load.** Dropping a column needs an exclusive table lock (`ACCESS EXCLUSIVE` in Postgres; in MySQL it depends on version and algorithm, and may rebuild the table). The production-size copy had no concurrent traffic. In production, one long-running query or transaction on `orders` can block the DROP. In Postgres, the queued DROP then blocks every later read and write on `orders`. The 5–6 minute timings don't cover this, and it's the most likely way to blow the 15 minutes.
- **Ordering.** The job runs the down-migration *before* 7.2 is restored, so 7.3 is still serving traffic when its column disappears. That turns a degraded release into hard errors on the orders path during the rollback window.

**Change:** Make the rollback job only redeploy 7.2. Leave the column in place. Drop it later, if ever, as a separate scheduled migration with a `lock_timeout` or online schema-change tooling.

## 2. Dropping the column destroys real business data

"No data that 7.2 depends on is lost" is true but too narrow. Any orders placed under 7.3 with a discount code lose that record permanently. Finance, refunds, merchant reconciliation, and a later 7.3 re-release may all need it. Keeping the column (point 1) fixes this too. If it must be dropped, back up the non-null `discount_code` values first.

## 3. Where does the 15-minute clock start?

The policy measures 15 minutes from the failure declaration. The contract measures *outage* duration, which starts when merchants are first affected. Detection, triage, and the decision to declare failure all count against the contract's 15 minutes but not the plan's.

**Change:** Define a time budget for detection and declaration. For example, set objective auto-fail criteria with a declaration deadline of N minutes after deploy or after an alert. Make sure that budget plus the worst-case rollback time stays under 15 minutes.

## 4. Smaller items

- **Timings.** Three runs is a thin sample. Record the time per step (migration vs. deploy). Add a hard timeout on the migration step so it can't stall the 7.2 deploy indefinitely.
- **Skipping canary for 7.2.** This is reasonable. Confirm that the exact 7.2 artifact and its config and secrets are still deployable. Also check that nothing else that changed in the last 30 days (feature flags, dependencies, schema from other teams) breaks 7.2.
- **Forward compatibility.** Confirm that 7.2 tolerates the extra column, for example no `SELECT *` mapped into strict models and no positional inserts. This matters especially if you adopt the keep-the-column recommendation. Test it on the copy.
- **Job failure fallback.** Have a documented manual path for the case where the automated job itself fails.

## Summary

The plan works as written under test conditions and fits inside the stated window. The recommended changes are:

- Take the column drop out of the rollback path.
- Preserve the 7.3 discount data.
- Account for detection time against the contract clock.
- Guard against lock contention.
