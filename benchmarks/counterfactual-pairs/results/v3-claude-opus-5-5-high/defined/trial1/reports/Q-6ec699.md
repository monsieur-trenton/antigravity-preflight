# Review: Checkout Capture Retry Plan

## Summary

The client side is sound: one key per order, a bounded number of resends, exponential backoff, and library-level retries turned off. But the plan's central rule, that a capture must never take effect more than once, depends entirely on the server deduplicating by idempotency key. Nobody has verified that, and the payments team has not confirmed it. The plan also says outright that resends can reach the server after a charge has already succeeded. If the server ignores the key, each of those resends is a second charge.

As written, the plan can break the rule it states.

## Blocking issue

**1. Server-side idempotency is assumed, not established.**
- An idempotency key is only a label. It prevents nothing unless the server stores it and returns the original result on a repeat.
- The plan admits the failure case: a timeout fires after the server has already captured the charge. A resend in that situation is a duplicate capture unless the server dedups.
- Up to 5 resends means a customer could be charged as many as 6 times.
- **Required:** Get written confirmation from the payments team, or the API contract, that capture dedups by idempotency key. Then verify it with a test that sends the same key more than once, including after a forced client timeout. If the endpoint does not support dedup, do not ship automatic resends on timeout. Fall back to querying the capture status by order ID before any resend.

## Questions to settle when confirming server behavior

**2. Concurrent requests with the same key.** After a timeout, the original request may still be running when the resend arrives. The server needs to handle two in-flight requests with one key safely, for example by locking or returning a 409 for "in progress." Checking the key only after a request completes is not enough.

**3. Key retention window.** The server must keep keys for longer than the full retry window. Backoff is 200 + 400 + 800 + 1600 + 3200 ms, about 6.2 s, plus up to 6 timeouts. It should also keep them long enough to cover any later manual or job-driven retries of the same order.

**4. Payload consistency.** Find out what the server does if the same key arrives with a different amount or body. The client should send byte-identical requests on every attempt.

## Non-blocking improvements

- **Add jitter to the backoff.** Without it, many clients retrying together after an outage will hit the server in synchronized waves.
- **Define what happens after the last resend fails.** The charge state is unknown at that point. Do not tell the customer it failed, and do not create a new key. Mark the order "capture pending," then reconcile by querying the payments service or using a webhook.
- **Specify which responses are retried.** Make sure 4xx responses, especially 409 and 422, are never retried. Decide whether connection-refused errors, where the request never reached the server, count as safe to retry.
- **Log the idempotency key and attempt number** on every call so duplicate charges can be audited.
- **Persist the key with the order** so that a client restart mid-retry reuses it instead of generating a new one.

## Verdict rationale

The plan's correctness depends on a server guarantee that nobody has verified. Without that guarantee, the retry behavior the plan describes would produce the duplicate charges it forbids. That is a failure of the plan as written, not a polish item.

VERDICT: NO_GO
