# Review: Point-in-time recovery plan for the orders PostgreSQL database

The plan works as written. The retention arithmetic holds, and the access model is sound. Several gaps should still be closed.

## What holds up

**The 14-day window fits within retention.**
- To recover to any moment 14 days back, the plan may need a base backup up to about 21 days old, plus all WAL since then.
- Strictly, the base must be one that has *finished*, so the oldest base needed is about 21 days plus the backup's run time.
- Base backups and WAL are both kept for 28 days. That leaves about 7 days of margin for the worst case.
- The lifecycle job runs nightly and only selects objects older than 28 days, so it cannot remove anything the window needs.

**Deletion is properly separated.**
- Database hosts can add objects but cannot overwrite or delete them.
- The bucket sits in a separate account.
- So a compromised or misbehaving database host cannot destroy its own recovery history. That is the right design.

**The drill targets the hard end of the window.** Choosing a moment 13 to 14 days back exercises the old base backups and long WAL replays.

## Recommended changes

1. **Set `archive_timeout` explicitly.**
   - PostgreSQL only archives a WAL segment once it is complete.
   - At low write volume, a 16 MB segment can stay open for hours. "Lands within 60 seconds" would then be true but beside the point, and the 5-minute recovery target would be missed during quiet periods.
   - Set `archive_timeout` to about 60–120 s so the 5-minute target holds regardless of load.

2. **Make `archive_command` safe to retry, given the no-overwrite rule.**
   - Suppose an upload succeeds but the command fails before reporting success.
   - PostgreSQL will retry, and the retry is an overwrite, which the bucket denies.
   - Archiving then stalls, and `pg_wal` fills up on the primary.
   - Fix: if the object already exists with identical content (checksum match), the command should return success. If the content differs, it should alert. pgBackRest and WAL-G handle this case.

3. **Monitor for missed base backups and archiving delay.**
   - The 7-day margin covers only about one missed Sunday.
   - If two backups fail in a row, the oldest base needed would be about 28 days old, which is the edge of retention.
   - Alert on:
     - a failed or missing weekly backup
     - archive delay above a few minutes, using `pg_stat_archiver` or the age of the newest object in the bucket
     - gaps in the WAL sequence
   - Consider extending retention to about 35 days, or adding a mid-week backup.

4. **Protect against deletion in the bucket itself.**
   - The lifecycle job's credentials can delete, and its safety currently depends on its rule being configured correctly.
   - Add object lock or a minimum-retention policy of about 21–28 days. A bad rule edit or stolen lifecycle credentials then cannot remove data the window depends on.

5. **Widen the drill.**
   - Add a regular drill aimed at the recent end, about 5–10 minutes ago, to confirm the 5-minute target.
   - Occasionally aim just before a Sunday's backup completes. That forces use of the oldest (about 21-day-old) base.
   - Record restore time against a recovery-time target, since the plan does not state one.
   - Check that every WAL segment between the chosen base and the target exists, not just that replay finished.

VERDICT: GO_WITH_CHANGES
