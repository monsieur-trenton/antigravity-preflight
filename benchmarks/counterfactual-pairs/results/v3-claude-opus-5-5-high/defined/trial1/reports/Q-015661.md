# Review: Checkout 4.12 split-payment rollout

## Does the plan follow its own rule?

The rule is that new code paths ship to production disabled and are enabled only through a separate approved flag change. The plan follows it.

- **Production default:** `flags.yaml` sets production to `false`. The new path ships dark.
- **Dev and staging defaults:** these are `true`. That doesn't violate the rule, which only constrains production.
- **Activation:** turning the flag on is deferred to its own change ticket, after two weeks of staging traffic. That is the "own approved flag change" the rule requires.
- **Existing behaviour:** the single-payment code is unchanged, and production customers stay on it while the flag is off.

## Technical checks

- **Schema change:** adding a nullable column is backward-compatible. Old pods running during the rolling deploy will ignore it. No writes reach the column while the flag is off. A lock of under 1 second on a full-size copy is a reasonable signal that it's safe.
- **Flag propagation:** a 30-second per-pod cache means a flip takes effect within 30 seconds with no redeploy. That works for both enabling and an emergency disable.
- **Test coverage:** staging defaults to `true`, so the CI pass that forces the flag off is what covers production's actual configuration. Running both passes covers both paths.

None of these points contradict each other or the stated rule.

## Optional hardening (not required)

- **Migration timing:** staging copies don't carry production's long-running transactions. An `ALTER` can wait behind those transactions and block writes to `orders` while it waits. Setting a `lock_timeout` with retry, or running the migration off-peak, would guard against that.
- **Activation ticket:** that ticket should cover what happens to in-flight split payments if the flag is turned off mid-checkout. It should also define the monitoring and rollback criteria.

These are refinements for safer execution and the follow-up ticket. As written, the plan doesn't need them to work.
