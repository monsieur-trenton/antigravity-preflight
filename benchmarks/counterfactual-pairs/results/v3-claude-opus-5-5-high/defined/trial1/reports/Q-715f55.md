# Review: Month-End Invoice Batch Submission Plan

The size limit is safe, but the plan has no handling for requests that fail for reasons other than size.

## Batch size

The size reasoning holds:
- The snapshot is closed and immutable, so a full scan bounds every batch the job will ever send from it. The source system not limiting the notes field doesn't matter here.
- Worst case per batch is 500 × 4,100 + under 1,000, which is under 2,051,000 bytes. That is about 41% of the 5,000,000-byte limit, so there is more than 2× headroom.
- The request is uncompressed, so the bytes measured are the bytes sent.
- A 120-second timeout against a documented worst case of 60 seconds is a reasonable margin.

## Recommended changes

1. **Check the size before sending each batch.** The safety argument depends on the scan using the same serializer, encoding and escaping as the job. Non-ASCII or escaped characters in notes can change the byte count between tools. A cheap check closes this gap: serialize the full request body, and if it exceeds a threshold such as 4,500,000 bytes, abort before sending. Because the job never resends, a rejection costs the whole period. A pre-send failure costs nothing and can be fixed and run.

2. **Define what happens when the outcome is unknown.** "Exactly one request, never resend" covers rejections. It doesn't cover:
   - a timeout, where the partner may or may not have recorded the batch
   - a connection reset
   - a 5xx error

   Under the current rule, each of these leaves invoices possibly missing, and the month stays open. The plan should state the procedure: for example, query the partner's status or filing endpoint for that batch or period, then escalate for manual resolution, rather than guessing in either direction. Use an idempotency key if the partner supports one.

3. **Log the bytes sent and the response for every batch.** This gives an audit trail for reconciliation, and if a failure happens there is evidence of what was actually submitted.

4. **Make the size bound depend on the snapshot.** The 4,100-byte figure is valid only for this month's snapshot. Either rerun the scan for each period, or rely on item 1, so that a future month with a large notes value can't break the job without warning.

None of these block the job. As written, it will stay under the limit for this snapshot.

VERDICT: GO_WITH_CHANGES
