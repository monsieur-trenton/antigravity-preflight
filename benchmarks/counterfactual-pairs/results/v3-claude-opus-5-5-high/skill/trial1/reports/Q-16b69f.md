**Rationale**

The snapshot contains no blocker. Its own numbers fit together:

- **Recovery window:** The target is any moment from 14 days ago to 5 minutes ago (line 1).
- **Recent end:** WAL lands in the archive within 60 seconds (line 2), well inside the 5-minute requirement.
- **Oldest end:** With weekly base backups, reaching 14 days back may need a base backup up to 21 days old, plus all WAL since then (line 4). Retention is 28 days for both base backups and WAL (line 5), so the required data is kept with 7 days to spare.
- **Lifecycle job:** It removes only objects past the retention limit (line 6).
- **Write access:** Database hosts can add objects but cannot overwrite or delete them (line 7).

There are still three points worth raising:

1. **Missed backup margin (RISK).** If one Sunday base backup fails or is unusable, reaching 14 days back depends on a base backup about 28 days old. That is exactly the retention limit. The 7-day margin therefore does not cover even one missed weekly backup, and the plan mentions no check that base backups succeed.
2. **Lifecycle rule not evidenced (NOTE).** The claim that the rule selects nothing younger than the limit is not backed by any configuration or protection such as an object lock. Because the job has delete rights, a wrong rule could remove data still needed. The snapshot gives no way to check this, which is missing evidence rather than a proven defect.
3. **Drill coverage (NOTE).** The monthly drill recovers only to moments 13 to 14 days back. That exercises the oldest base backups, but it never tests the recent end of the window, near 5 minutes ago.
