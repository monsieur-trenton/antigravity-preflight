**Rationale**

The plan's safety rule (line 2) is that no capture may be applied twice. Line 4 names the real hazard: a timeout can trigger a retry for a capture that already succeeded. The rest of the plan addresses that hazard directly:

- **Same key on every attempt (line 5).** Each attempt for an order reuses one idempotency key that is created once and never regenerated.
- **Idempotent endpoint (line 6).** The endpoint deduplicates per key. A staging run of 1,000 captures sent 6 times each recorded exactly 1,000 charges. The payments team also confirmed this is the documented contract.
- **No hidden retries (line 7).** The HTTP library's built-in retries are off, so the only repeats are the bounded 5 at line 3. All of them carry the same key.

No line in the snapshot contradicts another, and no line shows a path to a second charge. The text therefore supports no blocker.

One minor gap remains, recorded as a NOTE. Line 6 does not say whether the staging duplicates were sent while the first request was still being processed. That case matters because line 4 describes exactly such a race. The plan also does not state how long the server keeps idempotency keys. Both points are missing evidence, not proven defects. The documented contract in line 6 likely covers them.
