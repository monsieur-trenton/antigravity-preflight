**Rationale**

The sequence holds together on its own text. No line supports a blocker.

- **Trust before switch:** Every client gets the dual-root bundle on day 1 (line 4). Clients reload every 15 minutes without dropping connections (line 2). Fleet-wide confirmation is required on day 3, before the switch is scheduled (line 5). So every client trusts 'Internal Root 2026' before the server presents a cert from it on day 7 (line 6).
- **Old certificate:** The old certificate stays valid until day 60 (line 3). The server stops presenting it on day 7, well before it expires.
- **Old root removal:** 'Internal Root 2023' is removed on day 30 (line 8). By then the server has presented only the new chain for 23 days, so no client should lose connectivity from that removal.
- **Gaps that need confirmation:**
  - **Line 7, production clients unproven:** The two roots share a subject name and are told apart only by key identifier. The only evidence that clients pick the right root is from staging clients. Nothing shows that every production client type builds chains by key identifier rather than subject name alone. A client that matches on subject could choose the wrong root after the switch or after day 30. This is a RISK, not a proven defect.
  - **Line 8, no way back:** After day 30 the old root is gone from bundles and its key is destroyed. If the new chain fails, there is no path back to the old one. The plan describes no rollback criteria or hold period. This is a NOTE.
