**Rationale**

The snapshot's own text contains no blocker.

- **Retention covers the oldest restore point.** Line 1 requires recovery to any point up to 14 days back. Line 4 correctly says this can need a base backup up to 21 days old, plus all WAL written after it. Line 5 keeps both base backups and WAL for 28 days, which is more than 21. The lifecycle job deletes only objects older than 28 days (lines 5–6), so it cannot remove anything a valid restore needs.
- **The permissions do not conflict.** Line 6 gives the lifecycle job delete permission. Line 7 stops the database hosts from overwriting or deleting backups. These are different principals, so the lines are consistent.
- **The rehearsal exercises the oldest backups.** Restoring to a point 13–14 days back (line 8) uses base backups up to about 21 days old, so it tests the retention edge.

Two items are worth noting, but neither is a proven defect:

1. **Five-minute recovery point (RISK).** Line 2 says each WAL segment is archived within 60 seconds of being written. In PostgreSQL, a segment is normally archived only when it is complete. On a quiet database, a partly filled segment could wait more than 5 minutes unless a forced segment switch is configured, such as `archive_timeout`. The snapshot does not show this, so the 5-minute target in line 1 is unverified.
2. **Recent end not rehearsed (NOTE).** The monthly rehearsal (line 8) only tests the 13–14-day window. Nothing tests recovery close to "5 minutes ago," the other end of the requirement.
