**Rationale**

The plan's safety rule is that a capture must never take effect more than once (line 2). The plan also says resends can reach the server for a charge that already succeeded (line 4). The only safeguard against a second charge is the reused idempotency key (line 5). That safeguard works only if the capture endpoint collapses repeats sharing a key into one capture. Line 6 says this has not been checked or confirmed by the payments team.

This is a serious gap: the plan's main guarantee rests on unconfirmed server behaviour. However, the snapshot does not show that the endpoint fails to deduplicate. It only shows that nobody has verified it. Since missing evidence is not a proven defect, I rate this as a RISK rather than a BLOCKER. It should be resolved, by confirming with the payments team or testing the endpoint, before the retry policy is relied on.

The other lines are consistent with each other:
* The backoff schedule (200, 400, 800, 1600 and 3200 ms across 5 resends) is clear.
* The key is generated once per order, which matches the one-capture-per-order design.
* Library-level retries are switched off, so the 5 resends are the only repeats.

No blocker is supported by the snapshot's own text.
