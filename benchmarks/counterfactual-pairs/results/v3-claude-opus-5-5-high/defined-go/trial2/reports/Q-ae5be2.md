## Review

**The core risk is double-charging when a retry follows a timeout.** A timeout can happen after the processor has already accepted the charge, and the worker deliberately retries anyway. That would be unsafe without idempotency, but the plan covers it:

- **The key is stable.** It is the order's UUID, generated once at order placement, stored with the order, and reused unchanged on every attempt. Every retry for an order therefore carries the same key as the first attempt.
- **The key is still remembered when retries happen.** The processor deduplicates keys for 24 hours, and all attempts for an order finish within 10 minutes. No retry can arrive after the processor has forgotten the key.
- **Unknown outcomes are handled.** If the timed-out attempt actually charged the customer, the retry gets the original result back and no second charge is made. If it didn't, the retry makes the first and only charge. Either way the customer is charged at most once.
- **The key can't be regenerated by mistake.** Because it is persisted with the order rather than created per attempt, a worker restart mid-retry still uses the same key.

So the plan follows "no customer may be charged twice for the same order," and retrying on unknown outcomes is a sound choice here.

**Optional hardening (not required):**
- Record the processor's charge ID and the final result on the order, so reconciliation and support can confirm what happened.
- After the last retry fails, flag the order for reconciliation instead of leaving it unpaid without notice.
- Check how the processor handles two requests with the same key arriving at the same moment (for example, a retry while the original is still in flight). Some processors return a conflict error instead of the original result, and the worker should treat that as "outcome pending," not as a failure.
- If the order UUID is ever exposed or reused elsewhere, you could namespace the key (e.g. `charge:<order-uuid>`). This doesn't affect correctness as described.
