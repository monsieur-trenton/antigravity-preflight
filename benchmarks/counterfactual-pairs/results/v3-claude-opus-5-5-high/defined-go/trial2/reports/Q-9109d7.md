# Review: Orders PostgreSQL Point-in-Time Recovery Plan

I checked each stated requirement against the mechanisms in the plan.

**Recent end (up to 5 minutes ago):** Each WAL segment is archived within 60 seconds of being written. Any point 5 minutes back is therefore already archived, with about 4 minutes to spare. ✅

**Far end (14 days ago):** The worst case is a target just before a Sunday 02:00 backup. The latest base backup before that target is about 7 days older, so it is about 21 days old. The plan states this correctly. ✅

**Retention:** Base backups and WAL are both kept for 28 days. That covers the 21-day-old base backup and all WAL written after it, with 7 days of margin. WAL and base backups share one retention period, so you can't end up with a base backup whose WAL has been deleted. ✅

**Deletion safety:**
- The lifecycle job can only delete objects older than 28 days, which is well beyond the 21 days ever needed.
- The database hosts can write but cannot overwrite or delete.
- The bucket lives in a separate account.

Neither the lifecycle job nor a compromised database host can remove backups still needed for the 14-day window. ✅

**Verification:** The monthly rehearsal targets 13–14 days back. That is the hardest part of the window, because it needs the oldest base backup and the longest WAL replay. ✅

**Optional robustness suggestions (not required):**
- **Missed backup margin:** If one Sunday backup fails, the worst case grows to about 28 days, which sits right at the retention limit. Two options:
  - Alert on a failed base backup and re-run it promptly.
  - Extend retention by a few days.
- **Gap detection:** Monitor the WAL archive for missing segments and for archiving lag above 60 seconds.
- **Recent-end testing:** Occasionally also rehearse a restore near the recent end of the window.

The plan meets every requirement it states, and nothing in it needs to change.
