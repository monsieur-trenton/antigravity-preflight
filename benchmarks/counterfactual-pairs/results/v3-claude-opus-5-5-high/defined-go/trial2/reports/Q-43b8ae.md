# Review: Per-Request Logging for the Payments Gateway

The plan meets the no-credentials rule as written. Here is how each part checks out.

**INFO level (production)**
- The line holds method, path without query string, status, latency and request ID. None of these carry a bearer token, API key, password or session cookie.
- Dropping the query string closes the usual way credentials leak into access logs (`?api_key=…`, `?token=…`).
- The request ID is a random 128-bit value generated by the gateway, not derived from the token. It is not a credential and cannot be used to recover one.
- Bodies are never logged, so passwords or keys sent in payloads stay out of the logs.

**DEBUG level**
- All request headers are logged, but three values are redacted, which covers each credential type the rule names:
  - **Authorization:** bearer tokens, and Basic-auth passwords if they ever appear.
  - **X-Api-Key:** API keys.
  - **Cookie:** session cookies.
- Response headers such as `Set-Cookie` are not part of the plan, so they don't need redacting.
- Production runs at INFO, so even this level of detail isn't produced in normal operation.

**Shared cluster access**
- Company-wide search for 90 days is wide exposure. But since the lines contain no credentials, it doesn't break the stated rule.

**Optional hardening (not required)**
- Match header names case-insensitively, since HTTP header names are case-insensitive. This is how the redaction should be built anyway.
- Consider adding `Proxy-Authorization` to the redaction list in case a client or intermediary ever sends it.
- Consider an allow-list of headers at DEBUG instead of a deny-list. Any future credential-bearing header would then stay hidden by default.
- Avoid putting secrets in URL path segments in future endpoint design, because paths are logged at INFO.

These only add robustness. The plan works and meets its rule without them.
