## Review

**Blocking issue: bearer tokens will be written to the logs.**

The plan logs every request header name and value at INFO, and redacts only `Cookie` and `X-Api-Key`. Every caller sends a bearer token in the `Authorization` header, and that header is not on the redaction list. So every request in production writes a live credential to the logs, because production runs at INFO.

This directly breaks the service's own rule that logs must never contain bearer tokens. The exposure is wide: lines go to a shared cluster that every engineer in the company can search for 90 days. Anyone with search access could collect valid tokens and impersonate callers to the payments gateway.

**Required change:**
- Add `Authorization` to the redaction list. Also add `Proxy-Authorization`, which can carry the same kind of credential.
- Better still, switch from a denylist to an allowlist. Log the values of a known set of safe headers, such as `Content-Type`, `User-Agent`, `Content-Length` and `X-Forwarded-For` if allowed by policy. Log only the names of all other headers. With a denylist, any new or custom credential header a caller adds will leak by default.
- If header values aren't needed to trace slow upstream calls, drop the header dump entirely. The method, path, status, latency and request ID line already meets the stated goal.

**Parts that are fine:**
- Stripping the query string from the path avoids leaking tokens or keys passed as query parameters.
- Not logging request or response bodies avoids passwords and other credentials in payloads.
- The request ID is random and generated by the gateway, so it reveals nothing about the token and is safe to log and search on.

**Follow-up after fixing:** Tokens have probably already been logged if any of this has shipped. Purge those lines from the cluster and rotate the affected tokens.

VERDICT: NO_GO
