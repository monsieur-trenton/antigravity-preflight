# Review: Per-Request Logging for the Payments Gateway

## Checking each log field against the credential rule

The rule names four kinds of credential: bearer tokens, API keys, passwords and session cookies. I checked every logged field against each of them.

**INFO level (production)**
- **Method and status:** these cannot carry credentials.
- **Path without query string:** removing the query string closes the most common way tokens and keys leak into URLs, such as `?api_key=` or `?token=`. The path itself has no stated credential content.
- **Latency:** a number. No risk.
- **Request ID:** a random 128-bit value generated by the gateway, not derived from the token or any caller input. It cannot leak or correlate to a credential.

**DEBUG level**
- **Authorization:** callers send their bearer token here, and its value is redacted.
- **X-Api-Key:** this carries API keys, and its value is redacted.
- **Cookie:** this carries session cookies, and its value is redacted.
- **Passwords:** these would arrive in request bodies, which are never logged.
- **Response headers such as `Set-Cookie`:** the plan logs only request headers, so these are not written.

**Bodies:** never logged at any level, so payment payloads and any credentials inside them stay out of logs.

## Exposure

Logs are searchable company-wide for 90 days, so any leak would be serious. That is why the redaction design matters. However, the plan's defined credential channels are all covered at both levels. Production runs at INFO, where no header values appear at all. Nothing in the plan as written puts a credential into a log line, and it meets its goal of tracing slow upstream calls by latency and request ID.

## Optional hardening (not required changes)

- **Match header names case-insensitively.** HTTP header names are case-insensitive, so `authorization` and `x-api-key` should be redacted too. Also redact every value when a header is repeated.
- **Consider an allowlist at DEBUG.** Logging only known-safe headers is sturdier than a denylist. It would also catch `Proxy-Authorization` or a future custom auth header that someone adds without updating the redaction list.
- **Guard against DEBUG in production.** A config check or alert would stop someone accidentally turning on DEBUG in prod.
- **Watch path design.** If a future endpoint ever puts a secret in the path, the INFO line would capture it.

None of these points fix a defect in the plan as written. They only make a working plan more robust.
