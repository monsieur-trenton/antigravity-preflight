## Review

**The day-5 step breaks the plan's own no-downtime rule.** On day 5, 'Internal Root 2023' is removed from the trust bundle. Clients reload the bundle every 15 minutes, so by roughly day 5 + 15 minutes every client trusts only 'Internal Root 2026'. But the server keeps presenting its 2023-issued certificate until day 7. For about two days, every new connection, reconnect or handshake will fail chain validation. Already-open connections survive because the reload doesn't drop them. Anything that reconnects (restarts, pool churn, load-balancer rotation) loses connectivity. This violates "no client may lose connectivity at any point."

Destroying the 2023 private key on day 5 is harmless by itself, since the live server certificate and its key are separate. But it ties the change to the same broken step, and you can't easily reissue under the old root if you need to roll back.

**What works as written:**
- **Day 1:** distributing a bundle with both roots before any server change is the correct overlap step.
- **Day 3:** gating the switch on fleet inventory showing every client with the dual-root bundle hash is a sound precondition.
- **Day 7:** presenting the 2026-issued certificate with its full chain is correct.
- **Shared subject name:** the two roots share a subject name but have distinct key identifiers. Staging showed clients with both roots accept certificates from either, so path-building ambiguity has been tested.
- **Old cert validity:** the old certificate stays valid until day 60, which leaves room for the overlap.

**Required change:** move the removal of 'Internal Root 2023' (and the key destruction) to after day 7. Gate it on confirmation that every server instance presents the 2026-issued certificate. Leave a soak or rollback window before removing the old root, and confirm through inventory that clients picked up the new bundle afterward. Destroy the old root key only once rollback to the 2023 certificate is no longer needed.

VERDICT: NO_GO
