**Rationale**

The snapshot's own text satisfies the no-double-charge rule (line 7). There are no blockers.

- **Same key on every attempt.** Line 5 says the idempotency key is the order's UUID. It is created once, stored with the order, and sent unchanged on every attempt.
- **Retries fall inside the processor's window.** Line 4 bounds all attempts for an order to 10 minutes. Line 2 says a repeated key within 24 hours returns the original result and does not charge again.
- **Unknown-outcome retries are safe.** Line 3 says a timed-out request may already have been charged. Line 6 deliberately retries in that case. A retry with the same key gets the original result rather than a second charge, so the two lines are consistent.
- **No conflicts between lines.** A new charge needs a new key (line 2), and the plan never generates a second key for an order.

One minor point is not a defect against the stated rule. Line 4 also retries "failed" submissions. Line 2 says a repeated key returns the original result, so retrying a definitively failed charge with the same key might just return the same failure. That would make such retries ineffective, but it cannot cause a double charge. The snapshot does not say how the processor handles keys whose original request failed, so this is optional robustness, not a needed change.
