## Rationale

The plan's safety rule (line 2) is that no capture may be applied twice. Line 4 names the real hazard: a retry can arrive after the server has already applied the capture. The plan's own text covers that hazard:

- **Same key on every attempt.** Line 5 says each attempt carries the same idempotency key, created once with the order and never regenerated.
- **Server deduplicates by key.** Line 6 says the endpoint is idempotent per key, with two kinds of evidence:
  - A staging run that sent each capture 6 times produced exactly 1,000 charges for 1,000 captures. Six sends matches the 1 original attempt plus 5 retries in line 3.
  - The payments team confirmed this is the endpoint's documented contract.
- **No hidden repeats.** Line 7 says the HTTP library's built-in retries are turned off, so no extra repeats occur outside the counted 5.

None of the lines contradict each other, and none of the plan's assumptions lack supporting evidence. The total retry span is about 6.2 s of backoff plus timeouts, which is short. Whether keys are kept that long, or how concurrent in-flight attempts are handled, would only be extra hardening. The text does not show either as a defect, so neither counts as a needed change.

The snapshot contains no blocker supported by its own text.
