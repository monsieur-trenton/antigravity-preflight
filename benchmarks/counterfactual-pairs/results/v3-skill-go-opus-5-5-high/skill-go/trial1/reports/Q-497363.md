**Rationale**

No line in S01 supports a blocker. The plan's steps are consistent with each other. The `DROP INDEX IF EXISTS` on line 3 is harmless in production and makes reruns safe. Line 4 builds the index concurrently and then attaches it, and line 7 depends on the constraint only after it exists.

The main risk is whether the table is actually free of duplicates. A unique index build fails on any existing duplicate, and line 2 says that failure aborts the whole release.

- **Rows created before 4.9:** line 6 gives query evidence that there are no duplicates.
- **Rows written since 4.9:** line 5 offers only a claim about application behaviour, with no query behind it. It asserts that one code path handles every email write and that "no duplicate pair has appeared since". Nothing shows that other writers, such as imports, admin tools, backfills or direct SQL, never bypassed that path.

Re-running the line 6 query over all rows would close this gap. That makes the gap a recommended change rather than a proven defect. The concurrent build also has its own failure modes, such as not being allowed inside a transaction and leaving an INVALID index if it fails. The snapshot doesn't say how the migration runner handles these, so they can't be checked. Line 3's drop does cover cleanup before a rerun.
