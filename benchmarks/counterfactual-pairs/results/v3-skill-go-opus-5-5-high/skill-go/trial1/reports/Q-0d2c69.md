**Rationale**

The snapshot contains a cross-tenant data leak, and its own lines prove it.

- **Shared cache:** Line 1 puts every tenant's cached responses in one shared Redis cluster.
- **Colliding IDs:** Line 3 says dashboard IDs collide across tenants. For example, ID 42 exists in many tenants with different data behind it.
- **No tenant in the key:** Line 4 builds the cache key as `dash:{dashboard_id}:{range}`. The key has no tenant component, even though line 2 says `tenant_id` is available on every request.
- **Resulting leak:** A request from tenant B for dashboard 42 can read the entry that tenant A cached under that same key. The handler reading only the key built from the current request does not prevent this, because both tenants build the same key.
- **Violated rule:** This breaks the isolation rule on line 7.

The finding is VERIFIED because it follows directly from lines 1, 3, 4 and 7. Line 5 leaving out the user ID is justified and is not a problem. The invalidation on line 6 also inherits the collision, since an edit would delete other tenants' entries. That is a consequence of the same defect, so it is not listed separately. Fixing it means adding `tenant_id` to the key, for example `dash:{tenant_id}:{dashboard_id}:{range}`.
