## Rationale

The plan contains a lock-ordering inversion that its own text shows can deadlock.

- **Checkout path (line 2):** holds `stock_mu`, then requests `reserve_mu`.
- **Restock path (line 3):** holds `reserve_mu`, then requests `stock_mu`. This is the opposite order.
- **Concurrency (line 4):** both paths often run at the same time on separate threads.
- **No escape (line 1):** acquisition blocks indefinitely with no timeout.

So checkout can hold `stock_mu` while restock holds `reserve_mu`, and each then waits forever for the other's lock. That is a circular wait, and it violates line 7's requirement that a deadlock is never acceptable. Line 7 also says a hung pod is not recovered automatically, which makes the impact serious. Every condition comes directly from the snapshot, so this is a verified blocker.

The nightly audit job (line 5) takes only `stock_mu`, holds it for a bounded time and requests no other lock. It cannot take part in a cycle, so it is not a finding. Line 6 rules out other acquisition sites, so the analysis is complete for the stated scope.
