Rationale: the plan contains a blocker supported entirely by its own text. Line 1 puts every tenant's cached responses in one shared Redis cluster. Line 3 says the same dashboard ID, such as 42, exists in many tenants with different data. Line 4 builds the cache key from only the dashboard ID and range, with no tenant_id. The tenant_id is available, since line 2 says the gateway attaches it, but the key never uses it.

So a caller in tenant B asking for dashboard 42 over the same range builds the same key as tenant A. Tenant B then receives tenant A's cached response. This directly breaks the isolation rule on line 7.

Line 4 also says the handler only reads or writes the key built from the current request. That does not help, because both tenants build the identical key.

Line 5's choice to leave out the user ID is consistent with line 5's own premise, so it is not a defect. The fix is to add tenant_id to the key, for example "dash:{tenant_id}:{dashboard_id}:{range}".

A secondary effect: under the current key, an edit in one tenant would also delete cached entries belonging to other tenants (line 6). Fixing the key resolves this as well.
