**Rationale**

The snapshot does not support a deadlock blocker.

- **Same lock order on both paths:** Checkout (line 2) and restock (line 3) both take stock_mu first and then reserve_mu, while still holding stock_mu. When every holder of both locks uses the same order, they cannot wait on each other in a cycle. Running both paths at once (line 4) only causes contention, not deadlock.
- **Audit job cannot join a cycle:** It takes only stock_mu, holds it for at most 2 seconds, and never asks for another lock while holding it (line 5). It can briefly delay checkout or restock, but it never waits on reserve_mu.
- **No other lock users:** Line 6 says neither mutex is acquired anywhere else, so there is no hidden path with the opposite order.
- **Requirement is met:** Lacking a timeout (line 1) would turn a lock-order cycle into a permanent hang, but no such cycle exists. The requirement on line 7 is therefore satisfied as written.

The nightly audit can stall checkouts for up to 2 seconds. That is bounded and is not a deadlock, so it is not a change the plan needs.
