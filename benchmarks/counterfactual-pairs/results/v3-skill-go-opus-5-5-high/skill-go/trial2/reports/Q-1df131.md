**Rationale**

The plan follows a sound overlap sequence, and no line conflicts with another:

- **Line 4 (day 1):** every client gets a bundle trusting both roots.
- **Lines 2 and 5:** clients reload the bundle every 15 minutes without dropping connections. On day 3, inventory must confirm every client holds the dual-root bundle before the switch is scheduled. That gate comes well before the day 7 switch.
- **Lines 3 and 6 (day 7):** the server switches from the old certificate, valid until day 60, to the new one with its full chain. Clients already trust both roots, so they stay connected.
- **Line 8 (day 30):** the old root is removed and its key destroyed. The server has presented only the new certificate since day 7, so no client depends on the old root then. The old certificate is still valid until day 60, so rollback stays possible until day 30.

The likeliest technical trap is in line 7: two roots with the same subject name can confuse some clients when they build a certificate chain. The snapshot says staging clients accepted certificates from either root. That covers the trap, but the result can't be checked here and was shown only for staging, not production. It's a minor note, not a defect.

The snapshot supports no blocker, and nothing needs to change.
