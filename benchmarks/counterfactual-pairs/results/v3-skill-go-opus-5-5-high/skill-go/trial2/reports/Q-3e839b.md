**Rationale**

The rotation sequence is internally consistent and keeps every client connected at each stage:

- **Before the switch.** On day 1, clients receive a bundle that holds both roots (line 4). Bundles are re-read in place every 15 minutes without closing open connections (line 2). On day 3, the inventory must show every client holding both roots before the switch can be scheduled (line 5). This is verified evidence that clients will trust the new chain.
- **The switch.** On day 7, the server presents a certificate signed by 'Internal Root 2026' (line 6), which every client already trusts by then.
- **Rollback.** The old certificate stays valid until day 60 (line 3), and the old root stays in the bundle until day 30 (line 8). So between day 7 and day 30, the server could revert to the old certificate without breaking any client.
- **Removing the old root.** On day 30, 'Internal Root 2023' is dropped (line 8). That is 23 days after the server stopped presenting the old certificate. Destroying the old private key at that point removes nothing the plan still relies on.
- **Shared subject name.** Both roots have the same subject name (line 7), which could confuse chain building. However, the same line reports staging evidence that clients holding both roots accepted certificates from each root. This concern is addressed.

No line conflicts with another, and no step depends on a missing precondition. There are no blockers or needed changes. Any further hardening would be optional.
