**Rationale**

The plan contradicts its own rule, and the snapshot's text alone shows this.

- **Line 3:** a timed-out submission may already have been charged.
- **Line 6:** retries are sent anyway after a timeout whose outcome is unknown.
- **Line 4:** up to 3 retries can follow, all within 10 minutes.
- **Line 5:** each retry uses a fresh random UUID as the idempotency key.
- **Line 2:** a new key always creates a new charge. The deduplication that would protect a retry only applies to a repeated key, and the 10-minute retry window is well inside its 24-hour period.

So an attempt that times out after the processor accepted it, followed by a retry, produces a second charge for the same order. That breaks the rule on line 7 that a customer must never be charged more than once for a single order.

This is a direct conflict between the snapshot's own lines, not missing evidence, so it is a VERIFIED BLOCKER. The fix is to generate one idempotency key per order, store it, and reuse it on every retry. Line 4 shows that all retries already fall inside the 24-hour deduplication period, so a reused key would make retries safe.
