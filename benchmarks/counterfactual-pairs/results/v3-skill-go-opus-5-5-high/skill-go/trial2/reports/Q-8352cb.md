**Rationale**

The plan contradicts itself on the production flag state, and the text alone supports this.

- **Line 3 is a blocker.** It says the default in flags.yaml is `true` in production. That breaks three other lines:
  - Line 2 requires every new code path to ship switched off in production and be turned on only through a separate, approved flag change.
  - Line 4 assumes customers stay on the single-payment path "while the flag is off."
  - Line 8 says enabling in production is a later change ticket.

  With line 3 as written, deploying 4.12 would turn on split payment in production at release. That skips the separate approved change and the two weeks of staging traffic.
- **Line 7 is a related risk.** CI forces the flag off "to mirror production." Given line 3, that assumption is wrong, so CI would not test the configuration production would actually get.
- **Line 5 depends on line 3.** "Not written while the flag is off" only holds if the flag really is off, so it needs no separate finding.
- **No other blockers.** Line 6 (30-second cache with no redeploy) and line 5 (brief lock, nullable column) have no conflicts.

The fix is to set the production default in flags.yaml to `false`.
