**Rationale**

The snapshot's own text describes a classic lock-ordering inversion that can deadlock. Each premise is stated directly:

- **Opposite lock orders:** Checkout takes stock_mu, then reserve_mu, while holding stock_mu (line 2). Restock takes reserve_mu, then stock_mu, while holding reserve_mu (line 3).
- **Concurrency:** Both paths often run at the same time on separate threads (line 4).
- **No escape:** Lock acquisition blocks indefinitely with no timeout (line 1), so a circular wait never resolves.
- **No other mitigation:** Neither mutex is acquired anywhere else (line 6), so nothing else in the code breaks the cycle.

So a checkout thread holding stock_mu and a restock thread holding reserve_mu can each wait forever for the other. This violates line 7's requirement that a deadlock is never acceptable. Every link in that chain comes from the snapshot, so this is a verified blocker, not an inference from missing evidence.

The nightly audit (line 5) holds only stock_mu, for a bounded 2 seconds, and requests no other lock. It cannot take part in a cycle, so it adds only brief contention and is not reported as a finding.

The fix the plan needs is a single global lock order for both paths (for example, stock_mu before reserve_mu in restock as well), or an equivalent mechanism such as acquiring both locks together.
