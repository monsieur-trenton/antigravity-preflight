**Rationale**

The plan's safety rule (line 2) is that no capture may be charged twice. The danger it names is real: a retry after a timeout may reach a capture the server already applied (line 4). The plan answers that danger with three mechanisms, and its own text supports each one:

- **Stable idempotency key.** Every attempt for an order uses the same UUID, created once with the order and never regenerated (line 5).
- **Server-side deduplication by key.** The endpoint deduplicates per key. A staging run backs this up: 1,000 captures each sent 6 times, which is 1 original plus 5 retries and matches line 3, produced exactly 1,000 charges. The payments team also confirmed this is the documented contract (line 6).
- **No hidden extra retries.** The HTTP library's built-in retries are turned off, so the 5 retries in line 3 are the only repeats (line 7).

No line conflicts with another, and nothing in the text shows a path to a double charge. No blocker is supported.

One point is not shown either way, so it is a NOTE rather than a defect. Line 6 does not say whether the staging run sent duplicates while the original was still being processed. That is exactly the timeout case in line 4. It also does not say how long the endpoint keeps a key, against a backoff window of about 6.2 s plus request timeouts. The documented contract probably covers both. Confirming them explicitly would strengthen the evidence.
