**Rationale**

The double-charge risk is real, but the plan's own text closes it:

- **Unknown outcomes can be resent.** Line 3 says a timeout may hide a charge that already went through. Line 6 says retries are sent anyway in that case.
- **The key never changes.** Line 5 says the key is the order's UUID. It is created once, stored with the order and sent unchanged on every attempt. So no retry for an order can carry a new key. Line 2 says only a new key creates a new charge.
- **Retries fall inside the deduplication window.** Line 2 says the processor deduplicates a repeated key for 24 hours. Line 4 says all attempts for an order finish within 10 minutes.

Together, any retry after a hidden successful charge returns the original result and does not charge again. The rule on line 7, never charging more than once per order, holds for the retry path the plan describes. The snapshot gives no text supporting a blocker.

**One non-blocking note**

Line 4 retries "failed" submissions as well as timeouts. Line 2 says a repeated key returns the original result. If the processor accepted and rejected the request, a retry with the same key should return that same rejection. Those retries would not help get the order paid, but they also cannot cause a double charge. The snapshot does not say what kinds of failure are retried, so this is unverified.

**Scope**

I checked only the paths described in the snapshot. Nothing in it says whether other paths could submit a charge, such as re-enqueuing an order after the 10-minute window. Its absence is not treated as a defect.
