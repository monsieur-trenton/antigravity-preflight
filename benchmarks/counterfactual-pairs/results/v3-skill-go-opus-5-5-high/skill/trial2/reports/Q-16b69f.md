**Rationale**

The snapshot's own text contains no blocker.

- **Retention covers the worst case.** Line 4 says recovering 14 days back may need a base backup up to 21 days old, plus all WAL since. Line 5 keeps base backups and WAL for 28 days, and line 6 says deletion never touches anything younger than that. So the stated worst case fits inside retention, with 7 days of margin.
- **The 5-minute target is consistent on paper.** Line 2 says each WAL segment reaches the archive within 60 seconds of being written.
- **The archive is protected.** Line 7 says database hosts can add objects but not overwrite or remove them, in a separate account.

These issues are worth addressing but do not block the plan:

1. **One missed weekly backup removes most of the margin (line 4).** If a Sunday backup fails, recovering to 14 days ago would need the backup before it, which could be about 28 days old. That is at or past the retention limit. The plan does not say how failed base backups are detected or handled. This is an inference, not stated in the plan (UNVERIFIED).
2. **The 60-second claim may not hold when traffic is low (line 2).** The timing counts from when a segment is "written", meaning complete. When few changes happen, a segment can stay partly filled for a long time, unless the database is set to force a new segment on a timer. The plan does not mention such a setting, so the 5-minute target is not shown to hold in quiet periods (UNVERIFIED).
3. **The drill only tests the oldest end of the window (line 8).** It never tests recovery to a recent moment, near 5 minutes ago. So the newest-data end of the requirement is never exercised (NOTE).
